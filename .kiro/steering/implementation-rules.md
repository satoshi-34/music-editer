# 実装ルールまとめ

このファイルは、毎回の実装で迷わないための「作業前チェックリスト」です。  
詳細ルールは `CLAUDE.md` を優先し、このファイルは実務向けの要約として使います。

## 1. 最初に確認するファイル

- `CLAUDE.md`
- `.claude/specs/*/design.md`
- `.kiro/specs/*/design.md`
- 必要に応じて `README.md`

## 2. コメント方針

- コメントは **必ず日本語**
- 初学者が読んでも分かるように「何をしているか」より **なぜそうするか** を書く
- 専門用語を使うときは短く補足する
- 自明な処理にはコメントを書きすぎない
- 調整値や定数は「その値で何が変わるか」まで書く

## 3. 実装方針

- まず既存コードの流れを読んでから直す
- 既存の設計や命名をできるだけ崩さない
- ブラウザ差異や音声まわりのような不安定要素には、理由付きコメントを残す
- UI だけ直して内部状態がずれないよう、状態管理と実処理をセットで確認する

## 4. 変更後に必ずやること

- 影響範囲のあるテストを実行する
- 少なくとも `npm run build` を確認する
- 実装に応じて `README.md` と設計書を更新する

## 5. 音声まわりの注意

- `AudioContext` はブラウザ状態に左右されるため、`running / suspended / closed` を意識する
- 音色調整では、以下の役割を意識して値を変える
- `oscillators`: 音のキャラクター（明るさ、硬さ、広がり）
- `attack`: 鳴り始めの速さ
- `peakGain`: 最初の強さ
- `decayTarget`: すぐ減衰した後に残る量
- `releaseFloor`: 消え際の残り方
- `tailSeconds`: 余韻の長さ

## 6. Git / 作業の基本

- 破壊的なコマンドは避ける
- 関係ない差分は戻さない
- 作業内容が変わったら、今の前提に合わせてドキュメントも更新する

## 7. 依存追加の安全手順

- 新しい依存は、まず `postinstall` を自動で走らせない前提で確認する
- 可能なら Docker を使い、`--ignore-scripts` 付きで追加する
- このリポジトリでは `sh ./scripts/safe-add-package-in-docker.sh <package...>` を優先して使う
- 依存追加後は `npm run build` と必要なテストを確認し、README と設計書にも理由を残す
