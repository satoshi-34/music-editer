# 浄書の既定値（線の太さ・間隔・文字の階層）の棚卸しとA/B比較

> Issue #195（初見の浄書品質 段1）の調査記録。
> **この段ではアプリの値を一切変更していない。** 実測・慣行との対照・候補値の提示までが範囲で、
> どの値を採用するかは比較材料を見た人間（運用者・#89 のインタビュー）が決める。

## 1. 目的とスコープ

初見の印象を決める描画の既定値 — 五線の太さ、段/パート間隔の初期表示、文字（タイトル・パート名・歌詞等）の
大きさと太さ — が、浄書慣行に照らしてどうなっているかを数値で明らかにする。

- **やったこと**: 実際のブラウザ描画から現状値を実測 → 標準（Bravura の engravingDefaults 等）と対照 →
  乖離を一覧化 → 候補値2案を作り、実アプリ上で切り替えて見比べられる道具を用意
- **やっていないこと**: 既定値の変更、描画コードの変更（段2で行う）

## 2. 測定方法（再現手順）

- 基準リビジョン: `origin/main` = `ee7101d`（2026-08-08 時点）
- 測定環境: Chromium（アプリ内ブラウザ）、dev サーバー、画面表示のズーム 100%、設定はすべて工場出荷既定
  （`score-notation-size` 等のユーザー設定キーが localStorage に無い状態であることを確認済み）
- 譜例（`docs/qa/engraving-defaults/` に同梱。アプリの保存データ形式そのままなので「読込」で開ける）
  - `moonlight-figure-piano.json` — ピアノ大譜表。ベートーヴェン「月光」第1楽章 冒頭の音型
    （右手＝8分3連の分散和音、左手＝オクターブの全音符、嬰ハ短調・調号4♯）を8小節へ反復したもの。
    Issue #168 のコメント指定を受け、PR #177 が使ったベース譜面を8小節へ拡張した。
    **9小節の忠実な再現ではない**（記憶から復元した誤譜をリポジトリに残さないため。#168 と同じ判断）
  - `wind-band-score.json` — 編成プリセット `wind-band`（10パート）に検証用の音型を入れた総譜
- 測定は SVG の属性・`getComputedStyle`・`getBoundingClientRect` から行った

### 単位の換算（この文書で使う）

| 記号 | 意味 |
| --- | --- |
| **sp**（staff space） | 五線の線と線の間隔。浄書の世界の基準単位 |
| **u**（論理単位） | VexFlow の座標単位。このアプリでは **1 sp = 10 u** |
| **s**（実効描画スケール） | `SCORE_LAYOUT_RENDER_SCALE`(0.44) × 実効音符サイズ倍率。u → CSS px の倍率 |
| px → mm | 1 CSS px = 25.4/96 = **0.2646 mm**（印刷時は原寸なので画面の CSS px がそのまま紙の寸法になる） |

## 3. 現状値の棚卸し（実測）

### 3-1. 五線のサイズ（＝すべての比率の基準）

| 譜種 | 実効音符サイズ倍率 | s | 1 sp | 五線の高さ（4 sp） |
| --- | --- | --- | --- | --- |
| ピアノ・単旋律（既定 150%） | 1.50 | 0.660 | 6.60 px = **1.746 mm** | 26.4 px = **6.99 mm** |
| 吹奏楽10パート（実測） | 1.24（150% に自動縮小 fit が掛かった値） | 0.546 | 5.46 px = **1.444 mm** | 21.8 px = **5.78 mm** |
| 弦楽四重奏・編成譜（**設計上の**既定 100%） | 1.00 | 0.440 | 4.40 px = 1.164 mm | 17.6 px = 4.66 mm |

- ピアノ・単旋律の 1 sp = 1.746 mm は、MuseScore の既定値 1.75 mm（＝五線 7 mm）と実質一致する。
  **この2譜種のサイズは慣行どおり**と言ってよい
- 編成譜は「工場出荷既定 100%」のはずだが、**保存済みの譜面を開いたときは 150% が使われる**（§6-1 参照）

### 3-2. 線の太さ

太さの正本は **`App.css` の `.score-area svg path, .score-area svg line { stroke-width: var(--score-stroke-width, 1.2) }`**。
`--score-stroke-width` は表示ウェイト設定（細 0.8 / 標準 1.2 / 太 1.8、`ScorePage.tsx:4889`）で、印刷・印刷プレビューでは
0.8 に固定される。この一括指定が**要素ごとの太さ属性（符幹 1.5・加線 2 など）をすべて上書き**するため、
**線という線がすべて同じ太さ**になっているのが現状の最大の特徴である。

| 要素 | 実装値（標準ウェイト時） | sp 比 | Bravura の推奨 | 判定 |
| --- | --- | --- | --- | --- |
| 五線 | 1.2 u（CSS） | **0.120** | 0.130 | やや細い |
| 符幹 | 属性 1.5 u → CSS で 1.2 u | **0.120** | 0.120 | ✅ 一致 |
| 加線 | 属性 2 u → CSS で 1.2 u。色は **#444（黒でない）** | **0.120** | 0.160 | 細い・色も薄い |
| 加線の左右への張り出し | 片側 3.0 u | **0.300** | 0.400 | 短い |
| 小節線（細） | `rect` 幅 1 u（CSSの影響を受けない） | **0.100** | 0.160 | **細すぎ**（五線より細い＝主従が逆） |
| 終止線の細線＋太線 | 1 u ＋ 3 u（間隔 2 u） | **0.100 + 0.300**（間隔 0.200） | 0.160 + 0.500（間隔 0.400） | 太線が細く、締まらない |
| 連桁（ビーム） | 5 u（塗り） | **0.500** | 0.500 | ✅ 一致 |
| 松葉（クレッシェンド） | インライン 1.2 u（選択時 1.8） | **0.120** | 0.160 | 細い |
| ペダル線 | インライン 1.2 u（選択時 1.6） | **0.120** | 0.160 | 細い |
| リハーサルマークの枠 | `rect` stroke 1.4 u | **0.140** | 0.160（textEnclosure） | ほぼ一致 |
| グループ括弧 | path 属性 1 u → CSS で 1.2 u | **0.120** | 0.500（bracket）/ 0.160（subBracket） | **細すぎ** |
| 印刷時の全 path/line | 0.8 u | **0.080** | — | 画面よりさらに細い |

**要点**

1. 要素ごとの太さの**階層が存在しない**（五線・符幹・加線・括弧がすべて 0.12 sp）。浄書では
   「五線 < 小節線 ≦ 加線 < 連桁・太線」という階層があるのが普通で、この階層が版面の締まりを作る
2. 小節線が五線より細い（0.10 < 0.12）ため、**小節の区切りが視覚的に弱い**
3. 終止線の太線が 0.3 sp しかなく、曲の終わりの「締め」が弱い
4. 印刷では一律 0.08 sp まで細くなる。市販譜の濃度感に寄せる意図（`App.css` のコメント）だが、
   Bravura 推奨の 0.13 sp に対して 6 割の細さで、**階層が無いまま全体が薄くなる**

### 3-3. 縦の間隔

| 項目 | 実装値 | ピアノ譜（s=0.66） | 吹奏楽（s=0.546） |
| --- | --- | --- | --- |
| ページ | A4 210×297 mm、余白 上 14 / 下 12 / 左右 14 mm | 同左 | 同左 |
| タイトルブロック | `.page-head` min-height 18 mm ＋ 下余白 6 mm | 同左 | 同左 |
| パート間隔（五線上端どうし） | 4パート以下 80 u / 5パート以上 60 u | 52.8 px = **13.97 mm** | 32.7 px = **8.66 mm** |
| ↑のうち五線と五線の隙間 | 40 u / 20 u | 26.4 px = 6.99 mm（= 4 sp） | 10.9 px = 2.89 mm（= 2 sp） |
| 段の間隔（既定値） | ピアノ +30 px、その他 0 px | — | — |
| 実測: 1段の描画高 | — | 118.8 px = **31.4 mm** | 349.2 px = **92.4 mm** |
| 実測: 段と段の空き | — | 80.3 px = **21.2 mm**（4段/ページ） | 91.6 px = **24.2 mm**（2段/ページ） |
| 実測: ページ下部の余り | — | ほぼ無し | 約 **37 mm** |

- ピアノ大譜表の右手/左手の隙間 4 sp は、加線が多い曲では窮屈になりうる（月光の譜例でも左手の
  オクターブが加線2本ぶん下へ出ており、隙間の余裕は少ない）
- 吹奏楽は 2段/ページで段間 24 mm。**段の高さ（92 mm）に対して段間が広く、かつ下端に 37 mm の余りが残る**。
  この「間延び」は初見の印象で「スカスカした譜面」に見える要因になる

**ページの文字（HTML。CSS px 固定で、譜面サイズを変えても大きさは変わらない）**

| 対象 | 実装値 | 紙面での大きさ | 備考 |
| --- | --- | --- | --- |
| タイトル | 28 px / `h1` の既定 bold / letter-spacing 0.08em / Hiragino 等の sans | 7.41 mm ≈ **21 pt** | 印刷時は 24 px ≈ 18 pt |
| サブタイトル | 14 px / #555 | 3.70 mm ≈ 10.5 pt | 印刷時は 12 px |
| 作詞者・作曲者・編曲者 | 14 px / #555 / 右上に絶対配置（**インライン style で直書き**、`ScorePage.tsx:4874`） | 3.70 mm ≈ 10.5 pt | 幅が予約されておらず、長いタイトルと**重なる**（§6-2） |
| 2ページ目以降の見出し | 14 px / #444 | 3.70 mm | |
| ページ番号 | `.page-foot` / 既定サイズ | — | |

**要点**

1. **パート名・小節番号が小さすぎる**。ピアノで 5.4 pt、吹奏楽では 3.6 pt しかない。
   市販の総譜でパート名が本文文字より小さいことはまずなく、初見で最初に読む情報がこの大きさなのは不利
2. 強弱記号が **Times New Roman のイタリック文字**で描かれている。楽譜の強弱は音楽フォント側の
   専用グリフ（Bravura の `dynamicForte` 等）を使うのが標準で、書体が混ざって見える
3. 文字の書体が3系統（`system-ui` sans / `sans-serif` / Times New Roman）に分かれており、統一されていない。
   Bravura 自身は組み合わせるテキスト書体として **Academico / Century Schoolbook / Edwin / serif**（セリフ体）を
   推奨しているが、アプリはタイトル等に Hiragino のゴシック体を使っている
4. タイトルの大きさ（21 pt）と作者欄（10.5 pt）の比は妥当。ただし **letter-spacing 0.08em** は
   日本語のタイトルでは間延びして見え、かつ折り返しやすくなる

## 4. 慣行の参照値（出典つき）

### 4-1. 線の太さ — SMuFL / Bravura の engravingDefaults

このアプリは VexFlow 経由で **Bravura**（SMuFL 準拠の楽譜フォント）を使って記号を描いている。
Bravura のメタデータには、そのフォントで組むときの推奨太さ（`engravingDefaults`、単位は staff space）が
定義されており、**アプリはこれを一切参照していない**。

| キー | Bravura の値 |
| --- | --- |
| `staffLineThickness` | 0.13 |
| `stemThickness` | 0.12 |
| `legerLineThickness` / `legerLineExtension` | 0.16 / 0.40 |
| `thinBarlineThickness` | 0.16 |
| `thickBarlineThickness` | 0.50 |
| `barlineSeparation` / `thinThickBarlineSeparation` | 0.40 / 0.40 |
| `beamThickness` / `beamSpacing` | 0.50 / 0.25 |
| `hairpinThickness` | 0.16 |
| `slurEndpointThickness` / `slurMidpointThickness` | 0.10 / 0.22 |
| `tieEndpointThickness` / `tieMidpointThickness` | 0.10 / 0.22 |
| `bracketThickness` / `subBracketThickness` | 0.50 / 0.16 |
| `tupletBracketThickness` / `textEnclosureThickness` | 0.16 / 0.16 |
| `octaveLineThickness` / `pedalLineThickness` / `repeatEndingLineThickness` | 0.16 / 0.16 / 0.16 |
| `textFontFamily` | `["Academico", "Century Schoolbook", "Edwin", "serif"]` |

- 出典: Bravura 1.481 の `Bravura.json`（<https://github.com/steinbergmedia/bravura> の `redist/Bravura.json`）の
  `engravingDefaults`。2026-08-08 に取得
- 各キーの意味の定義: SMuFL 仕様「Engraving defaults」
  <https://w3c-cg.github.io/smufl/latest/specification/engravingdefaults.html>

### 4-2. 五線のサイズ

- 五線の大きさは「ラストラル（rastral）＝五線の最下線から最上線までの高さ」で表す
  （Steinberg Dorico 用語集 <https://archive.steinberg.help/dorico/v1/en/dorico/topics/glossary/rastral_size_g.html>）
- MuseScore の既定は **1 sp = 1.75 mm、五線 7 mm**。ドキュメントは「独奏曲・合唱曲・小編成のスコア・
  パート譜のほとんどに適した高さ」としている
  （<https://handbook.musescore.org/formatting/score-size-and-spacing>、
  <https://musescore.org/en/handbook/4/score-size-and-spacing>）
- 大編成の総譜はこれより小さい五線を使うのが通例だが、**「何 mm が適切か」を明記した一次情報は
  今回見つけられなかった**。段2で値を決めるときは、運用者が手元に持っている市販の吹奏楽譜を
  実測して比べるのが確実（本文書の吹奏楽の実測値 5.78 mm と直接比較できる）

### 4-3. 文字の階層

数値の一次情報は今回確保できなかった。確実に言えるのは次の2点にとどめる。

- Bravura のメタデータが推奨するテキスト書体は**セリフ体**（§4-1 の `textFontFamily`）
- 強弱記号は SMuFL に専用グリフ（`dynamicPiano` 〜 `dynamicFF` 等）が定義されており、
  テキスト書体のイタリックで代用するのは標準的ではない

## 6. 調査中に見つかった、値の選定より先に決着が要る問題

いずれも**本Issueのスコープ外**（コードを触っていない）。段2の前に別Issueで扱うのが自然。

### 6-1. 保存済みの譜面を開くと、譜種別の既定サイズ（Issue #49）が効かない

- 症状: 吹奏楽（編成譜）の譜面を読み込むと「音符の大きさ」が **150%**（＝単旋律・ピアノ用の既定）になる。
  UI にも「音符の大きさ 150%（紙面に収めるため実際は124%で表示）」と表示される
- 原因: `resolveDefaultLayoutForScoreType()` の適用は「ユーザーが UI で譜種・編成を切り替えたとき」だけ
  （`ScorePage.tsx:813` / `:848`）。`notationSizeMultiplier` の初期値は**初回マウント時の scoreType**で決まる
  （`ScorePage.tsx:2610`）ため、後から保存データを読み込んで scoreType が ensemble になっても再評価されない
- 影響: 編成譜の見た目が「100% の既定」ではなく「150% ＋ 自動縮小 fit」で決まる。本文書 §3-1 の
  吹奏楽の実測値（1 sp = 1.444 mm）はこの状態のもの。**段2で編成譜の既定サイズを決めるなら、先にこの
  経路を直さないと「決めた値が使われない」**

### 6-2. 長いタイトルが作者欄と重なる

- 症状: タイトルが折り返す長さになると、右上に絶対配置された作詞者・作曲者・編曲者の行と重なる
  （本文書の譜例2件とも再現）
- 原因: `.score-title` は中央寄せの通常フロー、作者欄は `position: absolute; top:0; right:0` で幅の予約が無い
  （`ScorePage.tsx:4874`）

#### 修正（Issue #204, 2026-08-09）

タイトル欄を **3列グリッド**にして、タイトルと作者欄が同じレイアウトフローで場所を取り合う形にした。
絶対配置をやめたので「幅を予約していない」という原因そのものが消える。

```
[左の見えない控え][タイトル・サブタイトル][作詞者・作曲者・編曲者]
     auto            minmax(0, 1fr)                auto
```

- **左端の「控え」が要る理由**: 右にだけ場所を空けると、タイトルは残りの領域の中央＝紙面の中央より
  左にずれてしまう。左右に同じ幅の列を置くと、タイトルは「作者欄の幅を避けつつ紙面の中央」に留まる。
  控えは作者欄と同じ内容・同じ指定の複製（`.score-credit.score-credit-spacer`）なので、
  作者名を書き換えても幅が自動でそろう
- **`visibility: hidden` を使う理由**: `display: none` にすると幅が 0 になり中央がずれる。
  `visibility: hidden` は場所を取ったまま描画だけ消すので、画面にも印刷にも出ない。
  読み上げの重複を避けるため `aria-hidden="true"` も付けている
- **作者欄に `max-width: 40mm`**: 作者名が長いと左右で 2 倍の幅を取られてタイトルが極端に細くなるため、
  紙幅（182mm）の約 2 割を上限にした。超えたぶんは作者欄側が折り返す
- **作者欄が3つとも空のとき**は `.score-head-grid--empty-credit`（`column-gap: 0`）を付け、
  タイトルへ紙面の全幅を返す
- あわせて `.page-head` の `position: relative` をインライン style から `App.css` へ移した
  （#202 と同じく、見た目の指定の置き場を1つにするため）

#### 再設計（Issue #216, 2026-08-11）: 横並びをやめて縦積みへ — 前提ごと解消した

上の #204 は「タイトルと作者を**同じ行に置く**」という前提の上での対症だった。重なりは消えたが、
副作用として**タイトルが使える幅が作者欄のぶんだけ狭くなる**（実測 685.88px → 353.29px）。
その結果、市販譜なら1行で収まるタイトルが2〜3行に折り返す。運用者から
「そもそも重ならない配置では」と月光の市販譜例が示され、慣例どおりの**縦積み**へ作り直した。

```
[    タイトル（中央・行を専有）    ]
[   サブタイトル（中央）   ]
[            作詞者 / 作曲者 / 編曲者（右寄せ・縦に並ぶ）]
```

- **なぜ重ならなくなるか**: タイトルと作者欄が同じ行に無いので、
  タイトルが何行に折り返しても作者欄の領域へ侵入しない。#204 の「左の見えない控え」
  （`.score-credit-spacer`）も、タイトルを中央に保つための細工だったので不要になった
  （タイトルは版面の全幅を使うため、`text-align: center` だけで版面中央に来る）
- **`max-width: 40mm` を外した**: あれは「作者名が長いとタイトルの幅が潰れる」ための上限だった。
  縦積みでは作者欄が自分の行を丸ごと使えるので、誰の幅も奪わない。長い作者名も折り返さない
- **空の作者欄は行ごと描かない**（`ScorePage.tsx`）: 中身が空でも `contentEditable` の div は
  ブラウザが1行ぶん（実測 15px）の高さを確保するため、置いたままだと「作曲者だけの譜面」で
  上下に空行ができ、市販譜の配置からずれる。3つとも空なら `.score-credit` 自体を描かない
- **タイトル余白（上/下）スライダーの意味は不変**: 効かせている先は `.page-head--title` の
  `padding-top` / `margin-bottom` で、見出しブロック全体の上下余白という位置づけのまま
- **2ページ目以降・印刷・印刷プレビュー**: 見出しの構造は1か所（`ScorePage.tsx` の `.page-head`）
  にしかなく、`@media print` / `.print-preview` は文字サイズしか上書きしていないため自動で追従する。
  2ページ目以降は従来どおりタイトルのみ（`.page-title`）で、作者欄は市販譜と同じく載せない

### 6-3. 強弱記号などのクリック判定枠が「黒い枠」として見え、印刷では黒く塗り潰される

- 症状（画面）: 強弱記号の周りに黒い長方形の枠が出る
- 原因: `PianoSystemCanvas.tsx:1587` が作る `rect.symbol-hit-region` に `stroke: none` が指定されていない。
  VexFlow が SVG ルートへ `stroke="black"` を付けるため、透明な当たり判定のはずが枠線として描かれる
  （`.vf-hit` / `.vf-note-hit` は `App.css` で `stroke: none !important` を当てているが、このクラスは対象外）
- 症状（印刷・印刷プレビュー）: さらに深刻で、`App.css` の
  `.print-page svg rect:not([fill="none"]):not(.vf-hit):not(.vf-note-hit)…` が `fill` を印刷インク色にするため、
  **枠の中が黒く塗り潰される**。`.print-preview` クラスを付けた状態で `getComputedStyle` が
  `fill: rgb(0,0,0)` を返すことを確認済み
- 影響: 強弱記号を入れた譜面を印刷すると記号が黒い箱になる可能性が高い。**浄書品質以前の不具合**

#### 修正（Issue #203, 2026-08-09）

対処は既存の当たり判定（`.vf-hit` / `.vf-note-hit` / `.vf-hit-voice2`）と同じ **`App.css` 側**へそろえた。
当たり判定を透明にする方法を「CSS」と「rect 生成時の属性」の2系統に分けないための判断
（トリアージコメントの指示）。変更は3か所。

1. **画面**: `.symbol-hit-region { stroke: none !important; }` を追加。
   `fill` はここで固定していない。マウスを乗せたときの薄い青（`rgba(37,99,235,0.16)`）を
   `appendSymbolHitRegion` が **fill 属性の付け替え**で出しているため、CSS で `!important` を当てると
   ホバーの手応えが消えるからである（`.vf-note-hit` が `fill: transparent !important` を持てるのは、
   あちらが色を出さない当たり判定だからで、事情が違う）。`pointer-events` も
   `symbolsClickable` に応じて inline style で出し入れされるので CSS では触らない
2. **印刷（`@media print`）**: インク色を強制する rect のルール2本へ `:not(.symbol-hit-region)` を追加し、
   透明へ戻すルール（`rect.vf-hit, …`）の並びに `rect.symbol-hit-region` を加えた。
   当たり判定の `fill` は `rgba(37,99,235,0)`（アルファ 0 の透明色）であって `none` ではないため、
   既存の `:not([fill="none"])` では除外できていなかったのが塗り潰しの原因
3. **印刷プレビュー（`.print-preview`）**: 上と同じ内容（`@media print` の複製定義なので同時に直す必要がある）

回帰テストは `src/AppCssSymbolHitRegionPrint.test.ts`。jsdom は外部 CSS を読まないため、
App.css を文字列として読み「透明化のルールが消えていないこと」「インク色ルールが当たり判定を除外していること」
「生成側のクラス名 `symbol-hit-region` が変わっていないこと」を静的に見張る。

**影響範囲**: 変更したセレクタはすべて `.symbol-hit-region` を対象に加除しただけで、
`.vf-hit`（小節選択のハイライト。REGRESSION.md G節）・`.vf-note-hit`・`.vf-note-selected` の
扱いは1文字も変えていない。ブラウザ実測では、修正後もクリックで位置調整エディタが開き、
ホバーの薄い青（`fill: rgba(37,99,235,0.16)`）も従来どおり出る。

### 比較画像の作り方（2026-08-08 追記）

画面キャプチャを撮るのではなく、**描画中の DOM から単体で完結する SVG を組み立てて PNG 化**している。
そうした理由と手順は次のとおり。

- **なぜ SVG をそのまま取り出すだけでは駄目か**: 線の太さ・書体の多くは `App.css` の CSS 側で
  決まっており（§3-2 の `stroke-width: 1.2` の一括指定など）、`<svg>` を切り出しただけでは
  それらが失われて実際と違う見た目になる。そこで**計算後スタイル**（`getComputedStyle`）を
  要素1つずつ属性へ焼き込む。`ab-preview.js` の候補値も CSS 経由で当たるため、この方法なら
  A/B の切り替え結果がそのまま画像に反映される
- **なぜフォントを埋め込むのか**: 音楽記号は Bravura の `<text>` として描かれており、
  単体 SVG では実行時に読み込まれた webfont が効かない。アプリ自身が使うのと同じ
  jsDelivr の `@vexflow-fonts` から woff2 を取得し、base64 で `@font-face` に埋め込む
- **なぜ同じ切り出しになるか**: 組み立てる SVG は「ページ座標系（A4 = 794×1123 CSS px）」で統一してあり、
  切り出しは root の `viewBox` を差し替えるだけ。3案で同じ矩形・同じ倍率になることが構造的に保証される
  （トリアージの「同じ箇所を同じ倍率で切り出す」への対応）
- **タイトル等の HTML 側の文字**は `<text>` へ写している。折り返し位置は実画面と同じだが、
  ベースラインはフォントサイズの 0.8 倍で近似しているため、1px 程度の縦ずれはありうる

画像には**現状の不具合もそのまま写っている**（§6-2 のタイトルと作者欄の重なり、
§6-3 の強弱記号の黒い判定枠、§6-4 の2段目のパート名なし）。既定値の選定とは別問題なので、
案を選ぶときは無視してよい。

## 11. 実装で判断したこと（トリアージ表の解釈と、あえて変えなかったもの）

### 11-1. 一律 `stroke-width: 1.2` は「フォールバック」として残した

§5 の指摘どおり、`.score-area svg path, .score-area svg line` の一律指定が要素ごとの
太さを潰していた。これを**対象ごとの個別指定へ分解**したが、**一律指定自体は残してある**。

理由は「A/B 比較で承認された見た目に合わせる」ため。`ab-preview.js` は一律指定の**上に**
`!important` で候補値をかぶせる作りなので、比較画像では一律指定が生きたままだった。
いま一律指定を撤去すると、スラー・タイの弧（1.6〜2.2 u）、終止括弧、連符の括弧、
ペダル線、オッターバ線などが**いっせいに元の属性値へ戻る**。これらは比較画像に写っておらず、
選定者が見て選んだ状態でもないため、この段では触らない。

**残っている作業（段3以降の候補）**: 上に挙げた要素を個別指定へ移し、一律指定を撤去する。
移すときは Bravura の `slurEndpointThickness` 0.10 / `slurMidpointThickness` 0.22、
`tupletBracketThickness` 0.16、`pedalLineThickness` 0.16、`octaveLineThickness` 0.16、
`repeatEndingLineThickness` 0.16 が参照値になる。

なお、一律指定を残したことで**符幹には明示指定が必要**になった。符幹の SVG 属性は 1.5 u で、
一律指定を上書きしないと 0.12 sp（=1.2 u・据え置きのはず）から太ってしまうため、
`g.vf-stem > path` に 1.2 u を明示している。

### 11-2. 表示ウェイト設定（細/標準/太）は「倍率」として生かした

§8 の未決定事項3。個別指定にしたので、太さを固定値で書くと 細/標準/太 の設定と
印刷時の細線化（0.8）が効かなくなる。そこで `.score-area` に

```css
--score-stroke-scale: calc(var(--score-stroke-width, 1.2) / 1.2);
```

を定義し、個別指定を `calc(1.3px * var(--score-stroke-scale))` の形で書いた。
**標準（1.2）のとき倍率 1.0 = 候補Aの値そのまま**になり、細 0.667 倍 / 太 1.5 倍 /
印刷 0.667 倍が比例して効く。実測: 細 0.867px / 標準 1.3px / 太 1.95px。

ただし**小節線（rect）はこの倍率の対象外**で、常に 0.16 sp のまま。
rect の幅は CSS で変えられず、変更前も一律指定の影響を受けていなかった（常に 1.0 u だった）ため、
「変更前と同じく、ウェイト設定に連動しない」という挙動を保っている。

### 11-3. トリアージ表の「ブラケット 0.12 → 0.16」は**サブ括弧**に適用した

調査の結果、総譜左端の**太いメイン括弧**は VexFlow の `StaveConnector`（BRACKET）が
**幅 3 u の塗り矩形（= 0.30 sp）** で描いていることが分かった。§3-2 の表で
「グループ括弧 0.12 sp」と記録していたのは `PianoSystemCanvas.tsx` が SVG で直接描く
**サブ括弧**（Vln.I / Vln.II をまとめる細い括弧）のほうで、現状 0.12 sp はこれと一致する。

したがって 0.16 はサブ括弧へ適用した。Bravura の `subBracketThickness` も 0.16 で整合する。
メイン括弧を 0.16 にすると **0.30 → 0.16 と細くなり**、「総譜の楽器グループが読み取りにくい」
（§5 の乖離5）を悪化させるため、意図に反する。

**未決定として残す**: メイン括弧を Bravura 推奨の `bracketThickness` 0.50 sp へ太らせるか
（現状 0.30 sp）。太らせる場合は VexFlow の rect 幅を書き換える実装になる。

### 11-4. cresc./dim.・テンポ表記も強弱記号と同じ倍率で拡大した

トリアージ表が名前を挙げているのは「強弱記号 1.6 → 2.0」だけだが、
`ab-preview.js` の `classifyText()` は **Times New Roman のイタリック全部**を `dynamics` と
判定して 1.25 倍していた。つまり比較画像では cresc./dim.（1.2 sp）とテンポ表記（1.2 sp）も
1.5 sp に拡大された状態で、選定者はそれを見て候補Aを選んでいる。

受入条件1が「`engravingAB('a')` を当てた表示と同等」であることを優先し、
同じ 1.25 倍を適用して 1.5 sp にした（`ENGRAVING_TEXT_SP.expressiveText`）。
強弱記号より一段小さい文字という関係も保たれる。

### 11-5. 書体は「CSS で SVG の text 全部」ではなく描画側で指定した

`ab-preview.js` は `.score-area svg text { font-family: <セリフ体> }` を当て、
音楽記号は `g[class^="vf-"] text` で Bravura に戻していた。**この作りが、トリアージが警告した
「ブラケットの枠状のアーティファクト」の正体だった**（§11-6）。

そのため本実装では CSS で一括指定せず、**アプリが自分で描く `<text>` にだけ**
`SCORE_TEXT_FONT_FAMILY` を渡している（パート名・小節番号・歌詞・強弱・cresc./dim.・
テンポ表記・♩=BPM・リハーサルマーク・運指・ペダル・オッターバ）。
VexFlow が描く文字には一切触らない。

ページ側の文字（タイトル・サブタイトル・作者欄）は HTML なので、
`.print-page` に `--score-text-font` を1回だけ定義して継承させている
（タイトル欄 `.page-head` と `.score-area` の共通の先祖がこの要素）。

## 12. トリアージが警告した「ブラケットのアーティファクト」の原因と結論

トリアージの既知の注意:

> A/B ライブ確認時に**ブラケットの stroke 描画に副作用（枠状のアーティファクト）**が出た。

**原因を特定した。アプリ側の不具合ではなく、A/B スニペット固有の副作用が2つ重なったもの。**

1. **括弧の上下端グリフが豆腐（□）になる**
   `StaveConnector` は BRACKET の上下端を Bravura のグリフ **U+E003 / U+E004**
   （SMuFL の `bracketTop` / `bracketBottom`）を `<text>` で描く。
   この2つは `g.vf-*` の**外**（SVG 直下）に出るため、`ab-preview.js` の
   `g[class^="vf-"] text` による Bravura 復帰が効かない。結果セリフ体で描かれ、
   セリフ体に U+E003 のグリフは無いので**空の四角（豆腐）**になる。
   実測: 実装では字幅 19px（正しい Bravura グリフ）、`engravingAB('a')` 適用時は 40px（豆腐）。
2. **メイン括弧の縦棒が細くなり左へずれる**
   `applyAttributes()` の rect 書き換えは「幅 3 以下」を対象にするため、
   幅 3 のメイン括弧まで 1.6 へ縮め、x も 0.7 左へずらしていた。

証拠画像:

- `docs/qa/engraving-defaults/images/preview-a-bracket-artifact.png`
  — main + `engravingAB('a')`。括弧の上下に**空の四角**が出て、縦棒が細い（=警告された症状）
- `docs/qa/engraving-defaults/images/adopted-a-bracket.png`
  — 本実装。Bravura の括弧の上下端が正しく描かれ、縦棒の太さは変更前のまま

**結論: 本実装ではアーティファクトは発生しない**（§11-5 のとおり CSS で書体を一括指定せず、
§11-3 のとおりメイン括弧の rect を触らないため）。受入条件4は満たしている。

# 段3: 画面表示の線に下限（フロア）を設ける（Issue #210・2026-08-09）

## 15. 問題 — 縮小表示で五線がサブピクセルに落ちる

運用者の実機報告（2026-08-09、本番・室内オーケストラ・50%縮小表示）:「細すぎやて」。

§10 で採用した候補Aの太さは**五線間隔に対する比率**（五線 0.13 sp = 1.3 u）なので、
譜面を縮小すると線も同じ割合で細くなる。編成譜は1段が高く、紙に収めるための
自動縮小（`ensembleAutoFitMultiplier` と `useAutoPageScale` の `--scale`）が強く掛かるため、
モニタ上の実効太さが1デバイスピクセルを割り、線がかすれて見えなくなっていた。

### 15-1. 実測（修正前・main a3842e1 / 1440×900・dpr 2・localStorage 空）

「実効倍率」= SVG論理単位1つが画面上の何 CSS px になるか
（= VexFlow の描画倍率 `SCORE_LAYOUT_RENDER_SCALE × 音符の大きさ実効倍率` ×
ページの `transform: scale()`）。要素の `getScreenCTM().a` で実測した。

| 譜種・表示 | 実効倍率 | 五線（CSS px） | 五線（デバイスpx） | 小節線 | 終止線の太線 |
| --- | --- | --- | --- | --- | --- |
| 単旋律・ズーム100% | 0.660 | 0.858 | 1.72 | 1.056 | 1.980 |
| ピアノ・ズーム100% | 0.660 | 0.858 | 1.72 | 1.056 | 1.980 |
| 室内オーケストラ・ズーム100% | 0.440 | 0.572 | 1.14 | 0.704 | 1.320 |
| **室内オーケストラ・ズーム50%** | **0.220** | **0.286** | **0.57** | **0.352** | **0.660** |

トリアージの仮説（「実効 0.65px 程度まで落ちているのでは」）は方向として正しく、
実際にはさらに細い **0.57 デバイスピクセル**だった（＝1つの画素を塗り切れない）。
なお、ウィンドウ幅によっては自動縮尺（`useAutoPageScale`）がさらに掛かる。
1440×900 でツールバーを開いたまま同じ操作をした別の実測では実効倍率 0.191・
五線 0.50 デバイスピクセルとさらに細くなっており、狭い画面ほど症状は重くなる。

## 16. 修正設計

### 16-1. 「線種ごとの下限」ではなく「全線に同じ倍率」で表す

トリアージの指示は「五線 1px を下限とし、他の線種は候補Aの相対比を保った下限にする」。
全線が同じ実効倍率で縮むので、**五線が下限を割った比率をそのまま全線へ掛ける**1つの倍率で
これを表現できる（線種ごとに個別に丸めると、下限のところで太さの階層が潰れる）。

```
フロア倍率 = 下限 / (五線の太さ × 表示ウェイト倍率 × 実効倍率)   ← 1 を下回らない
```

正本は `src/utils/engravingDefaults.ts` の `computeScreenStrokeFloorMultiplier()`。
ScorePage が結果を CSS カスタムプロパティ `--score-stroke-floor` として `.score-area` へ注入し、
App.css 側の各指定はそれを掛けるだけにしてある。**発動しないときは 1** なので、
その場合の計算結果は候補Aの値と完全に一致する（＝見た目が1pxも変わらない）。

表示ウェイト（細い/普通/太い）は**適用したあとの実効値**で判定する
（「細い」を選んだ意図は残しつつ、読めない細さだけを防ぐ、というトリアージの指示による）。

### 16-2. 下限は「1 CSS px」ではなく「1 デバイスピクセル」にした

トリアージの文言は「五線 1px（デバイスピクセルでかすれない最小値）」。
この2つの読み方で結果が変わるため、**受入条件2を満たすほう**を採った。

| 下限の解釈 | 単旋律・ピアノ 100%（実測 0.858 CSS px = 1.72 デバイスpx） | 受入条件2 |
| --- | --- | --- |
| 1 CSS px | **発動する**（0.858 → 1.000、+17%） | ✗ 満たせない |
| 1 デバイスピクセル（Retina で 0.5 CSS px） | 発動しない | ✓ |

かすれの原因は「1つのデバイスピクセルを塗り切れないこと」なので、下限もデバイスピクセルで
決めるのが筋が通る。運用者は #195 のコメントで「単旋律譜・ズーム100%は現状で良い」と
判定済みであり、その見た目を17%太らせるのは退行にあたる、という判断も含む。

**申し送り**: dpr=1 の外部モニタでは 1 デバイスピクセル = 1 CSS px なので、単旋律・ピアノの
100%表示でもフロアが発動する（0.858 → 1.0）。これは「そのモニタでは実際にサブピクセルなので
太らせる」という意図どおりの動作だが、受入条件2の「1pxも変わらない」は
**dpr≥2 の画面での話**になる。もし「1 CSS px を下限にしたい（＝どの譜種でも一律に太くしたい）」なら、
`MIN_STAFF_LINE_DEVICE_PX` を 2 にする1か所の変更で切り替えられる。

### 16-3. 上限（頭打ち）を設けた

下限まで戻す倍率は縮小率に反比例するため、極端な縮小（大編成をズーム50%で見る等）では
五線5本が1本の黒帯に潰れる。そこで **「五線がこの譜面でいちばん太い線（終止線の太線・
メイン括弧 = 0.30 sp）より太くはならない」** ところで頭打ちにした
（`MAX_SCREEN_STROKE_FLOOR_MULTIPLIER` = 0.30 / 0.13 ≈ 2.31）。
かすれ対策としては弱くなるが、黒く塗り潰れる壊れ方はしない。

### 16-4. 塗り矩形の縦線（小節線）は CSS のジオメトリプロパティで太らせた

VexFlow は小節線・段の左右の縦線・メイン括弧を `fillRect()` の**塗り矩形**で描くため、
`stroke-width` が効かない（§11-1・`widenThinBarlineRect` を用意した理由）。
ここにフロアを掛ける方法として2案を比べた。

| 案 | 内容 | 判断 |
| --- | --- | --- |
| A: 描画時に width 属性へ焼き込む | `widenThinBarlineRect` に倍率を渡す | **不採用**。①ズーム変更のたびに譜面を描き直す必要がある（今はCSSの拡大縮小だけで済んでいる） ②焼き込んだ値が**そのまま印刷に持ち込まれる**（属性は `@media print` で戻せない） |
| B: CSS の `width` ジオメトリプロパティで上書き | 描画時はクラスを付けるだけ | **採用**。印刷は `--score-stroke-floor: 1 !important` を当てるだけで従来どおりに戻り、ズーム追従も再描画なしで効く |

案Bの実装:

```css
.score-area svg rect.vf-engraving-thin-line {
  width: calc(1.6px * var(--score-stroke-floor, 1));
  transform: translateX(calc(-0.8px * (var(--score-stroke-floor, 1) - 1)));
}
```

- 広がったぶんの半分だけ `translateX` で左へ戻し、線の中心を保つ（`widenThinBarlineRect` と同じ考え方）
- フロアが 1 のときは `width` が属性値と同じ 1.6px、`translateX` が 0 になり**完全に同一の描画**になる
- 万一ジオメトリプロパティ非対応のブラウザでも、属性の 1.6 / 3 が残るので #202 時点の見た目に戻るだけ
  （Chrome / Safari / Firefox はいずれも対応済み。Chromium で `width` の上書きが効くことは実測で確認した）

**終止線の太線・メイン括弧（幅 3 u）にも同じ倍率を掛けている。**
対象から外すと、細線だけが太って「終止線の太線が通常の小節線より細い」という主従の逆転が起きるため
（実測: フロア 2.01 のとき 細線 0.615px に対し太線は 0.573px のまま）。太さの比 3 : 1.6 は変えていない。

### 16-5. 印刷・PDF書出には掛けない

- **実印刷**（`@media print`）: `.print-page .score-area` へ `--score-stroke-floor: 1 !important`。
  ScorePage がインライン style で書いているため、打ち消すには `!important` が要る
  （`!important` 付きの宣言はインライン style より強い、というカスケードの規則を利用）
- **印刷プレビュー**: ScorePage 側で `isPrintPreview` のとき 1 を渡す（紙の見た目を確認するための表示なので）
- PDF書出は `window.print()` なので実印刷と同じ経路（§pdf-export の設計どおり）
