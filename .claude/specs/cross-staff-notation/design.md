# 段またぎ記譜（cross-staff）段1: 表示だけ隣の五線に載せる（Issue #259）

作成: 2026-08-17（レビュアー起案・運用者承認待ち）
状態: **設計メモ（段0）— 承認後に段1を ai-ready 化する**

## 1. 目的と背景

月光第1楽章5小節目の冒頭のように、ピアノ譜には「右手の声部の音を、加線を避けるため
下の五線（ヘ音記号）に描く」慣習がある（cross-staff）。現状は手段が無く、
運用者は加線5〜6本の超低音として書くか、左手パートの声部2として入力するかしかない。
どちらも「音楽的な所属（右手の声部）」と「見た目の置き場所」が食い違う。

**段1のゴール: 「どの声部の音か」は一切変えず、「どの五線に描くか」だけを
音符単位で切り替えられるようにする。** リズム・再生・声部の整合・弧や記号の所属は
すべて元のまま。段2（段またぎ連桁の浄書品質）はスコープ外（§8）。

## 2. なぜ今の構造なら安く入るか（実装可能性の根拠）

`PianoSystemCanvas` は1システム（=1 SVG）に**全パートの五線を描き、
全パート・全声部の Voice を1回の Formatter で合同整形している**（Pass 2、
`PianoSystemCanvas.tsx:3738` 付近）。つまり:

- 右手の音符と左手の五線は**最初から同じ座標系・同じ整形結果**の中にいる
- 「隣の五線に載せる」は、その音符の **(a) 音高→線の換算に使う clef** と
  **(b) `setStave` する対象** を隣のパートの物に差し替えるだけで成立する
- x 座標（拍の位置）は合同整形が保証するので、またいでも縦に揃う

既存の同型テクニックもある: Pass 1 の `voice.setStave(stave)` は「VexFlow は
**stave 未設定の音符にだけ** stave を伝播する」仕様を使って、合同整形時の
最上段上書きを防いでいる（`:3693-3698` のコメント）。段またぎ音符は
**音符単位で先に対象五線を `setStave`** しておけば、同じ仕組みで保護される。

## 3. データモデル

```ts
// NoteEvent に追加（音符単位・省略時は自分の五線）
renderStaff?: 'below' | 'above';
```

- **音符単位**で持つ（グループ単位にしない）。月光5小節目は三連符の途中で
  五線が変わるため、グループ一括では表現できない
- 省略時 = 従来どおり自分のパートの五線。**戻すときはプロパティごと削除**
  （#294 hideNumber と同じ。保存データが旧形式と同一に戻る）
- `'below'` = 自分の1つ下のパートの五線、`'above'` = 1つ上。ピアノ（2段）では
  右手→below / 左手→above だけが有効。**端のパートで無効な向き**
  （右手の above 等）と**単段の編成**では、保存はするが描画は self に
  フォールバックする（データを壊さない・エラーにしない）
- `storage.ts` の読込検証に型チェック（'below' | 'above' | undefined）を追加
- 休符にも許す（またぎ区間の中の休符を同じ五線に置きたいことがあるため）。
  ただし UI の初期対象は音符のみでよい（休符対応は実装が同じなら含めてよい）

## 4. 描画設計（触る場所の列挙）

### 4-1. 音符の生成と五線の割り当て

- `buildStaveNote` 相当（`:827-836`）で、`renderStaff` が有効な音符は
  **対象パートの clef** で `new StaveNote({clef, keys, ...})` を作る
  （line の計算が対象五線基準になる）。臨時記号・調号適用は既存の
  自パートの状態機械のまま（所属は変わらないため）
- Pass 1 の Voice 構築後、対象音符だけ `note.setStave(対象パートの stave)` を
  **preFormat より前に**行う（§2 の保護規則に乗せる）
- 符幹の向きは明示指定しない（VexFlow の自動判定に任せる。下の五線に載った
  高い音は自然に上向き＝浄書慣習どおり手元の五線側へ伸びる）。
  多声部小節の「声部1=上固定」（#192）はまたぎ音符には**適用しない**
  （下の五線上で上向き固定は成立するので実際には同じ結果になるが、
  判定は「実際に載る五線」基準で素直にしておく）

### 4-2. ビーム（連桁）は、またぎ位置で切る

- ビームのグループ化（`createBeams` 系）で、隣接音符の**実効五線**
  （renderStaff 解決後）が異なる位置をグループ境界にする
- 連符（tuplet）はグループとして維持する（拍計算のため Tuplet オブジェクトは
  従来どおり作る）。またぎで括弧・数字の描画が崩れる場合は、
  **またぎを含むグループは #294 の hideNumber と同じ「draw しない」経路**へ
  落としてよい（市販譜の月光がまさに数字なし。自動で消すか・#294 のトグルに
  任せるかは実装時に見た目で判断し、設計書へ追記すること）

### 4-3. 実効五線に追従させる既存機構（座標の取り所を1本化する）

以下は現在「パートの stave」を直接参照している。**「その音符が実際に載った
五線」= `note.getStave()`（または実効五線の解決関数）から取るよう変える**:

- 当たり判定 rect（`createNoteHitRect` の y 範囲・`data-line0-y` / `data-line-spacing`）
- 選択枠・個別音選択の line 換算（`resolveSelectableKeyIndexAt` の stave / k2l）
- 弧の端点（`drawTieArcP` の `fromStave/toStave` — `:3382`）と障害物収集
- 非アクティブ声部の選択判定（#306 の `.vf-inactive-voice-note-hit`）

**実装指針: 「イベント→実効五線」の解決を1つの関数
`resolveRenderStave(partIndex, event)` に集約し、上記全部がそれを呼ぶ。**
散らばった参照を1本化するのは #297（判定式）・#288（制御点）と同じ型で、
段2（またぎ連桁）に進むときの土台にもなる。

### 4-4. 変えないもの

- **再生**: keys から音高を取るため無変更（renderStaff は読まない）
- **保存・Undo**: 純粋なプロパティ変更1回（既存の setScore 経路）
- **MusicXML 書出**: 段1では変更しない。cross-staff は MusicXML では
  `<staff>` 要素で表現できるが、書出対応は後続 Issue に分ける
  （**既知の制限として README に明記**: 書き出すと同一五線に戻る）
- **パート譜表示**: パート単位の表示では renderStaff は無効（相手の五線が
  存在しない）。self へフォールバック

## 5. UI

> **後の変更**: この置き場所は Issue #317 で「音符・休符」タブへ移した（§15 参照）。以下の記述は導入時点のもの。

- パレット（演奏記号タブの記号調整系）に**モードボタン「段またぎ表示」**を追加。
  #294 の連符数字トグルと同じ「モードを選ぶ→音符をクリック」でトグル
  （右手の音符なら self↔below、左手なら self↔above）
- ピアノ譜（2段）以外の編成ではボタンを無効化（グレーアウト+理由のツールチップ）
- 対象音符が「またぎ表示中」であることは、描画位置そのもので分かるため
  追加の視覚マークは付けない（#264 の巡回・#306 の選択がそのまま効く）

## 6. 不変条件（受入の骨格）

1. `renderStaff` を1つも使っていない譜面は**1pxも変わらない**
   （#303/#307 と同じ「弧・音符のパス/座標の実測固定」方式で証明）
2. 再生スケジュールは renderStaff の有無で不変（moonlightRegressionPlayback 方式）
3. 月光5小節目の形（右手三連符の頭2音を below）で:
   - 音符が下の五線に、加線なしで描かれる
   - x 座標が左手の同拍と揃う（合同整形の保証をテストで固定）
   - クリック選択・巡回・弧の端点が描画位置に追従する
4. 保存→読込の往復で renderStaff が保持される。戻すとプロパティが消える
5. 無効な向き・単段編成・パート譜では self にフォールバックし、例外を出さない

段1a（データ+描画）で実際に入れたもの、設計時の想定と変えた点、判断の理由を残す。

### 10-1. 入れたもの

| 場所 | 内容 |

| `src/utils/crossStaffUtils.ts`（新規） | 「イベント→実際に載せるパート番号」を決める純関数群。`resolveRenderPartIndex` / `resolveRenderPartIndexes` / `hasCrossStaffRender` / `groupIndexesByRenderTarget` / `isRenderStaffDirection` |
| `src/utils/storage.ts` | 読込検証に `renderStaff` の型チェック（`'below' \| 'above' \| undefined` 以外は corrupted_data として拒否） |
| `src/components/PianoSystemCanvas.tsx` | Pass 1 で「載せる先のクレフで StaveNote を作る」「preFormat より前に `note.setStave(対象の stave)`」「またぎ位置でビームを切る」、Pass 3 で描画方法の切替（10-3） |

描画側は `hasCrossStaffRender` が false のとき**従来とまったく同じ処理経路**を通る（不変条件1を分岐の構造で守る）。

### 10-2. クレフと符幹（§4-1 のとおり）

- またぎ音符だけ、載せる先のパートの**その小節のクレフ**（`resolveMeasureClef`）で `StaveNote` を作る。臨時記号・調号は自パートの状態機械のまま
- 符幹の向きは VexFlow の自動判定に任せる。多声部小節の「声部1=上向き固定」（#192）は**またぎ音符には渡さない**（自分の五線にいる音符のための規則のため）

### 10-3. 設計時に想定していなかった点: `Voice.draw()` が五線を上書きする

VexFlow 5 の `Voice.draw(ctx, stave)` は、描画の直前に**全 tickable の五線を引数の五線で上書き**する
（`voice.js`: `if (stave) tickable.setStave(stave)`）。§2 の「stave 未設定の音符にだけ伝播する」保護規則が効くのは
`Voice.preFormat()` までで、描画時は無条件に上書きされる。そのため、またぎ音符を含む声部だけは
`Voice.draw` を使わず、`voice.getTickables()` を1つずつ `setContext → drawWithStyle` する
（`Voice.draw` が内部で行っているのと同じ手順から、五線の上書きだけを外したもの）。
またぎを含まない声部は従来どおり `Voice.draw` を通る。

### 10-4. ビームと連符（§4-2）

- ビームは `groupIndexesByRenderTarget` で「連続して同じ五線に載る区間」に切り分け、区間ごとに `Beam.generateBeams` を呼ぶ
- 連符の Tuplet オブジェクトは従来どおり音符全体で1つ作る（拍計算のため）。**またぎを含む連符でも括弧・数字は描いたまま**にした

  ブラウザ（dev サーバー・月光5小節目の形）で実際に確認した結果:
  括弧・数字は壊れてはいないが、**グループ全体（上の五線に残った3音目まで）をまたぐ幅の括弧が、
  下の五線の下側に描かれる**。読めなくはないが、市販譜のように「音符の近く」には出ない。
  自動で消す（#294 の hideNumber と同じ「draw しない」経路へ落とす）判断は**この段では入れていない**。
  理由は、市販譜の月光がそもそも数字なしであり、運用者が #294 のトグルで既に消せるため、
  自動化するとトグルの意味が失われるから。UI が入る段1b で運用者が実譜面を清書したうえで、
  「またぎを含む連符は既定で数字を出さない」を入れるか判断する

### 10-5. フォールバック（§3 / §4-4）

`resolveRenderPartIndex` が次のすべてを「自分の五線」に落とす。保存データは書き換えず、例外も出さない。

- 端のパートで行き先が無い向き（最上段の `above` / 最下段の `below`）
- パートが1つしかない編成（単段譜・**パート譜表示**）
- 未知の文字列（旧データ・手書き JSON 対策）

## 11. 段1b の実装記録（Issue #310 / 2026-08-18）

段1b（座標追従の1本化 + UI）で入れたもの、設計時の想定と変えた点を残す。

### 11-1. 座標の取り所の1本化（§4-3）

Pass 3 の先頭に「イベント → 実際に載っている五線・クレフ」を返す関数を1組だけ置き、
座標を必要とする箇所はすべてそこを通す。

| 関数 | 返すもの |
| --- | --- |
| `resolveRenderPartIndexFor(ev)` | 実際に描くパート番号（`crossStaffUtils.resolveRenderPartIndex` の薄い包み） |
| `resolveRenderStave(ev)` | 実際に載っている `Stave` |
| `resolveRenderClef(ev)` / `resolveK2lFor(ev)` | その五線で音名→線を読むためのクレフと換算関数 |
| `computeStaveBand(partIndex)` | そのパートの当たり判定の帯（隣のパートとの中間線でのクリップ） |

差し替えた参照:

- `buildNoteHitGeometry`（当たり判定 rect の y 範囲・符頭の線の範囲・`snapLine`・
  `findNearestKeyIndexWithinLines`）— 音符ごとに `noteStave` / `noteK2l` / 帯を解決する
- 当たり判定 rect の `data-line0-y` / `data-line-spacing`
- 非アクティブ声部の選択用 rect（#306）の符頭の高さ
- 選択枠（`.vf-note-selected`）の個別音の高さ
- 弧・松葉の位置台帳（`notePositionMapP` / `pendingArcsP` / `pendingHairpinsP`）と
  レガシーのタイ（`partLineNotes`）の五線
- スラーが避ける障害物の高さ

またぎでない音符では解決結果が従来の値（自分の五線・自分のクレフ・自分の帯）とまったく
同じになるため、既存譜面の当たり判定・見た目は変わらない。

### 11-2. 設計時に想定していなかった点: 五線とクレフは対で持ち回る必要がある

弧の描画（`drawTieArcP`）は「パートのクレフで線を求め、渡された五線でその線の y を引く」
構造だった。段1a で五線だけを隣へ替えても、線の換算がト音記号のままなので、
端点だけが五線5本ぶん（実測 63px）ずれた位置に付く。

そこで **五線とクレフを必ず対で持ち回る**形に変えた:

- `notePositionMapP` / `pendingArcsP` の値に `clef`（実際に載った五線のクレフ）を追加
- `drawTieArcP` の第1引数を単一の `clef` から `{from, to}` の対に変更
  （レガシーのタイ経路は両方に `part.clef` を渡すので従来と同じ）

「五線だけ差し替えれば追従する」という段1a 時点の見立てが甘かった点で、
座標の取り所を1本化する作業の一部として本段で解消した。

### 11-3. UI（§5）

- 演奏記号タブの記号調整系（⤢ / ✥ の隣）に **モードボタン「段またぎ表示」（⇵）** を追加。

## 12. 残りの音符のビームが連符境界を無視して再グループされる不具合の修正（Issue #313 / 2026-08-19）

### 12-1. 問題

8分3連×4組（12音）の**頭2音**を ⇵ で下の五線へ出すと、上の五線に残った10音のビームが
`[e4(T1), g#3(T2), c#4(T2)]` `[e4(T2), g#3(T3), c#4(T3)]` … と**1音ずつずれたグループ**で
束ねられ、連符の境界（および「3」の位置）と食い違って小節全体が崩れて見えた。
音高・またぎ先の描画位置そのものは正常で、壊れるのはビームのグループ分けだけ。

運用者が月光5小節目（声部2・三連符4組・頭2音またぎ）の清書で踏んだ。

### 12-2. 原因

段1a（10-4）の実装は「同じ五線に連続して載る音符**だけ**」を `Beam.generateBeams` へ渡していた。

```ts
groupIndexesByRenderTarget(renderPartIndexes)
  .flatMap(group => Beam.generateBeams(group.map(idx => vfNotes[idx]), beamOptions))
```

`Beam.generateBeams` は渡された音符の tick（拍の内部単位）を**先頭から足し上げて**拍の区切りを
決める（Issue #217 の経緯と同じ性質）。またぎで抜けた2音ぶんの tick が数えられないため、
残り10音の拍グリッドが 2/3 拍ぶんずれ、連符の切れ目と一致しないグループになっていた。

### 12-3. 修正設計

「**拍の区切りは全音符列で決め、またぎ位置では切るだけ**」の2段構えにした
（`src/utils/crossStaffBeamUtils.ts` の `generateCrossStaffBeams`）。

1. まず**全音符列**で `Beam.generateBeams` を1回呼び、またぎが無いときとまったく同じ区切りを得る。
   ここで作られる Beam は区切りを知るためだけのもので、描画には使わず捨てる
2. 各区切りを `splitIndexesByRenderTarget` で**またぎ位置（載る五線が変わる位置）でさらに分割**する
3. 断片ごとに `Beam.generateBeams` を呼び直して、描画に使う Beam を作る

手順3で1音だけの断片も `generateBeams` に通しているのは、**符幹の向きをその断片の音符だけで
決め直させる**ため。VexFlow は渡されたグループ単位で向きをそろえるので、まとめて渡すと
「別の五線へ行った音符の高さ」に引きずられて、上の五線に残った音符の向きが変わってしまう。
断片ごとに通せば段1a と同じ向きになる（＝またぎ以外の見た目は変わらない）。

**捨てるビームの後始末が必須**（見落とすと別のバグになる）: VexFlow の `Beam` は
コンストラクタで `note.setBeam(this)` を呼ぶため、手順1で捨てたビームの参照が音符に残ると、
その音符は「ビームがある」と判断されて**旗（flag）を描かなくなる**。ビーム本体は描かれないので
符尾だけの裸の音符になる。手順3の前に全音符の参照を外している
（VexFlow の型は `setBeam(beam: Beam)` しか公開していないので、undefined 代入だけ型を広げて呼ぶ）。

| --- | --- |

## 14. またぎペアの1音目に余分な旗が描かれる不具合の修正（Issue #319 / 2026-08-20）

### 症状と真因

§12 の修正後も、またぎペアの1音目に**移動前の五線の高さで余分な旗**が描かれることがあった（ビームの束ね方は正しい）。プロパティトラップで実測した結果、真因は VexFlow の衝突解決:

1. またぎで移した音符は、移動先の五線で**相手パートの音符と同じ tick・同じ五線**に載る
2. 合同整形中に `ModifierContext.preFormat` → `StaveNote.format`（同一 tick の音符同士の衝突解決）が走り、条件次第でどちらかの `setStemDirection` を呼ぶ
3. `StemmableNote.setStemDirection` は内部で `this.beam = undefined` を**直接代入**する（`setBeam` を経由しないため、参照の消失を検知できない）
4. 描画時に `shouldDrawFlag()` が「ビーム無し」と誤判定 → ビームは描かれているのに旗も描かれる。旗の位置は反転後の符幹の幾何で計算されるため宙に浮く

またぎの無い譜面では、同一 tick の音符は ModifierContext 上で五線が分かれており、ビーム済み音符の向きが反転される組み合わせが生じない。発生条件が「衝突の組み合わせ次第」だったのはこのため（m5 実データ形では出ず、声部1が全休符のみ／単声の m10 で出た）。

### 修正

`restoreCrossStaffBeamAssignments(beams)`（crossStaffBeamUtils.ts）: 各ビームについて `getStemDirection()`（ビーム構築時に記録された向き）と `getNotes()` を使い、**向き → 参照の順**で復元する（`setStemDirection` が再び参照を消すため順序が必須）。呼び出しは PianoSystemCanvas の描画パス（Pass 3）の `hasCrossStaffNote` 分岐の中・per-note 描画の直前。またぎの無い声部はこの分岐に入らないので、従来の描画は 1px も変わらない。

向きも一緒に戻す理由: ビームで繋がったグループの符幹は同方向が浄書の前提で、衝突解決が片方だけ反転させたままだとビームの形が壊れるため。

### 検証（2026-08-20 実測）

- 単声 m10（三連符2組・頭2音またぎ・左手全音符和音）: 旗が e/4 の1本だけになった（修正前は1音目に fx119/fy89 の余分な旗）
- 声部2 m10（声部1=全休符）: 同上（fx108/fy94 の余分な旗が消えた）
- m5 実データ形（声部2またぎ+声部1メロディ）: ビーム14本の x/w が §12 実測と完全一致・旗1本のまま（回帰なし）
- 単体テスト: setStemDirection による参照消失の再現 → 復元で参照と向きが戻ること／ビームに属さない音符（旗）には何もしないこと

## 16. 段またぎ連符の数字が下の五線の中に描かれる不具合の修正（Issue #574 / 2026-09-04）

§10-4 で宿題にしていた「またぎを含む連符の括弧・数字の扱い」の決着。
運用者QA（月光検聴版 7〜8小節目）で、右手の段またぎ3連符の数字「3」が
**ヘ音記号の五線の中**に描かれ、五線の線・左手の音符と重なって読めない状態が報告された。

### 16-1. 原因（実測）

VexFlow の `Tuplet.getYPosition()` は「**先頭音符の五線**」を起点にして、そこから
グループ内の**符幹の先**まで外側へ広げて数字の高さを決める。段またぎでは

- 音符ごとに五線が違う（起点が「相手の五線」になることがある）
- 段またぎ連桁（§15 段2）では符幹が**五線と五線の間**へ向く

ため、起点も符幹の先も相手の五線の中を指す。jsdom 実測（ト音 y=60〜100 /
ヘ音 y=140〜180 の大譜表・8分3連の2〜3音目を below）で、数字は **y=167 ＝
ヘ音記号の五線のど真ん中**に描かれていた。またぎ方を変えた5通りの実測:

| またぎ方（3音） | 修正前の数字 y | 判定 |
| --- | --- | --- |
| self / below / below | 167 | ヘ音記号の五線の中（報告された症状） |
| self / self / below | 43 | 上の五線の上（たまたま正常） |
| below / self / self | 73 | **ト音記号の五線の中** |
| below / below / self | 202 | 下の五線の下（外だが音符から遠い） |
| below / below / below（全音符またぎ＝五線1つ） | 202 | 従来どおり（§16-4） |

`syncTupletPlacementWithNotes`（#471）は段またぎを**対象外にして早期 return** していたため、
この補正は効いていなかった。

### 16-2. 修正設計（round1 の差し戻しを受けて作り直した版）

`syncTupletPlacementWithNotes` の早期 return を、段またぎ専用の置き直し
（`placeCrossStaffTupletNumber`・同じモジュール内）へ差し替えた。
連符数字の置き場所を決める処理は引き続きこの1関数群だけが持つ（同じロジックの2枚目を作らない）。

置き場所の規則:

1. **梁の側を実測で決める**（`isBeamSideBelow`）。浄書では連符数字は梁と同じ側に置く
   （Gould, Behind Bars）。段またぎでは梁が相手の五線の方へ渡るので、
   **梁の高さ（＝符幹の先の平均 y）が持ち主の五線より下なら下側**、上なら上側とする。
   月光7〜8小節の右手（下段へ食い込む3連符）はこの判定で「下側」になる。
   符幹が読めない場合・梁が持ち主の五線の中に収まっている場合は、
   グループがまたいだ先の向き（下の五線へ出ているか）で決める
2. その側の一番外の五線（下側なら一番下の五線）の外へ出す。起点の 1.5間・2間は
   VexFlow が普通の連符に使っている余白と同じ値
3. そこからさらに、**連符自身の音符（符頭・符幹の先）と、同じ横位置にある他の音符
   （左手の和音など）を避ける**ように外側へ押し出す。これで五線・音符のどちらとも重ならない
   （Issue の仕様1「どちらの五線にも重ならない」・仕様2「左手の音符・符幹との衝突回避」）
4. VexFlow には位置を直接指定する API が無いので、`options.yOffset` に
   「目標値 − VexFlow が計算した値」を書き込む（型は yOffset の1項目だけに絞って触る）。
   括弧も数字と同じ `yPos` から描かれる（`Tuplet.draw()`）ので、この1か所で両方が一緒に動く

**五線と五線の間（梁そのものが通る場所）には置かない。** 段またぎ連桁と符幹が通っていて、
大譜表の段間（実測 40px 程度）には数字を入れる余地が無いため、「梁の側」は満たしつつ
**その側の五線の外へ抜けた位置**を選ぶ。

#### 左手の音符を避けるための障害物の集め方

数字を置く時点で「左手（下段）の和音がどこまで下がっているか」を知る必要があるが、
描画（Pass 3）はパート順に進むため、右手を描く時点で左手はまだ描かれていない。
ただし **Pass 2 の合同フォーマットが済んだ後なら、まだ描いていないパートの音符でも
位置は確定している**ので、`PianoSystemCanvas` の Pass 3 手前で
「この段の全パート・全声部の音符の描画範囲（BoundingBox）」を返す関数を用意し、
`syncTupletPlacementWithNotes` へ渡す。

- **段またぎ連符があったときだけ**呼ばれる（関数で渡し、呼ばれた時点で1回だけ集めて使い回す）
  ので、またぎの無い大多数の小節では従来と同じコストのまま
- 障害物は**連符の横位置に重なるものだけ**に絞る。小節の別の場所にある低音まで見ると、
  関係の無い音のせいで数字が遠くへ飛んでしまう
- **集める前に、この段の全パートのビームを post-format しておく**（round 2 P1・下記 16-7）。
  Pass 2 の合同フォーマットで確定するのは「横位置」までで、**符幹の長さは
  `Beam.postFormat()`（＝既定では `Beam.draw()` の中）で連桁の傾きに合わせて伸び縮みする**。
  右手を描く時点で左手はまだ描かれていないので、そのままでは左手の連桁付き音符が
  「伸びる前の符幹」で記録されてしまう

なお数字は「求めた高さに**中心**をそろえて」描かれる（`Tuplet.draw()`）ので、
五線・音符から空ける間隔には**数字の高さの半分**（`TUPLET_NUMBER_HALF_HEIGHT_SPACES = 0.75` 間）を
足している。足さないと、基準の高さは空いていても文字の上端だけが符頭へ食い込む。

### 16-6. round1 の差し戻しと作り直し（2026-09-04）

最初の実装（PR #615 初版）は、数字を**持ち主のパートの五線の外側**（右手が下へまたぐなら
上の五線の上）へ出していた。レビューで「配置方針が仕様と逆。梁の位置・向きを見ずに
『右手=上・左手=下』へ固定している」として差し戻された。

作り直しの要点は上の 16-2 のとおり:

- 置く側を**梁の実測位置**（符幹の先の平均）で決めるようにした。月光7〜8小節の右手なら
  梁は下段へ渡るので、数字も下側へ出る
- 「五線の外」だけでなく、**左手の符頭・符幹（他パートの音符）とも重ならない**ようクランプした
- ScorePage 実マウントの配線テストと、括弧・両方向・左手との非交差の回帰テストを足した

初版が主張していた「またぎでない連符と同じ高さ帯に並ぶ」という副次的な利点は失われるが、
浄書規則（数字は梁の側）と Issue の仕様1が優先である、というのがレビューの裁定。
