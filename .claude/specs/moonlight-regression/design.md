# 設計書: 月光1〜9小節の実曲回帰チェック（Issue #243）

## 問題

実機テストの振り返り（2026-08-11・21本の教訓）で、次のプロセスの穴が確認された。

- #237（発想標語がデータには入っているのに描画されない・StaffCanvas 廃止時の移植漏れ）
- #240（BPM 下限）

いずれも「機能を単体で作り、実曲では一度も使わないまま次へ進む」ことで見逃されていた。
単機能の単体テストは全部緑なのに、実曲を1曲通すと壊れている、という状態を機械で止められていない。

PR #242 で `docs/qa/regression/moonlight-bars1-9.score.json`（ベートーヴェン「月光」第1楽章
1〜9小節を運用者が実機で入力したそのままの保存データ）を回帰テスト資産として追加したが、
この時点では手動で「ファイルを開く」ためのデータでしかなく、CI では一度も読まれていなかった。

## 修正設計

fixture を **読込 → 描画 → 再生スケジュール** の3経路へ流し、毎回の `npx vitest --run src` で
自動的に検証する。ブラウザ自動化は新規導入しない（jsdom 上で完結させる）。

### テストファイルの分担

| ファイル | 見るもの | 使う関数 |
| --- | --- | --- |
| `src/utils/moonlightRegressionLoad.test.ts` | 読込。ファイルを開く経路を通したあとのデータの形 | `importScoreFromFile`（= `validateSavedScoreData` を内包） |
| `src/components/MoonlightRegressionRender.test.tsx` | 描画。例外なく完走し、期待した数の要素が出るか | `PianoSystemCanvas`（3段ぶんを1マウント） |
| `src/utils/moonlightRegressionPlayback.test.ts` | 再生スケジュール。音を鳴らす手前の純ロジック | `flattenMeasureForPlayback` / `getMeasureDurationBeats` / `buildPlaybackPositionTimeline` |

3ファイルに分けたのは、落ちたときに「読めないのか・描けないのか・鳴らせないのか」が
ファイル名だけで分かるようにするため。fixture の読込は各ファイルで `readFileSync` して
おり、共有ヘルパは作っていない（`node:fs` を `src` の非テストコードへ持ち込まないため）。

### 期待値の決め方

期待値はすべて **fixture から機械抽出した実測値をテスト内に定数化** した。
「本来こうあるべき」という理想値ではなく、**いま実際にこう振る舞っている** という値を固定する。

README（`docs/qa/regression/README.md`）記載の「既知の入力上の傷」3件は直さず、
そのまま期待値に織り込む。むしろ「傷が傷のまま残っていること」自体をテストで固定した
（`fixture` を後から誰かが"直して"しまう事故を検知するため）。

- 傷1: 5小節目・右手声部2の最初の3連符が `b/1, d#/2, g#/2`（#219 の誤帰属で入った超低音）
- 傷2: 8小節目・右手声部2に `b/3` の3重ユニゾン和音（誤クリックの実物）
- 傷3: 9小節目・右手声部2の連符IDが入れ子に交錯（4番目のグループの最後の1音が末尾に取り残されている）

### 主な固定値

fixture 全体（両パート・全声部の合計）:

| 項目 | 値 |
| --- | --- |
| パート | 2（`right-hand`/treble・`left-hand`/bass） |
| 小節数 | 13（入力済み9＋末尾の空4） |
| イベント総数 | 140 |
| うち休符 / 和音 / 付点 | 3 / 11 / 3 |
| 連符グループ | 36（右手のみ。全小節4グループずつ） |
| スラー | 3本（3小節目内に2本＋7→8小節の小節またぎ1本） |
| 松葉 | 0本 |
| テンポ表記 / 発想標語 / 強弱 / 運指 | 1 / 1 / 1 / 2 |
| 段構成 | `systemMeasureOverrides` により 3小節×3段 |

描画（段ごと）:

| 段 | 小節 | stavenote | パディング休符 | 連符の囲み | 弧 |
| --- | --- | --- | --- | --- | --- |
| 1段目 | 1〜3 | 42 | 0 | 12 | 2 |
| 2段目 | 4〜6 | 50 | 0 | 12 | 0 |
| 3段目 | 7〜9 | 50 | 2 | 11 | 1 |

- **不変条件**: `stavenote − パディング休符 = その段のデータ上のイベント数`（42 / 50 / 48）。
  丸暗記した数字とは別経路で「描き漏らし・描きすぎ」を検知できるので、期待値の写し間違いにも気づける
- 連符の囲みは 36 グループ中 **35個**しか描かれない。足りない1個は上記の傷3（連符IDの交錯で
  グループが連続していない）によるもの。fixture を直さない約束なので、この 35 を正として固定する

再生スケジュール:

| 項目 | 右手 | 左手 |
| --- | --- | --- |
| 畳んだあとのイベント数（合計） | 121 | 19 |
| 総拍数 | 36拍 | 36拍 |
| 位置タイムラインの件数 | 59 | 11 |
| 最終ハイライト時刻（BPM120） | 16000ms | 16000ms |

- 位置タイムライン（`buildPlaybackPositionTimeline`）が声部1（`measure.events`）しか見ないのは
  現行仕様。声部2の音符は光らない。ここでは**現状の仕様をそのまま固定**しており、
  声部2も光らせるべきかどうかは本Issueの範囲外
- 3連符は1音 1/3 拍のため、拍の比較は浮動小数の誤差を許容して行う。
  `flattenMeasureForPlayback` の開始拍の並びも、同拍とみなす許容差 0.0001（実装のソートと同じ値）
  の範囲では逆転を許す（同拍なら声部順で並ぶのが正しい挙動のため）

### fixture の完全性チェック

構造と件数だけを見ていると、**音高を1文字書き換えるような変更を素通ししてしまう**
（実際に `g#/3` → `g#/4` の1バイト変更で件数系のテストは全緑のままだった）。
そこで次の2段構えにした。

1. `docs/qa/regression/README.md` に記載済みの SHA-256
   （`1beb6b3d246a13d24c8b1f5ddf8cd37ea37a29e3af5d77811c6ed3c94bfc5d8b`）をテストで照合する
2. それだけだと落ちたときに「何が変わったか」が分からないので、1小節目の音高列と
   1音目に載っている記号（テンポ表記・発想標語・運指）も併せて固定する

fixture はテストから読むだけで、書き換えは一切しない。

### なぜ描画テストを1マウントにまとめたか

`ScorePage` / `PianoSystemCanvas` を全体マウントするテストは共有Docker環境で1回あたり数秒かかり、
マウント回数を増やすと同時実行の他ファイルまでタイムアウトへ巻き込む（#176 の知見）。
そのため3段ぶんを1回の `render()` にまとめ、その結果に対して複数の観点を確認する形にした
（`it` を細かく割らず、コメントで何を見ているかを書く方針）。

## 検証

- 新規3ファイル・10テストすべて緑（`npx vitest --run` で該当3ファイルを指定、約5秒）
- **検知能力の証明**: fixture の1バイト（`["g#/3"]` → `["g#/4"]`、オフセット584）を書き換えて
  同じ3ファイルを流すと、SHA-256 照合と1小節目の音高列の2テストが失敗することを確認。
  確認後、`git checkout` で元に戻し、SHA-256 が README 記載値と一致することを再確認済み
- 全体テスト・lint・build の結果は PR 本文に記載

## 影響範囲

- **追加のみ**。アプリのコード（`src` の非テストファイル）には一切手を入れていない
- `docs/qa/regression/moonlight-bars1-9.score.json` は読むだけで変更なし
- 新しい依存は追加していない（`node:crypto` / `node:fs` は Node 標準）
- 3ファイルとも `src` 配下にあるため、`npx vitest --run src` と CI の `npm test` に自動で含まれる
  （常設化のための追加設定は不要）

## 今後この fixture を触るとき

- fixture を意図的に更新する場合は、README の SHA-256 と
  `moonlightRegressionLoad.test.ts` の `EXPECTED_FIXTURE_SHA256` を同時に更新する
- 傷を直した版が必要になったら、README の指示どおり別ファイル（`-clean.score.json`）を作る。
  本ファイルは書き換えない
- 描画・再生の仕様変更で期待値が変わる場合は、**変わった理由を必ずこの design.md へ追記**する
  （数字だけ書き換えると、退行なのか意図した変更なのか後から区別できなくなる）
