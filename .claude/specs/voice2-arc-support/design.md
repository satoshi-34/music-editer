## 1. そのまま再利用する層（無改修が前提）

トリアージ追記（2026-08-02）の指示どおり、**次の2層には手を入れない**設計にする。
調査の結果、いずれも「声部を知らない」形になっており、実際に無改修で使えることを確認した。

1. **弧の形の計算** — `src/components/arcUtils.ts` の `computeArcGeometry`。
   引数は座標・向き・種別・符幹方向・障害物Y・オフセットだけで、イベント配列にも声部にも触れない。
   曲率・太さの調整が必要になったらこの関数だけを直す、という現在の切り分けを維持する。
2. **行またぎ（段またぎ）の2セグメント分割描画** — `crossSystem` 判定と `drawArcPathP(... '-1' / '-2')` の2本描き、
   および終点が別 Canvas にある場合の逆引き描画（`incomingArcIndex`）。
   入力は「描画済みの `StaveNote` と `Stave`」だけなので、**どの声部の音符を渡しても同じように動く**。

**この層に改修が必要になった場合は、その理由を未決定事項として運用者へ明示してから着手する**（黙って触らない）。

ただし1点だけ、**`incomingArcIndex` の作り手側**（`src/utils/incomingArcUtils.ts`）は
`measure.events` しか走査していないため、ここは「再利用する層」ではなく改修対象になる（§3-4）。
描画側の逆引きロジック自体は無改修のままでよい。

## 2. データモデル案の比較

### 案A: 声部ローカルで完結させる（**推奨**）

`TieArc` / `HairpinMark` のスキーマを**一切変えない**。代わりに解釈を1つだけ明文化する。

> `arcs[]` / `hairpins[]` が載っているイベントが属する声部と、`toEventIndex` / `endEvent` が指す先の声部は**常に同じ**。
> つまり `toEventIndex` は「その声部の events 配列の中の位置」を意味する。

- 既存データ（arcs はすべて `measure.events` ＝ 声部1）はこの解釈でそのまま正しい。
  `getMeasureVoices` / `getVoiceEvents` が「voiceIndex 0 は常に `measure.events`」と定義しているため
  （`voiceMeasureUtils.ts:67-81`, `:113-118`）、**声部1のデータは1バイトも意味が変わらない**。
- マイグレーション不要・保存形式のバージョン上げ不要。読み込み時の分岐も不要。
- 既存の声部1向けコード（`deleteEventFromMeasures` の `m.events` 走査など）が
  「他声部の arcs を触らない」＝**正しい**という性質を自動的に満たす（案Bだと同じコードが誤爆源になる）。
- 弱点: **声部をまたぐ弧を表現できない**（§4 で検討。当面は許可しない方針なので弱点にならない）。
- 将来、声部またぎを解禁したくなったときは `toVoiceIndex?: number`（省略時＝始点と同じ声部）を
  optional で足すだけで案Bに移行できる。**前方互換のある出発点**になっている。

### 案B: `TieArc` に `voiceIndex?: number` を持たせる

弧の**終点が属する声部**（あるいは弧自身の声部）を明示的に持つ。

- 声部またぎを最初から表現できる。
- 既存データは `undefined` ＝ 0 とみなせば互換。ただし「省略時の意味」を全参照箇所で正しく揃える必要があり、
  1箇所でも `arc.voiceIndex` を見落とすと**声部1の同じインデックスの音符を指してしまう**
  （#112 のタイ誤爆・#105 のクリック誤爆と同じ「無言のデータ破壊」の形）。
- 索引の付け替え処理（削除・小節挿入）が「全声部を走査しつつ声部ごとに別々に数える」二重ループになり、
  既存の単純なコードより明確に壊れやすい。

### 案C: `fromVoice` / `toVoice` を両方持つ完全明示

- 弧を小節単位のどこに置いてもよくなる（イベントに載せる必要すらなくなる）。
- 保存形式の破壊的変更＋マイグレーションが必要で、#112〜#180 で積み上げた「既存データを壊さない」原則に反する。
- 得られる表現力（声部またぎ）に対して代償が大きすぎる。**不採用**。

### 比較表

| 観点 | 案A（声部ローカル） | 案B（`voiceIndex` 追加） | 案C（完全明示） |
| --- | --- | --- | --- |
| 既存保存データの互換 | ◎ 無変換 | ○ 省略時0の解釈でOK | × マイグレーション必須 |
| 実装量 | 小（走査を声部ぶん回すだけ） | 中 | 大 |
| 誤爆（他声部を書き換える）リスク | 低（既存コードが自然に安全側） | 中〜高 | 中 |
| 声部またぎの表現 | × | ◎ | ◎ |
| 将来の拡張余地 | ○ `toVoiceIndex` を足せば案Bへ移行可 | — | — |

**結論: 案A を採用する。** 声部またぎが必要になった時点で `toVoiceIndex` を optional 追加して案Bへ育てる。

## 3. 描画収集の声部対応方針

### 3-1. `notePositionMapP` のキー設計

現状は `${pi}-${absI}-${j}`（`PianoSystemCanvas.tsx:2708`）。案Aでは**声部を混ぜてはいけない**ので、
声部を含めた `${pi}-${absI}-${vi}-${j}` に変える。

ただし、**キー文字列を `split('-')` で読み直している箇所が3つある**点に注意する。
桁を1つ増やすと位置がずれるため、機械的な置換では必ず事故る。

| 箇所 | 用途 | 現在の解釈 |
| --- | --- | --- |
| `PianoSystemCanvas.tsx:4287` | スラーの障害物候補を集めるとき `notePositionMapP` を走査 | `[pi, m, e]` |
| `PianoSystemCanvas.tsx:2213` | `arcKey` から弧の同定（曲率ドラッグ開始） | `[pi, fm, fe, ai]` |
| `PianoSystemCanvas.tsx:2248` | `arcKey` から弧の同定（端点ハンドルのドラッグ開始） | `[pi, fm, fe, ai]` |

**方針: 文字列を解析するのをやめる。**

- `notePositionMapP` の**値**に `partIndex / measureIndex / voiceIndex / eventIndex` を持たせ、
  走査側（4287）は値を読む。キーは同定専用の不透明な文字列に格下げする。
- `arcKey` も同様に、`arcIdentityMap: Map<string, {partIndex, voiceIndex, fromMeasure, fromEvent, arcIndex}>` を
  1本用意して `drawArcPathP` の中で登録し、ドラッグ開始側（2213 / 2248）はそこから引く。
- こうすると、将来キー形式を変えても解析側が壊れない（今回の事故りやすさの根本を潰せる）。

### 3-2. 収集ループの声部対応

現状の収集は「小節ループの中で `safeEvs`（声部1）を1回なめる」形（`:2704-2712`）。
これを **`renderedVoiceEntries` を回す形**に変える（描画・淡色化・当たり判定がすでに使っている単位）。

```
renderedVoiceEntries.forEach(entry => {
  entry.sourceEvents.forEach((ev, j) => {
    notePositionMapP.set(key(pi, absI, entry.voiceIndex, j), {...})
    ev.arcs?.forEach(...)      // pendingArcsP へ（voiceIndex 付き）
    ev.hairpins?.forEach(...)  // pendingHairpinsP へ（voiceIndex 付き）
  })
})
```

- レガシーの `partLineNotes`（`tiedToNext` 方式）は**声部1のまま**にする。
  旧データ互換専用の経路であり、声部2の旧データは存在しない（声部2は arcs 方式より後に生まれた機能のため）。
- `pendingArcsP` / `pendingHairpinsP` の要素へ `voiceIndex` を足し、終点の逆引きも同じ声部のキーで行う。

### 3-3. パディング休符・ghost 休符とのインデックス整合（要注意）

`entry.sourceEvents` は「実データ ＋ 表示用パディング休符（`__isPlaceholder`）」である
（`PianoSystemCanvas.tsx:2455-2460`）。パディングは**常に末尾へ追加**されるので、
先頭から `rawSourceEvents.length` 件までのインデックスは実データと一致する。
弧の端点は必ず実データ側（かつ非休符）なので、**この「末尾追記」の性質が崩れない限り安全**。

- 実装時の不変条件として明記する: **パディング休符を途中へ挿入する改修をしてはならない**（既存インデックスがずれる）。
- ghost 休符（追加声部の末尾休符を非表示にする既存仕様）は休符にしか掛からないため、弧の端点には影響しない。
  ただし `GhostNote` は `getStemDirection()` で例外を投げる（#180 の教訓）。
  弧の描画は `getStemDirection()` を**呼ぶ**ため（`:4275`, `:4324`）、
  万一 ghost 休符が端点になり得る改修が入ると同じ形の例外が出る。既存の `try/catch` は残す。

### 3-4. `incomingArcIndex`（段またぎの終点側）

`buildIncomingArcIndex`（`src/utils/incomingArcUtils.ts:12`）が `measure.events` しか見ないため、
**声部2の弧は「終点だけが次の段にある」ケースで第2セグメントが描かれない**。

- `getMeasureVoices(measure)` を使って全声部を走査し、`IncomingArcEntry` に `voiceIndex` を追加する。
- 終点側 Canvas の照合（`:4357-4360`）も声部込みのキーで行う。
- この関数は `ScorePage.tsx:3052` で1回だけ作られ、全譜種（単旋律・四重奏・編成・パート抽出）へ配られる。
  声部が無い譜種では `getMeasureVoices` が声部1のエントリ1件だけを返すため、**挙動は完全に不変**。

## 4. 声部をまたぐタイ／スラーを許すか

### 浄書慣行の観点

- **タイ**: 同一音高の音を繋ぐ記号なので、原則として同じ声部の中で完結する。
  声部をまたぐタイは「声部の入れ替わり（voice exchange）」や「ある声部が消えて別の声部が引き継ぐ」書法で稀に現れるが、
  市販譜では**その場面で声部の割り当て自体を組み替える**（＝タイは同一声部内に収まる）ことが多い。
- **スラー**: 1本のスラーは「1つの声部のフレーズ」を示す記号であり、声部をまたぐスラーは通常書かない。
  複数声部にまたがる大きな括りが必要な場面ではフレーズ記号や括弧を使う。
- **松葉**: 声部ではなく**段（staff）全体**に掛かる強弱指示なので、そもそも「どの声部か」は本質的でない（§7 で別途扱う）。

### 実装コストの観点

声部またぎを許すと、案B（`toVoiceIndex`）が必要になるうえ、
削除・挿入時の索引付け替えが「声部をまたいだ参照」を追跡する必要が出て、
既存の単純な走査（`m.events.map(...)`）がすべて誤爆源に変わる。

### 結論

**当面は許可しない**（同一声部内でのみ弧を張れる）。

- 入力段階でガードする: ドラッグの始点と終点の声部が違う場合は**何もしない**（＝誤って声部1へ書かない）。
  始点と終点は常にアクティブ声部の当たり判定から来るため、実際には自然に同一声部になる。
  ただし「アクティブ声部を切り替えながらドラッグする」ような経路が将来生まれた場合に備えて、
  確定処理（`applyArc`）側でも声部の一致を確認する（**入口と確定の両方で塞ぐ**のは #112 で採った方針と同じ）。
- ユーザーから要望が出たら、`toVoiceIndex` の追加として別Issueで検討する。
- **未決定事項として運用者へ確認する**（§14-1）。

## 5. 弧の向きの既定値

現状の `upward` は音高の平均から決まる（タイは `fromLine<2`、スラーは区間内の音符の平均。`:2274-2281`）。
2声部書法では**声部1＝上向き・声部2＝下向き**が慣行であり、符幹の向き固定（`resolveVoiceStemDirections`）と同じ発想になる。

**方針案**: `isMultiVoiceMeasure`（＝その小節に声部が2本ある）のときだけ、
`upward = (voiceIndex === 0)` を既定値にする。`flipDirection`（手動反転）は従来どおり最優先で効かせる。

注意点:

- 弧が複数小節にまたがる場合、「多声かどうか」は**始点の小節**で判定する（途中で切り替わると弧が途中で向きを変えてしまう）。
- **既存譜面の見た目が変わり得る**: 声部2を使っている小節に既に声部1の弧が張ってある譜面では、
  今まで音高で決まっていた向きが「常に上向き」に変わる。リグレッションではなく意図した仕様変更だが、
  ユーザーの手動調整（`cpDyOffset`）と組み合わさると見た目が崩れる可能性がある。**運用者判断が要る**（§14-2）。
- 単声部の小節・声部トグルの無い譜種（単旋律・四重奏・編成）は `isMultiVoiceMeasure` が常に false なので**完全に不変**。

## 6. スラーの障害物回避のスコープ

スラーは途中の音符を避けるために `allLines` / `allNoteYs` を集める（`:4282-4300`）。
現状は「同じパートの、始点〜終点の範囲にある**すべての**音符」を拾う（声部の区別なし）。

**方針案: 自声部の音符だけを避ける。**

- 根拠（浄書慣行）: スラーは声部に属する記号であり、市販の2声部譜でも
  上声のスラーは上声の音符に沿って引かれる。下声の音符まで避けようとすると弧が不自然に大きく膨らみ、
  かえって下声のスラーや符幹とぶつかる。
- 副次的な利点: 案A（声部ローカル）と収集単位が一致し、実装が `entry` 単位で素直に閉じる。
- 副作用として、下向きの声部2スラーが声部1の低い音符と交差する構図はあり得る。
  その場合はユーザーが `cpDyOffset`（曲率ドラッグ）で逃がせるので、自動回避は入れない。
- **運用者判断が要る**（§14-3）。実装は「自声部のみ」を既定にしつつ、収集関数の引数1つで切り替えられる形にしておくと
  レビュー後の方針変更が安い。

## 7. 松葉（ヘアピン）の縦位置 — 調査で新たに分かった論点

松葉は五線の下（`stave.getYForLine(4) + HAIRPIN_Y_OFFSET + offsetY`）に描かれる（`:4403`）。
この計算に声部の区別が無いため、**声部1と声部2の松葉を同じ区間に付けると完全に重なる**。

- 浄書慣行では、松葉は原則として**段全体**に掛かる指示であり、
  2声部それぞれに別の松葉を付けること自体が例外的（ピアノ譜では下声＝左手ではなく、同じ段の下声である点に注意）。
- したがって選択肢は2つ:
  - **(a) 声部2でも松葉を張れるようにするが、縦位置は共通のまま**（重なりはユーザーが `offsetY` で逃がす）
  - **(b) 声部2の松葉は当面サポートしない**（タイ／スラーのみ解禁し、松葉は声部1限定のガードを残す）
- この文書の推奨は **(a)**。理由は、#112 で「声部2では無反応」にした対象がタイと松葉の両方であり、
  片方だけ解禁すると「なぜ松葉だけ無反応なのか」が UI から読み取れないため。
  ただし重なりの実害が大きいと運用者が判断するなら (b) でも実装コストは下がる。**運用者判断が要る**（§14-4）。

## 8. 編集整合性（この対応の最大の難所）

弧を張れるようにするより、**張った後にデータが壊れないようにするほうが難しい**。
声部2で弧を解禁した瞬間に「通常操作で必ず踏む」壊れ方が生まれる箇所を洗い出した。

| 処理 | 現状 | 声部2で弧を解禁すると起きること | 必要な対応 |
| --- | --- | --- | --- |
| 音符削除（声部2） `PianoSystemCanvas.tsx:1363-1394` | 素の `splice`（＋連符グループ置換）のみ | 削除した音符を終点とする弧が**宙に浮く**。後続を指す `toEventIndex` が**1件ずつずれて別の音符に繋がる** | 声部2の削除にも `deleteEventFromMeasures` 相当の「終点の除去＋後続の繰り上げ」を入れる（案Aなら**同じ声部の中だけ**を走査すればよい） |
| 音符削除（声部1） `noteDeletionUtils.ts:88-112` | `m.events` のみ走査 | 案Aでは**これで正しい**（声部2の弧は声部2のインデックスを指すため、声部1の増減と無関係） | 変更不要。ただし「なぜ変更不要か」をコメントで残す |
| 和音の1音だけ削除 | 声部1のみ実装（`keyIndex` 経路） | 声部2の和音から1音消す経路が無い（現状も無い）ため、まずは影響なし | 段外。将来対応時に `fromKey`/`toKey` 一致による弧の除去を忘れないこと |
| 小節の挿入・削除 `measureInsertDeleteUtils.ts:63-69` | **すでに `voices` も走査済み** | 問題なし | 変更不要（テストで固定する） |
| 音高移動（↑↓） `pitchShiftUtils.ts:98-152` | `voiceIndex` 対応済み。同じ声部の中で `fromKey`/`toKey` を追従 | 案Aと整合し、問題なし | 変更不要（テストで固定する） |
| 連符グループ削除 | 声部2も `planTupletGroupDeletion` を通る（#168） | グループが**複数イベントまとめて**消えるため、繰り上げ量が1ではない | 上の「削除」対応をグループ範囲に対応させる（`groupEnd - groupStart + 1` 件ぶんずらす） |
| 記譜音表示の移調 `displayTransposeUtils.ts:19-40` | `measure.events` のみ | 声部2の音符も arcs もシフトされない（**既存の穴**。声部はピアノ譜専用で、ピアノは移調楽器ではないため実害は小さい） | 本対応のスコープ外。別Issue候補として記録（§14-6） |

**教訓の再確認**（`piano-two-voice-implementation/design.md` より）: 声部を広げるときは
「書き込み経路の入口をすべて塞ぐ／すべて配線する」ことが要る。今回の書き込み経路は**5本**ある。

1. `applyArc`（新規タイ／スラー）`:2791`
2. `applyHairpin`（新規松葉）`:2805`
3. 端点ハンドルのドラッグ確定（`startDx/Dy` 等）`:1740-1758`
4. 曲率ドラッグの確定（`cpDyOffset` / `flipDirection`）`:1763-1784`
5. Delete キーによる弧・松葉の削除 `:1305-1316`, `:1325-1335`

3〜5 は `cpDragRef` / `epDragRef` / `selectedArc` / `selectedHairpin` が `voiceIndex` を持っていないので、
**状態の型から順に配線する**（型を先に直せば、直し漏れがコンパイルエラーとして出る）。

もう1つの落とし穴（#112 の教訓）: `withVoiceEventsUpdated` を無条件に通すと、
**声部2をまだ使っていない小節に空の `voices[1]` が作られ、多声小節と判定されて見た目が勝手に変わる**。
弧の追従処理で全小節をなめるときは、`pitchShiftUtils` と同じく
「中身が実際に変わった小節だけ差し替える（変化が無ければ元の参照をそのまま返す）」形にする。

## 10. MusicXML への影響

### 調査結果（重要な訂正）

**タイ・スラーは MusicXML の書出・読込に一切載っていない。声部1でも未実装である。**
（`musicXmlExport.ts` / `musicXmlImport.ts` に `<tied>` / `<slur>` を扱うコードが無い）

したがって「声部2のタイ／スラーを MusicXML に書けるようにする」ことは、
**この Issue の主題（声部2対応）ではなく、そもそも未実装の機能追加**である。

### 方針案

- **段5の範囲は松葉のみとする。** `buildHairpinPositionMaps` を `getMeasureVoices` 経由の全声部走査にし、
  声部2の `<wedge>` を `<backup>` の後（声部2の音符列の中）に出す。読込側は `<backup>` で声部を分けているので
  （`musicXmlImport.ts` の既存方式）、同じ区切りに従えばよい。
- **タイ・スラーの MusicXML 対応は別Issueへ切り出す**ことを提案する（`<tied>` は `<notations>` 内、
  `<slur number=... type="start|stop">` は番号管理が要るため、声部2とは独立した設計判断が要る）。
- 声部2は3声部以上を扱わない現状の制限（`voices[2]` 以降は対象外）を維持する。
- **運用者判断が要る**（§14-5）。

## 12. 段階的PR分割案

各段は**単独でマージしても壊れない**ように順序を決めている。特に「入力を解禁する段」を最後寄りに置き、
その前に整合性の土台を入れてある（#168 で連符入力を解禁したときに削除経路の穴が同時に露出した反省）。

### 段1: 描画収集の声部対応（読み取り専用・見た目は不変）

- `notePositionMapP` を声部込みのキーへ。値に `partIndex/measureIndex/voiceIndex/eventIndex` を持たせ、`split('-')` による解析を廃止（§3-1）
- `pendingArcsP` / `pendingHairpinsP` を `renderedVoiceEntries` から全声部ぶん収集（§3-2）
- `buildIncomingArcIndex` を全声部走査に、`IncomingArcEntry` に `voiceIndex` を追加（§3-4）
- 入力の解禁はしない（`activeVoiceIndex!==0` のガードは残す）

**受入条件案**
1. 手で用意した「声部2の events に arcs を持つ」データを読み込むと、その弧が描画される（ユニットテスト）
2. 声部2の弧が段をまたぐとき、終点側の段にも第2セグメントが描かれる（ユニットテスト）
3. 声部1のみの譜面・単旋律譜・四重奏・編成譜のスナップショット的な描画が**一切変わらない**
4. `npx vitest --run src` / `npm run lint` / `npm run build` が通る

### 段2: 編集整合性ユーティリティの声部対応

- 声部2の Delete に arcs / hairpins の追従（終点の除去・後続の繰り上げ・連符グループ範囲対応）を実装（§8）
- 「変化が無い小節は元の参照を返す」形を徹底し、空の `voices[1]` を作らない
- `measureInsertDeleteUtils` / `pitchShiftUtils` は変更不要であることをテストで固定

**受入条件案**
1. 声部2の弧の終点音符を削除すると、その弧も消える（声部1のデータは不変）
2. 声部2で弧の終点より前の音符を削除すると、`toEventIndex` が繰り上がって同じ音符を指し続ける
3. 声部2の連符グループを削除したとき、繰り上げ量がグループの件数ぶんになる
4. 声部2を持たない小節に空の `voices[1]` が作られない
5. 小節の挿入・削除で声部2の `toMeasureIndex` が正しく付け替わる（既存実装の固定）

### 段3: 入力・選択・ドラッグ編集の解禁（ユーザーから見て機能が増える段）

- `mousedown` / `mouseup` の `activeVoiceIndex!==0` ガードを外す（`:3199`, `:3223`）
- `applyArc` / `applyHairpin` を `getVoiceEvents` + `withVoiceEventsUpdated` 経由へ
- `selectedArc` / `selectedHairpin` / `cpDragRef` / `epDragRef` に `voiceIndex` を追加し、
  弧の同定を `arcIdentityMap` 経由にする（§3-1）
- 始点と終点の声部が一致しない場合は何もしない（§4）
- Delete による弧・松葉の削除も声部対応

**受入条件案**
1. 声部2アクティブで声部2の音符間をドラッグ → `voices[1]` 側に arcs が入り、**声部1の events は不変**
2. 同じ操作で松葉も声部2側に入る（§7 の方針が (a) の場合）
3. 声部2の弧をクリックで選択 → 曲率ドラッグ・端点ドラッグ・向き反転・Delete がすべて声部2側にだけ保存される
4. 声部1アクティブでの従来操作が一切変わらない（リグレッション）
5. ブラウザ確認（共有 dev サーバー）でゴールデンパスを操作し、コンソールエラーが 0 件
6. `docs/REGRESSION.md` の D 節（Safari の座標一致）を弧のドラッグについて確認

### 段4: 浄書品質（向きの既定値・障害物回避スコープ）

- 2声部小節では弧の既定の向きを声部1＝上・声部2＝下にする（§5）
- スラーの障害物回避を自声部限定にする（§6）

**受入条件案**
1. 2声部小節で、声部2に張ったスラーが既定で下向きになる（`flipDirection` は従来どおり効く）
2. 単声部の小節・声部トグルの無い譜種で向きが変わらない
3. 声部2のスラーが声部1の音符を避けようとして極端に膨らまない
4. 既存譜面の見え方が変わる範囲を設計書へ明記する

### 段5: MusicXML（松葉のみ）

- `buildHairpinPositionMaps` を全声部走査に、声部2の `<wedge>` を `<backup>` 以降へ出力（§10）
- タイ・スラーの MusicXML 対応は別Issueとして提案

**受入条件案**
1. 声部2に松葉がある譜面を書き出すと、`<backup>` の後に `<wedge>` が出る
2. 往復（書出→読込）で声部2の松葉が復元される
3. 声部2が無い譜面の出力が1バイトも変わらない

- 単旋律譜・弦楽四重奏・編成譜・パート抽出（`voices` を持たないので `isMultiVoiceMeasure` が常に false）

- 弧の形そのもの（曲率・太さ・段またぎの分割）。`computeArcGeometry` は無改修

なお、既に手動で `cpDyOffset`（曲率ドラッグ）を付けている弧が上下反転する場合、
