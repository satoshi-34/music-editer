# 記号と音符の自動衝突回避（Issue #340）

## 問題

強弱記号（pp など）・cresc./dim. の縦位置は「五線最下線から 26px 下」の固定値で、
低い音符の加線・下向きの符幹はそこまで届くため重なっていた。運用者が月光
（ベートーヴェン月光ソナタの写譜）で pp を手動で -93px 動かした実例があり、
弟インタビュー回答1（#89 → #340）の筆頭要望。

## 段階分け（Issue #340 の設計メモ 2026-08-22）

- **段1（本実装）**: 強弱記号・cresc/dim（dynamics 系）の下方向回避
- 段2: カスタム記号・運指など統一高さ帯の記号（未実装）
- 段3: スラー/タイの弧・松葉 — 「避ける」ではなく「形を変える」実装になるため
  別 Issue 化を提案

## 修正設計（段1・2026-08-22）

### 純粋関数エンジン `src/utils/symbolCollisionUtils.ts`（新規）

- `resolveBelowSymbolShifts(symbols, obstacles, options)` — 記号を x 順に処理し、
  障害物か確定済み記号の占有域に重なる間 7px ずつ下へ押し出した「追加 dy」を返す
- **手動調整（⤢/✥ の offsetX/offsetY 非0）の記号は動かさない**（Issue の原則）。
  ただし占有域には加えるので、自動配置の記号の方が手動配置を避ける
- 押し出し上限 112px（実例の 93px を上回る値）。上限まで押しても空かなければ
  元の位置に留める（半端に下がった「避けたのに重なっている」見た目を避ける）
- `estimateTextRect()` — DOM 計測なしの文字箱概算。縦は em 全体ではなく
  **字面の実コア**（ベースライン上 0.55em・下 0.2em）で見積もる。em 全体だと
  通常音域の下向き符幹の先端が 1〜2px かすめるだけで押し出しが発生し、
  譜面全体で強弱記号の高さが不揃いになるため（意味のある重なりだけを避ける）

### PianoSystemCanvas 側の配線

- 音符描画ループ（アクティブ声部＋非アクティブ声部の見た目だけ描画）で
  VexFlow の `note.getBoundingBox()`（符頭＋符幹を含む。モデル側の値なので
  DOM 計測不要＝jsdom でテスト可能）を `collectors.noteObstacles` に段
  （partIndex）付きで収集
- `dynamicTextEntries` に `obstaclePartIndex` を追加し、一括描画の直前に
  段ごとにエンジンを1回呼んで、y へ追加シフトを加算
- **自動回避の結果は保存しない**（描画のたびに計算。保存データは不変なので、
  後からロジックを改良しても既存の譜面が壊れない）

## 影響範囲

- 強弱記号・cresc/dim の描画位置のみ。クリック判定 rect は記号の描画実測（getBBox）から
  作られるため通常は自動で追従する（例外: #380 の Bravura グリフは getBBox が em 箱を
  返すため、字面のメタデータ実測値でクランプする。dynamic-marking の設計メモ追補参照）
- 手動調整済みの記号・重なりのない記号は従来位置のまま
- 保存データ・再生・書き出しは不変

## データ構造

- 保存形式の変更なし。`RenderCollectors` に描画時だけの `noteObstacles`
  （`{partIndex, x, y, w, h}` の配列）を追加

## 経緯・判断

- 障害物は同じ段の音符に限定。「同じ段」は元パートではなく**実際に描かれた五線**を指す（段またぎ音符（renderStaff）は描画先パートへ帰属。Codex round 2 P2）。下の段の音符まで見ると「押し出した先で
  下の段に食い込む」を解けず複雑化する。押し出し上限（112px）を安全弁とする
- ベースライン揃え（同じ段の強弱記号を同じ高さに揃える浄書慣習）は段1では
  行わない。重なった記号だけが個別に下がる

## 追補（2026-08-22・Codex round 1 対応）

- 手動調整済みの記号は**処理順に関係なく先に全件を占有域へ登録**してから、
  自動配置の記号だけを x 順で処理する（手動記号が x 順で後にあると、
  先に確定した自動記号が知らずに重なる取りこぼしがあった）
- 公開オプションの検証を追加（stepPx は正の有限値のみ・シフトは maxShiftPx へ clamp）
- 障害物の収集を、編集用ループ2箇所から **drawRenderedVoiceEntries 直後の1箇所**
  （描画した全声部の全音符）へ集約。レイヤー明示選択中の非選択パートの
  アクティブ声部が漏れていたため。あわせて、同じ穴で非選択パートの記号自体が
  描画されない #316 の表示退行を発見・修正した（editor-layer-selection/design.md の
  追補を参照）

## 追補2（2026-08-23・運用者裁定: 五線間クランプと「境界停止・部分重なり許容」への原則変更）

月光 m5 の実測（右手の深い三連符 + 声部2の pp）で、押し出しが三連符を抜けるまで下がり
**左手五線の上端あたり**へ達する事例が出た。エンジンは「押した先に次の五線がある」ことを
知らず（障害物は音符のみ・五線線は対象外）、大譜表では自パートの下＝隣の五線のため
構造的に起きる。

**裁定（2026-08-23）**:
- **案B（採用・#382 で実装）**: 押し出しは「下の五線の上端の手前（マージン付き）」で停止する。
  境界まで押しても重なりが残る場合は、**元位置へ戻さず境界位置に留める**（部分重なり許容）。
  市販譜の「ピアノの強弱は五線間に収める」慣習に合わせた変更で、重なりが残るケースは
  パート間隔を広げれば解消される（市販譜が五線間隔を広く取るのと同じ関係）
- **案C（別Issue #383・保存形式の裁定待ち）**: メロディ声部の強弱を五線の**上**へ置く配置先
  選択。テスト会後に裁定
- **案D（検討除外・承認済み）**: 符幹の向きによる自動分岐。声部1=上向き・声部2=下向きの
  固定規則の下では、メロディを声部2で書く実運用と逆に働くため不採用

**原則変更の記録**: 本文の「maxShift まで押しても空かなければ**元の位置に戻す**
（半端に下がった位置は紛らわしい）」は、次の五線という明確な境界がある場合に限り
**「境界に留める」へ置き換える**（境界が無い最下段は従来どおり元位置へ戻す）。
「避けたのに重なっている」見た目より「隣の五線へ入る」方が読譜上の害が大きい、
という月光実測に基づく判断。検証は運用者が月光 m5 実機で行う（#382 参照）。
## 実装（2026-08-23・#382 五線間クランプ）

追補2の裁定（案B）を実装した。

### エンジン `resolveBelowSymbolShifts` のオプション `maxBottomY`

- 意味は「記号 rect の**下端**がここを超える押し出しはしない」。未指定（`undefined`・NaN）なら
  境界なしで、**従来と完全に同じ挙動**（`maxShiftPx` だけが上限で、上限まで押しても空かなければ元位置へ戻す）
- 記号ごとに `boundaryShift = maxBottomY -（rect の下端）` を求め、`maxShift` と小さい方を
  その記号の押し出し上限にする。既に境界より下にいる記号は上限0（上へは戻さない）
- **境界の側で止めたときだけ**、重なりが残っていても元位置へ戻さず境界位置で確定する
  （`stopsAtBoundary = boundaryShift < maxShift`）。`maxShift` の側で止まった場合は従来どおり元位置へ戻す
- 境界の余白は `BELOW_SYMBOL_STAVE_BOUNDARY_MARGIN_PX = 3`（五線の第1線にぴったり接しない程度）

### PianoSystemCanvas 側の配線

- `RenderCollectors` に `staveTopYByPart: Map<number, number>` を追加し、Stave 生成直後に
  `stave.getYForLine(0)` を段ごとに記録する
- 一括描画前の衝突計算で、段 `pi` の記号へ `maxBottomY = staveTopYByPart.get(pi + 1) - マージン` を渡す。
  最下段（`pi + 1` が無い）は `undefined`＝境界なし
- **`staveYs[pi + 1]` をそのまま境界に使わない理由**: VexFlow の `Stave` は渡した y の
  4スペース下（`spaceAboveStaffLn` 既定4 × 10px = 40px）から線を引く。`staveYs` は
  「五線の上端」ではないため、そのまま境界にすると五線1つぶん高く見積もってしまい、
  ピアノ既定（間隔80px）では強弱記号の基準位置（五線最下線+26px）が**最初から境界より下**になり、
  押し出しが常に0になってしまう。実測に基づき、実際に描いた Stave から上端を取る方式にした
  （Issue 本文の実装ポイントからの意図的な変更点）

### 実測値（ピアノ既定・scale=1・vitest）

| | 上段(右手)の五線上端 | 下段(左手)の五線上端 | pp の字面下端 |
|---|---|---|---|
| 修正前 | 60 | 140 | **166.7**（左手の五線の中） |
| 修正後 | 60 | 140 | **137.0**（= 140 − マージン3） |

同じ音形を単旋律（下に五線が無い）で描くと修正後も 166.7 のままで、最下段の挙動は変わらない。

### テスト

- 単体: `src/utils/symbolCollisionUtils.test.ts` の
  「resolveBelowSymbolShifts の maxBottomY」— 未指定時の従来挙動・境界停止・境界でも重なる場合に
  元位置へ戻らないこと・maxShift の側で止まった場合は従来どおり戻すこと・既に境界より下なら動かさないこと
- 統合: `src/components/PianoSystemCanvasDynamicsCollision.test.tsx` の
  「押し出しの五線間クランプ（Issue #382）」— 大譜表で境界手前に留まること／同じ音形の単旋律では
  境界を越えて押し出されること（クランプが効いている証拠）／最下段の押し出し量が単旋律と一致すること。
  `maxBottomY` を一時的に外すと前2件が落ちることを確認済み（負のテスト）

### 影響範囲

- 変わるのは「下に五線がある段」の強弱記号の押し出し量だけ。最下段・単旋律・手動調整済みの記号は不変
- 保存形式・クリック判定・⤢/✥・再生・書き出しは不変（押し出しは描画のたびの計算で保存しない）
- ユーザー向けの説明（重なりが残るときはパート間隔を広げる）は README の「強弱記号」節に追記した
