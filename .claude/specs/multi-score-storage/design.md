# 設計書: 複数作品の保存管理（作品一覧・作品別自動保存・復元履歴）

> 対応 Issue: [#109](https://github.com/satoshi-34/music-editer/issues/109)
> 本書は #109 のトリアージコメント（2026-07-28, @satoshi-34）が要求する「実装着手前の設計メモ」であり、
> 段階的な PR 分割の計画を兼ねる。まだコードは変更していない（着手前の計画段階）。

## 前提として踏まえたこと

- [`save-load-redesign`](../save-load-redesign/design.md) の設計により、現在は「手動保存スロット」
  （`music-score-app-data` / `-backup` / `-meta`）と「自動保存スロット」（`music-score-app-autosave` /
  `-backup` / `-meta`）の**2スロット構成**になっている。どちらも `src/utils/storage.ts` の
  `saveScoreDataToSlot` / `loadScoreDataFromSlot` という共通処理を `StorageSlotKeys`（primary/backup/
  metadata の3キー1組）経由で使っており、直前の1世代だけ `backup` キーへ退避する。
- 起動時（`ScorePage.tsx`）は `migrateLegacyDataToAutosave()` → `loadAutosave()` → 復元、という
  順で「前回の続きをサイレント復元」する。**この挙動は #109 のコメント（2026-07-29, 運用者判断）で
  維持することが確定している**ので変更しない。
- Issue 本文で運用者が指摘している「保存／読込」と「ファイル保存／ファイルを開く」の呼び分けの
  分かりにくさも対象（本設計の第4段）。
- 保存データの型（`SavedScoreData`）自体は本設計では変更しない。作品単位の管理はあくまで
  「どのキーに、どの `SavedScoreData` を保存するか」という**スロット管理層**の拡張であり、
  楽譜データ自体のスキーマ変更ではない。

## 現状のスロット方式の限界

現在の実装は「スロットは手動用・自動保存用の2つで固定、それぞれ現在世代+直前世代の2世代のみ」
という設計になっている。これは元々「1曲だけを編集する」ことを前提にしており、以下は原理的に
対応できない：

- 複数の作品を同時に保持できない（スロットのキー名が固定文字列のため）
- 復元できる世代が「直前の1つ」だけ（数世代の履歴を持つには世代数だけキーを増やす必要がある）
- 作品ごとの一覧・削除という概念が無い（キーが直書きの定数のため列挙できない）

## 新設計

### データモデル: 作品（Work）という単位の導入

```ts
interface WorkSummary {
  id: string;            // 作品ID（crypto.randomUUID()）。localStorage キーの一部にも使う
  title: string;          // 一覧表示用。SavedScoreData.metadata.title のコピー（空なら「無題」）
  updatedAt: number;       // 最終更新時刻（一覧のソートに使う）
  createdAt: number;
}

interface WorkIndex {
  version: string;         // WorkIndex 自体のバージョン（将来のマイグレーション用）
  works: WorkSummary[];
  lastOpenedWorkId: string | null; // 起動時に「前回の続き」を復元する対象
}
```

- `WorkIndex` は単一の localStorage キー（例: `music-score-app-work-index`）に保存する軽量な
  カタログ。実際の譜面データ（`SavedScoreData`、大きい）はここには持たない。
- 各作品の実データは、作品ID を含むキー名のスロットに保存する（下記）。

### 保存領域（localStorage キー構成案）

```
カタログ（新設・1件のみ）
  music-score-app-work-index          … WorkIndex（作品一覧・最終オープン作品ID）

作品ごとの自動保存スロット（作品IDを含むキー名、作品の数だけ存在する）
  music-score-app-work-{id}-autosave         … 現在の自動保存内容
  music-score-app-work-{id}-autosave-meta    … チェックサム・バージョン・保存時刻
  music-score-app-work-{id}-history          … 復元履歴（下記、数世代ぶんの配列を1キーにまとめる）

手動保存スロット（従来のグローバル1本のキーを維持するか、作品ごとに分けるかは第2段で決定）
  music-score-app-data / -backup / -meta     … 当面は現行のまま据え置く（後述）
```

**世代バックアップの持ち方を変更する**: 現行は「primary 1本 + backup 1本」で直前世代のみ。
複数世代（例: 5世代）を保持するため、`-backup` 単体キーではなく `-history` キー1本に
「新しい順の配列（各要素は `{ timestamp, checksum, data: SavedScoreData }`）」を JSON でまとめて
持たせる方式へ変更する。理由: 世代ごとに個別キー（`-history-0`, `-history-1`, ...）にすると
「何世代目まで実在するか」を毎回列挙する必要が生じ、削除・ローテーションのロジックが複雑になる。
配列1本ならローテーション（先頭に追加して末尾を捨てる）が単純。ただし1キーのデータサイズが
大きくなる点はトレードオフとして残る（後述の容量見積もりを参照）。

### 作品IDをキーに含める設計にする理由（列挙可能性）

localStorage には「指定した prefix を持つキーを列挙する」API が無い。作品を作品IDから
逆引きできれば十分なので、`WorkIndex.works` が「実在する作品IDの一覧」の正本になる。
削除操作は「`WorkIndex.works` から該当エントリを消す」+「対応するキー群を `removeItem`」の
2手順を必ずセットで行う（片方だけ実行されると、参照が残ったゴミキーか、キーはあるのに
一覧に出ない孤児データのどちらかが発生するため、この2手順は同じ関数内で行い、
`WorkIndex` の更新を先に試みて失敗したら実データの削除も行わない）。

### 起動時の復元フロー（変更点は最小限に）

```
起動（ScorePage マウント）
  │
  ├─ migrateLegacyDataToAutosave()（第1段。既存の単一作品データを WorkIndex 配下の
  │    最初の作品（idを新規発行）として1回だけ移行。詳細は「移行」節）
  │
  ├─ WorkIndex を読む → lastOpenedWorkId を得る
  ├─ その作品の自動保存スロットを loadAutosave(workId) で読み込み → 画面へ復元
  │    （ここまでの「前回の続きを開く」という体験は現状から変えない）
  │
  └─ setAutosaveRestoreReady(true)
```

編集中の自動保存も「現在開いている作品の workId」に対して書き込むだけで、デバウンス・
空判定（`isEmptyScoreData`）などのロジックは現行のまま流用する。

### 作品一覧UI

- 一覧には `title`・`updatedAt` を表示し、選ぶとその作品の自動保存スロットを読み込んで画面を
  差し替える（＝ `lastOpenedWorkId` を切り替える）。
- 削除には確認ダイアログを挟む（Issue 受入条件）。削除は「取り消せない」操作であるため、
  ブラウザの `confirm()` ではなく既存の確認ダイアログ実装（`handleNewScore` が使っているものが
  あればそれに合わせる）を再利用する。
- 「新規作成」は新しい作品ID を発行して空譜面から始める（既存の `handleNewScore` の空譜面初期化
  ロジックはそのまま使い、保存対象の workId だけ新規にする）。

### 復元履歴（数世代）UI

- 各作品の詳細（または一覧の行アクション）から「復元履歴を開く」→ 世代（timestamp表示）を
  選んで「この時点に戻す」を選べるようにする。
- 「戻す」は現在の自動保存内容を上書きする前に、現在の内容も履歴の先頭へ積む（＝「戻す」操作
  自体も1世代として記録されるため、誤って古い世代に戻しても「戻す前」に再度戻せる）。

### 手動保存スロット（「ファイル保存／ファイルを開く」への呼び分け）

Issue 本文が指摘する「保存／読込」と「ファイル保存／ファイルを開く」の混同について：

- ブラウザ内保存（作品一覧・自動保存・復元履歴）は「作品として保存」「作品を開く」に文言統一。
- 現行の「保存」「読込」ボタン（`localStorage` の手動スロットへの保存で、実体はファイル入出力
  ではない）は、本設計の作品一覧機能と役割が重複する。役割が重複したまま両方残すと再び
  分かりにくくなるため、**この手動スロットは作品一覧機能のリリースと同時に廃止し、
  「ファイルへ書き出す」「ファイルから読み込む」（＝ JSON ファイルの export/import。
  実装があれば流用、無ければ最小限で新設）に一本化する**案を第4段で扱う。
  廃止時は、既存の手動保存スロットにデータが残っているユーザー向けに、廃止前の最後の移行
  （そのデータを作品として取り込む導線）を用意する。

### 保存先: localStorage のまま or IndexedDB への移行

Issue 本文で「作品数が増えると容量上限（一般に5MB前後）に当たる可能性があるため IndexedDB
移行を検討する」よう指示されている。設計メモの時点での判断:

- 現行の `SavedScoreData` は JSON 直列化されて保存される。音符イベント1件はキー・持続時間・
  各種装飾（強弱・アーティキュレーション・タイ・微分音など、すべて省略可能）を持つオブジェクトで、
  実測はしていないが目安として「4分音符主体・装飾少なめの1ページ程度の譜面」で数十KB、
  「フル編成・装飾記号を多用した長い譜面」では数百KB〜1MB程度に達しうると見込まれる
  （実測はこの Issue の実装段階で行い、PR に想定作品数×1作品あたりサイズの実測値を書くこと、
  という Issue の受入条件に従う）。
- 複数世代の履歴（例5世代）を持つと、1作品あたりの合計サイズは単純計算で「現在世代+履歴5世代」
  ＝おおよそ現在世代の6倍に達する。作品数が10〜20を超えるあたりで、localStorage の一般的な
  上限（ブラウザにより5〜10MB）に近づくシナリオは現実的にありうる。
- 一方で IndexedDB への移行は非同期API化・トランザクション設計・エラーハンドリングの作り直しが
  必要で、影響範囲が `storage.ts` 全体・呼び出し側フック（`useScoreStorage.ts`）・テストに及ぶ
  大きな変更になる。

**結論（設計方針）**: 本 Issue のスコープでは、まず**localStorage のままカタログ構造
（WorkIndex + 作品別キー）を実装**し、実装時に実測したサイズを PR に記録する。実測の結果、
想定作品数（例: 20作品×5世代）で容量上限に近い、または既にユーザーから容量エラーの報告がある
場合にのみ、**別Issueとして IndexedDB 移行を切り出す**（本 Issue の第5段では「移行が必要かの
判定と、必要なら移行計画をIssueに切り出すところまで」を担当範囲とし、移行の実装そのものは
含めない）。理由: データ移行を伴う大きな変更を、容量が実際に問題になるかどうか分からないまま
同じ PR に混ぜると、レビュー・検証の負担が上がり、本 Issue の主目的（作品を複数持てるように
すること）の検証を妨げる。

### 移行（既存ユーザーの保存データを失わないこと）

Issue の受入条件「既存ユーザーの保存データが失われない」を満たすための移行ロジック：

- `migrateLegacyDataToWorks()`（既存の `migrateLegacyDataToAutosave` と同じ「移行マーカーを見て
  1回だけ実行」パターンを踏襲。マーカーキー: `music-score-app-work-migrated`）
- `WorkIndex` が存在しない（＝初回）場合のみ実行する。
- 現行の自動保存スロット（`music-score-app-autosave` 系）にデータがあれば、新しい作品ID を
  1つ発行し、その内容を最初の作品として `WorkIndex` に登録する。
- 現行の手動保存スロット（`music-score-app-data` 系）は、上記と同じ作品に統合するのではなく
  独立した扱いとする（自動保存と手動保存が別内容である可能性があるため、安易にマージしない）。
  第4段で手動スロットを廃止するタイミングで、この手動保存データも「もう1つの作品」として
  取り込む導線を用意する（詳細は第4段のPRで設計する）。
- **回帰テスト**: 「旧形式（単一の自動保存キー）のデータがある状態で起動 → 作品一覧に1件だけ
  現れる → その作品を開くと旧データがそのまま復元される」をテストとして必ず追加する
  （Issue 受入条件）。

### 追加したキー（`src/utils/storage.ts` の `STORAGE_KEYS`）

| キー | 用途 |
| --- | --- |
| `music-score-app-work-index` | 作品カタログ（`WorkIndex`）1件 |

### 実装時に決めたこと（本書の計画に対する補足）

- **作品IDは `[A-Za-z0-9_-]{1,64}` に制限する**。作品IDはそのまま localStorage の
  キー名へ埋め込まれるため、壊れたカタログや手編集データに `../music-score-app-data` の
  ような文字列が入っていても、既存スロットを読み書きしてしまわないようにする。
  範囲外のIDは読み書き・削除とも失敗を返す。
- **壊れたカタログは「要素単位」で落とす**。譜面データ（`validateSavedScoreData`）は
  「1つでも壊れていたら全体を捨てる」方針だが、カタログで同じことをすると、実データが
  残っているのに一覧から消える作品（孤児データ）が大量に生まれる。カタログの各要素は
  互いに独立しているので、壊れた要素と重複IDだけを落として残りを保つ。
  カタログのJSON自体が壊れている場合のみ空カタログとして扱う。
- **`lastOpenedWorkId` は実在確認つき**。カタログに無い作品IDは `setLastOpenedWorkId()` で
  受け付けず、読み込み時に実在しないIDを指していたら `null` に落とす（次回起動で
  「開けない作品」を指したままになるのを防ぐ）。
- **`saveWorkAutosaveData()` は未登録IDを自己修復登録する**。実データはあるのに一覧に
  出ない孤児データを作らないため。カタログ更新に失敗しても、譜面データ自体は書けている
  ので保存は成功扱いにする（失敗を返すと呼び出し側が二重保存を試みるため）。
- **`deleteWork()` はカタログ更新 → 実データ削除の順を必ず守る**（本書の方針どおり）。
  逆順だと、実データだけ消えて一覧に残る「開くと空の幽霊エントリ」が生まれる。
  この順序なら、途中で失敗しても最悪「一覧に出ないゴミキー」が残るだけで済む。
- **移行は旧キーを消さない**。`migrateLegacyDataToWorks()` は旧自動保存スロットの生の
  文字列をそのまま新スロットへコピーするだけで、削除も正規化もしない。万一移行に
  バグがあっても、旧キーを読む従来の起動時復元がそのまま動き続けるため、譜面を失わない。
  すでにカタログがある場合（初回ではない場合）は移行せずマーカーだけ立てる。
  手動保存スロットは本書どおり取り込まない（第4段で扱う）。

### 自動保存の保存先

自動保存の書き込み先を、固定キーの自動保存スロットから
**「いま開いている作品」の自動保存スロット**へ変えた（`saveWorkAutosaveData`）。
デバウンス（1.5秒）・空譜面は保存しない判定（`isEmptyScoreData`）は従来のまま。

- 移行後は旧キー（`music-score-app-autosave` 系）へは**書かなくなる**。旧キーは
  移行時に消していないので、万一の切り戻し時も移行時点の譜面までは残る
  （移行後に編集した内容は作品側にしかない）。
- 作品を切り替える直前・新規作成の直前には、**保存待ちのデバウンスタイマーを取り消してから**
  現在の内容を保存する（`cancelPendingAutosave`）。取り消さないと、切替後にタイマーが発火して
  1つ前の作品の内容を切替先の作品へ書き込んでしまう（「作品Aの編集で作品Bが壊れる」経路）。

### 「新規作成」の意味の変更

これまでの「新規作成」は自動保存スロットを**消して**空譜面に戻していたが、
作品ごとに保存先が分かれたため、**いまの内容を保存してから新しい作品IDへ移る**動きに変えた。
これまでの譜面は作品一覧に残り、いつでも開き直せる（確認ダイアログの文言もそれに合わせた）。
手動保存スロット（「保存」「読込」）には従来どおり触れない（廃止は第4段）。

### 実装時に決めたこと

- **`applyLoadedScoreData()` の切り出し**: 「読み込んだ譜面を画面へ反映する」処理は、
  起動時復元と作品切替で完全に同じでなければならない（片方だけ更新し忘れると
  「切り替えたのに前の譜面の設定が残る」不具合になる）。復元 useEffect の中身を
  そのまま関数に切り出し、両方から呼ぶようにした。手動「読込」・ファイル読込の
  同種の処理は、今回のスコープ外なので触っていない（第4段で整理する）。
- **`currentWorkId` は ref を正本にする**: 自動保存はデバウンス後に走るため、
  state だけで持つと切替直後の保存が1つ前の作品IDを読むことがある。取り違えは
  他の作品への上書きになるので、常に最新値を読める ref を正本にし、state は表示用の写しにした。

## 第3段の実装記録（Issue #109・2026-08-22）

復元履歴（数世代）を実装した。設計本文 §復元履歴 のとおり、作品一覧の行アクション
「履歴」から世代（日時表示）を選んで「この時点に戻す」を選べる。

### 実装で決めたこと（本書の計画への補足）

- **世代化の間隔**: 自動保存は約1.5秒デバウンスのため、毎回積むと数秒違いの世代で埋まる。
  最新世代から **10分以上**（WORK_HISTORY_MIN_INTERVAL_MS）空いた保存だけを世代化し、
  上限 **5世代**（WORK_HISTORY_MAX_GENERATIONS）で古い順に落とす。
  直前1世代の -backup（毎回退避）は従来どおり残してあり、役割が異なる
  （backup=書き込み事故対策、history=編集の巻き戻し）
- **「戻す」は必ず現在を force で1世代積んでから**上書きする（設計どおり。誤復元しても
  「戻す前」へ再度戻せる。確認ダイアログの文言でもその旨を伝える）
- **容量あふれ**: 書けるまで古い世代を1つずつ落として縮めて再試行する（最後は新しい
  1世代だけでも残す）。それでも書けなければ失敗を返す。自動保存経路ではこの失敗を
  無視して編集を止めず、復元経路（退避）では失敗＝復元中止の判断に使う
- 壊れた世代（検証に落ちる JSON）は loadWorkHistory が黙って除く
- ScorePage 側は復元時に cancelPendingAutosave を先に呼ぶ（保存待ちタイマーが残っていると
  復元した内容が編集中の内容で上書きされて元の木阿弥になるため）

### 検証

- storage: 間隔スロットリング/force/上限/戻す往復（現在が積まれる）/異常系 3テスト
- WorkListPanel: 世代一覧の開閉・空表示・確認ダイアログ経由の復元 2テスト
- ブラウザ実機: 履歴を開く→「この時点に戻す」→通知+譜面反映まで確認
