# クリックした拍まで休符を埋めて配置する（Issue #322）

## 問題

空の声部（またはまだ途中までしか埋まっていない声部）で小節の途中をクリックして音符を置くと、
**クリックした拍ではなく声部の末尾（空なら小節頭）に入る**。

実例（運用者が月光 m10 の実書きで踏んだ・2026-08-20）:
声部1が満杯の小節で声部2を選び、「2拍目」のつもりで3連符を配置 → 空の声部2の**1拍目**に入り、
利用者には「1個目の三連符の位置に入った」ように見えた。

### 原因

`PianoSystemCanvas.tsx` の `doInsert()` が決める挿入位置 `at` は、
**アクティブ声部の描画済み音符（`activeVfNotes`）のどれにクリックXが近いか**という相対計算だけで決まる。

- 既存音符が無い声部では比較対象が無く、`at` は常に 0（先頭）になる
- クリックXが持つ「小節内の何拍目か」という意味は、どこにも使われていなかった

補完（`fillPriorMeasureRests`）は**それ以前の小節**専用で、編集中の小節の中の空き拍は対象外である。

## 修正設計

### 1. 拍の物差し = 合同フォーマットの列

複数パート・複数声部は1回の VexFlow Formatter でまとめて整形している（合同フォーマット）ため、
**同じ開始拍の音符は声部・パートをまたいで同じ X に並ぶ**。
この性質を使えば、音符が1つも無い声部でも「クリックXは何拍目か」を他の声部・パートから逆引きできる。

描画時に `beatColumnsByMeasureP: Map<小節番号, BeatColumn[]>` を作る（`BeatColumn = { beats, x }`）。

- 積むのは `renderedVoiceEntries`（＝全パート・全声部の描画エントリ）の `sourceEvents` と `vfNotes`
- **表示専用のパディング休符（`__isPlaceholder`）も含める**。利用者が「3拍目」と思ってクリックするのは
  画面に見えているその休符の位置であり、実データの音符だけを基準にすると狙いより手前に寄ってしまう
  （`notePositionMapP` がパディングを除外しているのは弧の障害物計算のためで、目的が違う）
- 台帳は描画のたびに作り直す。`doInsert` はクリック時（＝全パートの描画が終わったあと）に読むので、
  自分より後ろのパートの列もそろっている

### 2. 埋める拍数の判定（`src/utils/beatColumnUtils.ts`）

純粋関数として切り出し、単体テストで固定した。

| 関数 | 役割 |
| --- | --- |
| `buildBeatColumns(events, resolveX)` | 1声部のイベント列 → 「開始拍→X」の列一覧。X が取れないイベントは列にしないが、開始拍の積算は続ける |
| `resolveBeatAtX(columns, x)` | クリックXに**最も近い列**の開始拍。参照が無ければ `null` |
| `planLeadingRestFillBeats({...})` | 埋める拍数。0 なら従来どおり |

`planLeadingRestFillBeats` が 0 を返す（＝従来の挙動のまま）条件:

- 拍の基準になる列が1つも無い（その小節がどのパートも空）
- クリックした拍が、その声部の既に埋まっている拍より手前（`gap <= 0`）
- 埋めたうえで置くと小節の拍数を超える
- 空く拍が通常の休符でぴったり表せない（3連符の途中の 1/3 拍など）。
  中途半端に埋めると小節の拍が合わなくなるため、**埋めないほうを選ぶ**

「最も近い列」で決めるのは、利用者が狙うのが拍の境界ではなく画面に並んでいる**音符の列**だからである
（MuseScore / Finale と同じ感覚）。

### 3. 適用範囲（回帰面を最小にする）

`doInsert` の中で `buildLeadingRests()` が働くのは、**挿入位置がアクティブ声部の末尾のとき**
（`at >= currentVoiceEvents.length` ＝ クリックが既存の最後の音符より右）だけ。
既存音符の近くをクリックしたときの挿入位置・連符境界へのスナップ（#282）は1pxも変えていない。

通常の音価ツールと**連符ツールの両方**に同じ関数を通す（受入条件どおり）。

### 4. 埋める休符の高さ

`buildTrailingRestEventsForBeats`（`voiceMeasureUtils.ts`）に
`standardRestDisplayKey(clef, dur, voiceIndex, voiceCountAfterInsert)` を渡して作る。
これは画面に見えている補完休符（`computeVoiceDisplayPadding`）とまったく同じ規約なので、
「見えていた休符が、実データになった途端に別の高さへ動く」ことがない（Issue #227 の規約を共有）。

声部数は**挿入後**の数で数える。声部2への初回入力では `voices[1]` がまだ無く、
現在の小節だけを見ると単声部と数えて声部1の休符と重なってしまうため。

### 5. 通知（Issue #318「行き止まりは喋る」との整合）

拍を埋めたときだけ `notifyScoreEdit(describeLeadingRestFill(...))` を出す。
文言は「2拍目に置き、手前の空いた拍を休符で埋めました（Cmd/Ctrl+Z で元に戻せます）」で、
多声の小節では「声部2の」を頭に付ける。

音符だけでなく**休符も一緒に増える**操作なので、無言で行うと
「置いたつもりの拍」と「実際に入った拍」のずれに気づけない（空の声部では特にそうで、
1拍目に入っても譜面としては不自然に見えない）。1操作＝1 Undo なのは従来どおり。

### 既存テストの期待値を変えたもの

どちらも**本Issueが意図的に変える挙動**を固定していたテストで、
「小節の中ほどをクリックしたのに声部の先頭へ入る」という、まさに直した症状を前提にしていた。

- `PianoSystemCanvasVoiceClickScope.test.tsx`
  「声部2未入力の小節で背景クリック → 声部2に**1件**追加」→
  件数ではなく「音符はちょうど1つ・それが末尾・手前は休符だけ」で固定する形へ変更
  （このテストの本来の主旨＝声部1へ誤って書き込まない、は変えていない）
- `PianoSystemCanvasVoice2Tuplet.test.tsx`
  連符グループの検証対象を「先頭3件」から「末尾3件」へ変更。グループの中身（同一 id・比率・音価）の検証は同じ

## 未対応（意図的に外したもの）

- **単旋律譜（`StaffCanvas.tsx`）**: 本Issueの受入条件は多段譜側の症状で、
  単旋律譜は他パートの列が存在しないため拍の物差しが作れない（唯一の基準は自分の声部の音符列）。
  必要になったら「表示用パディング休符の列」を同じ台帳の形で作れば同じ仕組みが載る
- **3連符の途中の拍への配置**: 通常の休符で表せないため今回は従来動作のまま。
  連符内休符での埋め合わせは、連符グループの一貫性（#282）と合わせて別途設計が要る
