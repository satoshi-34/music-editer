# 編集レイヤー明示選択（Issue #316）設計メモ

作成: 2026-08-22（実装と同時。実装承認は運用者の包括指示「一旦全部実装終わらせてくれる」）。
背景・経緯の正本は Issue #316。ここでは裁定と実装の形を記録する。

## 1. 決定済み（運用者裁定 2026-08-19・Issue 記載）

- レイヤーの単位 = 手×声部の4レイヤー（右手・声部1 / 右手・声部2 / 左手・声部1 / 左手・声部2）
- 現在の声部セレクタを置き換える統合セレクタ
- 音符クリックでそのレイヤーへ自動切替+通知（#258 の型）

## 2. 未決だった論点の裁定（2026-08-22・レビュアー推しを採用して実装）

- **② 選択レイヤーと違う五線の空白クリック = 案B（帯域優先）**:
  クリックした帯のパートへ入れ、声部はセレクタ（レイヤーの声部側）に従う。
  案A（選択レイヤーのパートへ入れる）は「意図しないパートに大量の加線音」事故が
  通知だけでは追い切れない恐れがあるため。**弟のハンズオンの感想で差し替え可能**:
  帰属の入口は resolveHitAttribution（#244 段3c）に一本化されているので、
  案Aへの変更は挿入時の帰属ポリシー1点の差し替えで済む
- **③ 既定 = 案A（常に明示。既定レイヤーは右手・声部1）**:
  ②が案Bなので、空白は帯域・音符クリックは自動切替となり、常時明示でも
  従来の手軽さをほぼ失わない（Issue 記載のレビュアー分析どおり）
- **付随裁定: 帯またぎ挿入時のレイヤー自動追従**: 空白クリックで選択レイヤーと違う
  パートへ挿入した場合、入れた先へレイヤーを自動切替して必ず通知する。
  こうしないと「置いた音符がすぐには編集できない（選択専用になる）」ちぐはぐが起きる

## 3. 実装の形（2026-08-22）

- **状態**: ScorePage に activeLayerPart（0|1）を追加。レイヤー = (activeLayerPart, activeVoice)。
  ピアノ譜のみ4ボタンの統合セレクタを表示（他の譜種は従来どおり＝レイヤー概念なし）
- **PSC**: 新 prop activeLayerPartIndex（省略時は従来の帯域推測のみ＝完全後方互換）。
  指定時、選択レイヤーのパート以外では編集用セル（.vf-note-hit）を作らず、
  全声部の音符が選択専用ヒット（#258 の機構を条件拡張）になる。クリックで
  requestActiveVoiceChange(voice, part)（イベント detail を partIndex 付きに拡張）
- **通知**: describeActiveLayerSwitched(partLabel, voiceIndex)。同一パート内の声部切替は
  従来の describeActiveVoiceSwitched のまま
- **単声部譜種・従来呼び出しへの影響ゼロ**: activeLayerPartIndex 未指定の経路は
  1行も挙動が変わらない（テストで固定）

## 追補（2026-08-22・#340 段1 レビューで発覚した表示退行の修正）

レイヤー明示選択（ピアノ譜は常に明示選択）中、**非選択パートのアクティブ声部に
付いた強弱記号・カスタム記号・ペダル・オッターバ等が描画されない**退行があった。
記号の描画予定は「編集用ループ（アクティブレイヤーのアクティブ声部）」と
「見た目だけループ（isMultiVoiceMeasure かつ非アクティブ声部）」の2箇所から
積んでいたが、非選択パートのアクティブ声部はどちらの条件にも入らなかった
（単声部小節で声部2選択中の声部1も同じ穴）。

修正: 見た目だけループの対象を**編集用ループの補集合**
（`!(isActiveLayerPart && entry.voiceIndex === activeVoiceIndex)`）へ変更し、
描かれる記号の集合が常に全エントリを覆うようにした。回帰テストは
`PianoSystemCanvasDynamicsCollision.test.tsx`（レイヤー選択中でも非選択パートの
音符・記号が扱われるケース）。修正は PR #373（#340 段1）に同梱。

## 追補2（2026-08-23・裁定②を案Aへ差し替え）

§2 の裁定②（空白クリック=案B・帯域優先）と付随裁定（帯またぎ挿入時のレイヤー自動追従）を、
**案A（空白クリックは常に選択レイヤーのパートへ入れる・レイヤーは変わらない）**へ差し替えた。
§5 に書いた「弟ハンズオンの感想で差し替え可能」の見直しが、弟より先に運用者の実使用で発動した形。

**運用者裁定の根拠（2026-08-23）:**
1. 月光 m5 の1個目の三連符入力で実際に引っかかった（明示選択が壊れる）
2. 片手が帯域を外れるのはピアノ曲では常態（手の交差・月光型の低い右手）
3. Finale も「選択レイヤー絶対」方式（左下のレイヤー選択・クリック位置で変わらない）で、
   弟のメンタルモデルもこれ

弟テスト会で「引っかかりの逆流」（案Bで防いでいた、選択忘れによる反対の手への加線音事故）が

入れずに通知）を次の候補にする。

**実装の形:**
- 差し替え点は resolveHitAttribution ではなく ir（小節背景）ハンドラ→doInsert の委譲
  （音符クリックの自動切替＝裁定①は運用者の当初裁定どおり維持するため、変えるのは
  空白クリックの挿入だけ。doInsertByPart 配列で選択レイヤーのパートの doInsert を呼ぶ）
- **音高は選択レイヤーのパートの五線を物差しに計算される**（左手の帯の高さをクリックした
  右手の音は、右手五線の下の加線として入る＝月光のユースケースがそのまま通る）
- 旧 notifyLayerAutoSwitchOnInsert（自動切替+通知）は notifyCrossBandInsert（通知のみ・
  describeCrossBandInsert）へ置き換え。requestScoreSelectionClear の呼び出しも不要になった
  （レイヤーが変わらないので選択を手放す理由がない）
- 後方互換: activeLayerPartIndex 未指定（非ピアノ・従来呼び出し）は従来どおり帯域のパートへ
  入る（テストで固定）

## 一般化と声部の追加（Issue #417・2026-09-03）

#316 の「手×声部の4枚固定・ピアノ譜だけ」を、**譜種に依らないレイヤーモデル**へ広げた。
データモデルと描画は #244 段5 で既に N 声対応済みで（`nVoiceSupport.test.ts` /
`PianoSystemCanvasNVoiceRender.test.tsx`）、蓋をしていたのは編集UI側だけだった。

### 1. 決定（Issue 本文の UI 案 + 運用者の着手承認コメント 2026-09-02）

- レイヤー = 編集対象パート × 声部。**上限は 4声/段**（VexFlow の実用上限・Finale と同じ）
- レイヤーチップ列の末尾に**「＋」**を置き、声部を1つ足す
- **減らす専用UIは作らない**（片方向）。末尾の空声部は既存の自動掃除（#305・
  `collapseEmptyTrailingVoices`）で消える
- `V` キーはトグル → **巡回**（声部1→2→…→n→声部1）

### 2. パート軸の扱い（本実装での形）

ピアノ譜だけが「右手・左手」を**画面に出しっぱなしのパート軸**として持つ（#316 のまま）。
単旋律・四重奏・編成譜は、どのパートを編集するかを**クリックした五線**で空間的に選ぶ
従来の操作を変えず、チップ列には**声部だけ**を出す。

これは Issue 本文の「編成譜はチップの組み合わせ爆発（8パート×2声=16枚）を避け、
『クリックした五線がアクティブパート＋声部チップのみ表示』とする」という方針そのもので、
実装上は **`activeLayerPartIndex` を非ピアノ譜へ渡さない**（＝#316 の後方互換の経路をそのまま使う）
ことで満たされる。パート帰属の判定を1行も変えずに済むため、四重奏・編成譜の既存の
入力挙動に対する回帰リスクが無い。

### 3. 実装の形

- **新規 `src/utils/editorLayers.ts`**: レイヤーモデルの正本。
  `MAX_VOICES_PER_LAYER`(=4) / `layerPartCount` / `layerPartLabel` / `layerChipLabel` /
  `countUsedVoices` / `resolveVoiceSlotCount` / `buildLayerChips` / `cycleVoiceIndex` / `canAddVoice`。
  ラベルは既存の `pianoLayerLabel`（#316）を経由し、表記の正本を二重に持たない
- **最初に出す声部数**（`initialVoiceCount`）: ピアノ譜は **2**、それ以外は **1**。
  ピアノ譜を1声から始めると #316 以来の「手×声部1/2 の4枚」が消え、下声を書くたびに
  「＋」を押させることになる（2声はピアノ入力の基本機能で、既存の操作を一段深くしてしまう）。
  他の譜種はもともと声部のUIが無かったので1から始める。CI で
  `ScorePageUiContextBar.test.tsx`（「左手・声部2」を探す）が落ちて気づいた
- **声部数の決め方**: 「データで実際に使われている声部数」と「＋で足した希望値」の**多いほう**。
  足した直後の声部はまだ音符が無く、データ上は存在しない（#305 の自動掃除で畳まれる）ため、
  希望値を UI 側（`requestedVoiceCounts`）で覚えていないと押した瞬間にチップが消える
- **ScorePage**: `activeVoice` を `0 | 1` から `number` へ。声部数が減ったときに
  範囲外の声部を選んだままにしない `useEffect` を追加（放置すると「入力しても画面に出ない声部」に
  音符が入り続ける無言の行き止まりになる・#318）
- **`V` キー**: ハンドラは登録しっぱなしの window イベントなので、巡回に必要な声部数は
  ref 経由で読む（依存配列に足すと毎回貼り替えになる）
- **配線**: `activeVoiceIndex` を `SingleStaff` / `QuartetStaff` / `EnsembleStaff` /
  `PartExtractionStaff` へ通した（既定 0 = 従来と完全に同じ描画・挙動）。
  `PianoStaff` の prop 型 `0 | 1` を `number` へ広げた
- **文脈バー**（`uiContextBar`）: 非ピアノ譜でも声部2以降を選んでいるあいだは
  「レイヤー: 声部N」を出す。声部1だけのあいだは従来どおり区画を出さない
  （存在しない概念を教えないための既存方針を、使い始めたときだけ解く）

### 4. 「行き止まりは喋る」（#318）

- 上限4に達した「＋」は `disabled` + `title` で理由と代替手順を言う
  （`describeVoiceLimitReached`: 「声部は1つの段につき4つまでです。使わない声部は
  音符をすべて消すと自動で消えます」）。⇵ボタンの無効化ツールチップと同じ型
- 声部を足したときは `describeVoiceAdded` で「どこへ入力されるか」を通知する
  （足しただけで入力先が変わらないと「押したのに何も起きない」ように見えるため、
  足した声部へ切り替えるところまでを1操作にした）

#404 全体（レイヤー把握UI）の実装はこの PR の範囲外。

### 9. Codex round1 の差し戻しを受けた作り直し（2026-09-03）

round1 で P1 が6件出た。うち3件（末尾空声部の掃除・段単位の追加・上限のデータ境界）は

#### 9-1. 「＋で足した本数」という状態をやめた（P1-1）

**問題**: `requestedVoiceCounts`（＋で足した希望値）は増えるだけで減らなかった。
声部3の音符を全部消すと、データ側は #305 の自動掃除で2声へ畳まれるのに、
チップは3枚のまま残る。Issue 本文が約束した「末尾の空声部は勝手に消える」が
UI で成り立っていなかった。

**修正設計**: 状態を1つ**消す**。チップの本数は次の3つの下限の最大として毎回導出する。

| 下限 | 何のためか |
| --- | --- |
| データで使われている本数 | 音符がある声部は必ず出す（途中が空でも `voices` の長さに現れる） |
| 譜種ごとの常設本数 | ピアノ譜の声部1・2（#316 の4枚）を保つ |
| **いま編集中の声部** | ＋で足した直後はまだ音符が無いので、これが無いと押した瞬間に消える |

「足した本数を覚える」を「編集中の声部までは必ず出す」に言い換えると、
足した声部は使っているあいだ出続け、何も書かずに離れれば自然に消える。
末尾だけが縮み、途中の空声部（`voices` 配列の長さ）は保たれる、という round1 の要求と一致する。
副次的に §7 の「作品をまたぐ持ち越し」も、持ち越す状態自体が無くなって消えた。

#### 9-2. 段（パート）ごとの声部数（P1-3）

**問題**: 非ピアノ譜は全パートの最大を1つに集約していたため、四重奏でヴィオラが3声だと
ヴァイオリンのチップも3枚になり、「どの段に足したのか」が決められなかった。

**修正設計**: 非ピアノ譜のパート選択は「クリックした五線」という**空間的な操作**が既存の
編集挙動なので、これを状態として拾う。新しい `SCORE_ACTIVE_PART_CHANGE_EVENT`
（通知・声部切替と同じ window CustomEvent 方式。ラッパー5つを props で貫通させない）を
音符クリックの2経路から出し、ScorePage が `activePartIndex` として覚える。
チップの本数と「＋」の追加先はその段だけのものになる。**編集の挙動自体は変えていない**
（ピアノ譜の `activeLayerPartIndex` のような明示レイヤーモードには**しない**。
非ピアノ譜で空白クリックの挿入先まで固定すると、既存の操作が別物になるため）。

#### 9-3. 上限4のデータ境界（P1-4）

**問題**: 上限がチップの枚数（表示）だけで、書き込み・読込・MusicXML 取り込みには無かった。
5声以上のデータは編集 UI に出ないまま再生され、保存し直すとそのまま残る＝
**画面から見えないので直せない**声部になっていた。

**修正設計**: 上限の正本を UI（`editorLayers.ts`）から**データ層**（`voiceMeasureUtils.ts` の
`MAX_VOICES_PER_PART`）へ移し、`MAX_VOICES_PER_LAYER` はその別名にした。強制する境界は3つ:

- **書き込み**: `withVoiceEventsUpdated` は上限以上の声部への書き込みを受け付けず、
  引数の小節をそのまま返す（Issue #245 の「変化が無ければ引数を返す」に合わせる）
- **読込**: 新設 `enforceVoiceLimitInParts` を localStorage / ファイルの両経路に置く。
  落とした小節数を返し、呼び出し側が `describeVoiceLimitTrimmed` で**理由付きで通知**する
- **MusicXML 取り込み**: 声部ループを上限で打ち切り、超過した小節数を
  `voicesOverLimitMeasureCount` として結果に返す（`unsupportedDynamicsCount` と同じ型）

黙って捨てないのは #318「行き止まりは喋る」に従ったもの。

#### 9-4. 声部3・4の符頭／記号クリック（P1-2）

`PianoSystemCanvas` の「2声まで」ガード2か所（符頭・記号）と、ScorePage 側の受け口
（`voiceIndex !== 0 && voiceIndex !== 1` で捨てていた）を上限基準へ一般化した。
上限超えのデータは読込の境界で落としているのでこのガードには来ない想定だが、
来たときに黙って無視すると「切り替えたと言われたのに実状態は変わらない」食い違いになるため、
理由を言って終える形は残している。

#### 9-5. 声部3・4の松葉（P1-5）

書き出しの `hairpinsVoice2`（声部2専用の1本）を `hairpinsExtraVoices`（声部ぶんの配列）へ、
取り込みの `skipHairpins: true` を声部ごとの待ち行列（`openHairpinRefsByVoice`）へ変えた。
待ち行列を声部ごとに分けるのは、声部1・2を別々に持っているのと同じ理由
（別々の声部で同時に開いた松葉の `stop` を取り違えないため）。

#### 9-6. UI の2件（P2-7・P2-8）

- 「＋」を `disabled` にしない。`disabled` はクリックもフォーカスも受け付けないので、
  上限の理由（`describeVoiceLimitReached`）が出る経路が無くなる。
  見た目は `.is-disabled`、状態は `aria-disabled`、押されたら通知、という形にした
- ピアノ譜で8枚になったときに「＋」がどちらの手のものか分からなくなるため、
  手ごとに `role="group"` のサブグループで囲み、その中では折り返さないようにした

#### 9-7. 声部ごとの強弱を再生音量へ（P1-6）

**問題**: `resolveDynamicVelocities` が主声部だけを走査し、索引キーも `小節-位置` の
2つ組で声部を含んでいなかった。実害は2つある。

1. 声部2以降に置いた `p` / `f` が**再生音量にまったく効かない**
2. さらに悪いことに、再生側（ScorePage）は `flattenMeasureForPlayback`（全声部を開始拍で
   並べ替えた列）の位置でキーを引いていたため、**多声小節では別の音符の強弱が当たっていた**

**修正設計**: 同じファイル内で先に (小節, 声部, 声部内の位置) の3つ組へ移行済みだった
**タイ（`buildTiePlaybackEventKey`）・ペダル（`buildPedalPlaybackEventKey`）の形にそろえた**
（同じ目的の既存実装を共用する、という運用者方針。2枚目のロジックを作らない）。

- `buildDynamicEventKey(measureIndex, eventIndex, voiceIndex = 0)` に声部を足す。
  既定 0 なので、主声部だけを列挙する `ScorePlayer` の既存呼び出しはそのまま正しい
- `resolveDynamicVelocities` は声部ごとに独立して解決する。声部をまたいで1本の列に
  しないのは、`cresc.` の傾斜が「その声部の次の音符たち」へかかるものだから。
  1本にすると、2声で同時に `cresc.` を書いたとき片方の音数が多いほど傾きが緩くなる
- ScorePage の引き当てを `event.voiceIndex` / `event.eventIndex`（声部内の位置）へ直した

なお #514（強弱記号を再生音量へ反映）とは同じファイルを触るが、
この修正は**キーの3つ組化と走査の声部ループ化**だけで、
ベロシティの決め方（絶対強弱の値・傾斜の刻み方）には手を入れていない。
