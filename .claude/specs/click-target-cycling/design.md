# 設計書: クリック対象の再クリック巡回（Issue #264）

当たり判定が重なる場所で、**同じ場所をもう一度クリックすると編集対象が次の候補へ切り替わる**
仕組み（Illustrator / Figma のクリックスルー方式）の設計。

- 対象コンポーネント: `src/components/PianoSystemCanvas.tsx`（全譜種がここを通る）
- 巡回の入口・候補台帳: `src/editor/clickCycle.ts`（Canvas が描画ごとに生成）
- 判定ロジック: `src/editor/clickCycleUtils.ts`（DOM に依存しない純関数）
- 関連: Issue #257（弧の当たり判定を中央部へ限定・音符ヒットを前面へ）、#246（拡張ヒット帯のX方向）、
  #233（休符の1クリック置換）、#218 / #219（当たり判定の帰属）

---

## 1. 問題

SVG には z-index が無く「後に描いた要素が前面」で、**一番手前の要素だけがクリックを受け取る**。
そのため当たり判定が重なった場所では、奥にある対象を選ぶ手段が無い。

実際に重なるのは主に次の3組み合わせである。

| 重なるもの | 起きること |
| --- | --- |
| スラーの弧 × 途中の符頭 | 弧はスラーが掛かった音符の**上を通る**ので、途中の音符の符頭と中央帯が重なる |
| 弧 × 弧 | 声部1のスラーと、同じ区間に張った別の弧（タイなど）が近い高さで重なる |
| 松葉 × 符頭 | 五線の下の低い音符（加線域）と、五線下に描かれる松葉が重なる |

#257 で弧の当たり判定を中央部だけに絞ったことで頻度は下がったが、
**中央部（＝頂点まわり）はまさに途中の符頭の上**なので、この重なりは原理的に消せない。

## 2. 運用者が決めた方式（Issue 本文）

- **1回目のクリック**: 現行の決定的な優先順位のまま（PR #257 の規則を変えない）
- **同じ場所をもう一度クリック**: その座標のヒット候補を巡回して次の対象を選択。一巡したら先頭へ
- ポップアップ（候補リスト）は出さない（入力のホットパスを止めない・#248 のモーダルキー漏れの再発を避ける）

不採用となったセレクトボックス方式の理由も Issue 本文に記録されている。
将来「長押しで候補リスト」をハイブリッドで足す余地は残す。

## 3. 修正設計

### 3-1. 進み具合は「DOM 要素」ではなく「論理ID」で覚える

最初に躓くのがここなので明記しておく。

選択が変わるたびに譜面 SVG は**丸ごと作り直される**（`innerHTML=''` → 新しい `<svg>`）。
「もう選んだ対象」を DOM 要素の参照で覚えると、再描画のたびに参照が別物になって
「まだ誰も選んでいない」状態へ戻り、**何度クリックしても先頭の候補から動かない**。

そこで、再描画をまたいでも同じ値になる論理IDで覚える。

| 対象 | ID の形 | 発行場所 |
| --- | --- | --- |
| 音符 | `note:p{part}:m{絶対小節}:v{声部}:e{イベント}` | 音符ヒット rect の生成箇所 |
| 弧（タイ／スラー） | `arc:{arcKeyP()}`（例 `arc:p0v0m0e0a0`） | `drawArcPathP` |
| 松葉 | `hairpin:p{part}v{声部}m{開始小節}e{開始イベント}h{index}` | 松葉の一括描画 |

同じ対象が複数の要素に分かれている場合（音符の固定範囲 rect ＋ 拡張部 rect・#246、
段またぎで2本に分かれた弧・松葉）は**同じIDで登録**し、候補を集めるときに1件へ畳む。
IDは `data-cycle-id` 属性としても DOM に出す（テスト・デバッグ用。表示には影響しない）。

### 3-2. 候補の列挙は `document.elementsFromPoint` に任せる

「その座標に何が重なっているか」を自前で総当たりしようとすると、
**曲線の当たり判定（スラーの帯）を矩形で近似することになり必ずずれる**。
重なり順を正確に知っているのはブラウザだけなので、`elementsFromPoint`（手前→奥の順）に聞き、
巡回台帳（`Map<Element, ClickCycleTarget>`）に載っている要素だけを拾う。

- 台帳は描画のたびに作り直す（古い要素を握ったままにしない）
- `elementsFromPoint` は `pointer-events` を尊重するので、透明でもクリックを受けない要素は入らない
- jsdom のように `elementsFromPoint` を持たない環境では候補ゼロ＝巡回しない（従来どおりの挙動）

### 3-3. 「選択で終わったクリック」だけが巡回の起点（既存語彙との衝突の裁定）

Issue 本文が名指しした2つの既存の「同じ場所の再クリック」と衝突させないための裁定。

| 既存の意味 | 巡回との関係 |
| --- | --- |
| 休符の1クリック置換（#233） | 置換は**編集**なので起点にならない。2回目も従来どおり置換される |
| 奏法記号・リピート等のトグル解除 | トグルは**編集**なので起点にならない。2回目も従来どおり外れる |
| 小節選択ツール / Shift+クリック（#145） | 巡回判定より**前**に処理して return する。小節選択は巡回に一切関わらない |

実装は「巡回状態を明示的に持ち上げる（arm する）のは選択の成立地点だけ」という一点で表現する。

- クリックの入口で `tryClickCycle()` を呼び、巡回しなかったら**進み具合を捨てる**
- そのあと通常処理へ進み、**符頭の個別選択・弧の選択・松葉の選択が成立した所だけ** `armClickCycle()` を呼ぶ
- 挿入・和音追加・休符置換・記号トグルは arm しない ⇒ 次のクリックは常に「1回目」として扱われる

ツール種別（音価ツールか記号ツールか）で分岐する条件式を書いていない点が重要である。
条件式を二重に持つと、ツールが増えるたびに巡回側の除外リストの更新漏れが起きる。

### 3-4. 巡回で実行するのは「選択だけ」

奥の対象へ切り替えたいだけのクリックなので、巡回で走る `activate()` は選択と確認音だけを行う。
音符を増やす・置き換える・記号を付ける等の**編集は絶対にしない**。

音符側の `canActivate` / `activate` は、通常のクリック判定
（`nearNoteX` → `findKeyIndexAtLine` → 固定範囲外の吸い寄せ `findNearestKeyIndexWithinLines`）を
そのまま切り出した `resolveSelectableKeyIndex()` を共有する。別式で近似すると
「巡回では選べるのに普通に押すと選べない」という食い違いが出る（ホバー表示と同じ轍）。

符頭から外れた位置（挿入になる位置）では音符は**候補に入らない**。
そこでの1回目のクリックは従来どおり挿入であり、巡回の相手も現れない。

### 3-5. 巡回の入口イベント（対象ごとに違う理由）

| 対象 | 判定 | 実行 | 理由 |
| --- | --- | --- | --- |
| 音符 | `click` | `click` | 音符の選択そのものが `click` で確定するため |
| 弧 | `mousedown` | **`mouseup`（動かさずに離したときだけ）** | 下記 |
| 松葉 | `click` | `click` | 松葉の選択が `click`（`drawHairpinSegment` の既存仕様） |

弧だけ判定と実行がずれているのには理由がある。

- 弧の選択は `mousedown` で確定するので、`click` まで待つと**選択による再描画で当たり判定パスが
  作り直され、`click` が別の要素へ飛ぶ**（`.vf-hit` 側にも同じ理由のコメントがある）。
  よって判定（＝どの候補へ進むか）は `mousedown` の時点で行うしかない。
- 一方、**弧はドラッグの開始も `mousedown`** である。押した瞬間に次の候補へ移してしまうと、
  「選択した弧を同じ場所で掴み直して曲率を変える」ができなくなる。

そこで `mousedown` では**計画を ref へ預けるだけ**にし、通常どおり弧を選択してドラッグの準備もする。
`mouseup` の時点で `arcDragMovedRef` が false（＝ただのクリックだった）なら、そこで初めて巡回を実行する。
計画は ref に預けてあるので、再描画で当たり判定パスが作り直されていても拾える。
SVG の外で離した等で取りこぼした計画は、window の `mouseup`（`onUp`）で必ず捨てる
（後の無関係なクリックで古い計画が発火しないように）。

`drawHairpinSegment` には、作った当たり判定パスを呼び出し側へ渡す
`onHitPathCreated` を追加した（台帳へ登録するため。描画そのものは不変）。

### 3-6. アルゴリズム（`clickCycleUtils.ts`）

状態は「直前のクリック座標」＋「その座標で選び終えたIDの配列」だけ。

```
planClickCycle(state, x, y, candidateIds /* 手前→奥 */, selfId):
  座標が前回と違う（±4px 超）        → null（1回目扱い）
  候補が1件以下                      → null（切り替える相手がいない）
  自分が候補に入っていない            → null（安全側）
  remaining = candidateIds - consumed
  remaining が空                     → consumed をリセットし remaining = candidateIds（一巡）
  next = remaining[0]
  next が自分自身                    → null（通常処理でよい）
  それ以外                           → { nextId: next, consumed: [...consumed, next] }
```

**呼び出し側の約束**: `null` が返ったら通常処理へ落とす前に進み具合を必ず捨てる。
一巡して先頭へ戻ったケースでこれを忘れると進み具合が溜まったままになり、2周目が回らない
（「音符→スラー→音符→音符→…」で止まる）。テストでもこの通しシナリオを固定している。

許容誤差は画面 4px（`CLICK_CYCLE_TOLERANCE_PX`）。手ぶれで数px動いても巡回が続くようにするため。

### 変えていないこと

- 1回目のクリックの優先順位（#257 / #246 / #219 の当たり判定はそのまま）
- 描画・レイアウト・保存データ（巡回は選択状態しか触らない）
- 重なりが無い場所の挙動（候補が1件なので巡回は起動しない）

### 受け入れたトレードオフ

1. **弧の再クリックでは、押した瞬間ではなく指を離した瞬間に切り替わる。**
   §3-5 のとおりドラッグと両立させるための遅延で、押したまま止めているあいだは
   まだ弧が選択されたままに見える。ポップアップを出さない方式を選んだ以上、
   「同じ点の mousedown」に2つの意味（ドラッグ開始・次の候補へ）を同時に持たせられない
   ことによる必然の割り切りである。
2. **記号の調整オーバーレイ（`.symbol-hit-region`）は巡回の候補に入れていない。**
   あれはクリックが「選択」ではなく「オーバーレイを開く」であり、巡回の意味（編集対象の選び分け）と
   違うため。専用ツールを選んでいるときだけクリック可能になる仕組みでもあり、重なりの実害が薄い。
3. **`elementsFromPoint` を持たない環境では巡回しない。** 動作環境（Chrome / Safari / Firefox）は
   すべて対応済みなので実害は無い。jsdom のテストでは差し替えて重なりを再現している。
