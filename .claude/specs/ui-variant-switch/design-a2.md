# 設計書: UI案A2「譜面側でレイヤーを示す」（Issue #405 段3）

Issue #405 の段3。段1（`.claude/specs/ui-variant-switch/design.md`・切替の土台）の上に載る。
段2（A1 文脈バー）とは独立していて、触るファイルも重ならない。

## 目的と前提

弟テスト会で「詰まったとき、原因が **レイヤー / タブ / ツール** のどれだったか」を観察するため、
UI案を3つ（current / A1 / A2）用意して反応を比べる。

- **A1** は言葉で出す案（ツールバーに「右手・声部1 / 演奏記号 / pp」の1行を常設）
- **A2**（この段）は**譜面側**で出す案。視線が譜面から離れないことを狙う
- 対照群 `current` は現状のままで、**1px も変わってはいけない**

## 問題点（実装前の状況）

ピアノ譜の編集レイヤーは (手, 声部) の4通りあり、いま何が選ばれているかは
ツールバーのチップの色でしか分からない。音符を置く場所は譜面なので、
「どの段に入るのか」を確かめるには視線をツールバーへ往復させる必要がある。

譜面側の手掛かりは既に1つだけあった: **2声部が共存する小節**では、非アクティブな声部の
音符が淡色（`INACTIVE_VOICE_COLOR`）で描かれる（Issue #175）。ただしこれは
「同じ手の中の声部」だけで、**もう一方の手**はまったく区別されない。

## 修正設計

### 見せ方（2つ）

| 表現 | 対象 | 実装 |
| --- | --- | --- |
| **色帯** | アクティブなレイヤーの手の五線 | 五線の背後に薄い青の `rect`（`.vf-active-layer-band`）を敷く |
| **淡色化** | 非アクティブなレイヤー（もう一方の手）の音符・ビーム・連符・記号 | 音符系は既存の `INACTIVE_VOICE_COLOR`、記号は不透明度 `0.35` |

**既存の淡色表示（Issue #175）に相乗りしている**のが設計の要点。A2 のために
別の薄さ・別の色を新設すると、「声部が非アクティブ」と「手が非アクティブ」で
2種類の淡色が画面に混在してしまい、テスト会で何が伝わったのかが読めなくなる。
判定式に条件を1つ足すだけにした:

```ts
// 変更前
const isInactiveVoice = isMultiVoiceMeasure && voiceIndex !== activeVoiceIndex;
// 変更後（isInactiveLayerPart は A2 のときだけ true になりうる）
const isInactiveVoice = isInactiveLayerPart
  || (isMultiVoiceMeasure && voiceIndex !== activeVoiceIndex);
```

### 声部側は既存のまま（採った解釈）

レイヤー = (手, 声部) なので、厳密には「同じ手の別声部」も非アクティブなレイヤーである。
しかし声部側の淡色化は既に Issue #175 の規則（**2声部が共存する小節でのみ**淡色）で
動いており、A2 のためにこれを「単声部の小節でも淡色」へ広げると、声部2を選んでいる間は
声部1しか無い小節が軒並み薄くなる。譜面の大半が薄いグレーになると読めなくなり、
テスト会で見たいもの（レイヤーが分かるか）以前の問題になる。

そこで **A2 が足すのは「手」の次元だけ**とした。声部の見え方は current と同じ。

### なぜ真偽値の prop なのか（`highlightActiveLayer`）

`PianoSystemCanvas` / `PianoStaff` へ渡すのは UI案そのもの（`'a2'`）ではなく
`highlightActiveLayer: boolean`。描画コンポーネントに「テスト会のUI案」という
上位の都合を持ち込まないため。`ScorePage` 側で `uiVariant === 'a2'` を判定して渡す。

省略時は `false`。既定のUI（current）では判定式が従来と同値になり、描画は変わらない。

### 色帯を「背後」に敷く方法

SVG は後から描いた要素が手前に来るので、五線を描いたあとに `appendChild` すると
帯が音符の上に乗ってしまう。`svgRoot.insertBefore(band, svgRoot.firstChild)` で
先頭へ入れることで、塗りだけの薄い帯を線の見た目を変えずに敷ける。
帯には `pointer-events: none` を付け、下にある譜面のクリック（音符入力・小節選択）を
横取りしないようにしている。

帯は五線の上下へ `ACTIVE_LAYER_BAND_PAD`（6px）はみ出させる。五線の高さちょうどだと
帯の縁が最上線・最下線に重なり、「線が太くなった」ように見えるため。

### 記号の淡色化を1か所で行う

記号（強弱・アーティキュレーション・運指・発想標語・コードネーム・オクターブ記号・
カスタム記号）は種類ごとに描画コードが分かれているが、**どれも最後に
`appendSymbolHitRegion(描いた要素, partIndex, …)` を呼ぶ**という共通点がある。
`drawCollectedSymbolEntries` の中でこの関数を1枚包み、非アクティブなパートの要素に
不透明度とクラス（`.vf-inactive-layer-symbol`）を付ける形にした。
7種類ぶんの描画コードへ同じ2行を書き写すより、修正が片方に届かない事故が起きにくい。

音符と違って色を差し替えず**不透明度**を下げるのは、記号は種類ごとに色が違う
（黒い文字・青い線など）ため。色を一律に上書きすると意味が変わってしまう。

対象外（淡色にならない）のは、パートに属さない記号: 小節番号・リハーサルマーク・
速度記号（最上段基準で描かれる）と、歌詞・ペダル記号（`appendSymbolHitRegion` を
通らない経路）。テスト会で見たいのは「どの手を編集しているか」なので、
段全体に関わる表示まで薄くする必要は無いと判断した。

### 本番ビルドで出ないことの担保

段1 の `resolveUiVariant` が本番ビルド（`isDev=false`）では必ず `current` を返すので、
`uiVariant === 'a2'` は本番では成立しない。加えて段1・段2 と同じ形で
`import.meta.env.DEV && uiVariant === 'a2'` と二重に囲ってある。

ただし段1・段2 と違い、**描画コード自体は本番バンドルにも入る**（`PianoSystemCanvas` は
UI案に関係なく常に読み込まれるコンポーネントで、A2 の分岐はその中の条件分岐のため）。
到達しないだけで、文字列 `vf-active-layer-band` は `dist` に含まれる。
テスト会用の未完成UIが本番の画面に出ないという目的は満たしているが、
段1 の「バンドル文字列にも出さない」という確認方法はこの段には当てはまらない。

### 印刷では消す・戻す

色帯も記号の淡色も「いま編集している場所」という画面上の意味しか持たないので、
`@media print` と `.print-preview`（印刷プレビュー）では帯を `display: none`、
記号の不透明度を `1` に戻す。パディング休符（Issue #59）が印刷では黒に戻るのと同じ考え方。

## 影響範囲

変更:

- `src/editor/hitResolution.ts` — 定数を3つ追加（`ACTIVE_LAYER_BAND_COLOR` /
  `ACTIVE_LAYER_BAND_PAD` / `INACTIVE_LAYER_SYMBOL_OPACITY`）。既存定数の変更は無し
- `src/components/PianoSystemCanvas.tsx` — `highlightActiveLayer` prop、色帯の描画、
  音符・ビーム・連符の淡色判定への条件追加、記号の淡色化（いずれも追加のみ）
- `src/components/PianoStaff.tsx` — prop の中継
- `src/components/ScorePage.tsx` — `highlightActiveLayer={uiVariant === 'a2'}`
- `src/App.css` — 印刷・印刷プレビューでの打ち消し

README は更新していない。開発時のみのテスト会用表示で、本番（ユーザー）から見える
操作・画面は変わらないため（AGENTS.md「README はユーザーから見える操作・画面が
変わった場合のみ」）。段1・段2 と同じ扱い。
