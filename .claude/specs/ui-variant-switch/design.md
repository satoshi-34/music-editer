# 設計書: テスト会用のUI案切替（Issue #405 段1）

Issue #405。弟テスト会でUI案を「その場で」切り替えて反応を比べられるようにするための土台。
この設計書は **段1（切替の仕組みと、いまどの案かの表示）** を対象とする。
段2（A1 文脈バー）・段3（A2 譜面側表現）は、ここで作った土台の上に別PRで載せる。

## 目的と前提

- UI は議論より実物を触ってもらう方が早く、テスト会は**一度きりの機会**なので、
  案を変えるたびに再ビルドしていては間に合わない
- 「新UIが良いか」ではなく「**現状より良いか**」を見るため、現状（`current`）を対照群として必ず含める
- テスト会用の未完成UIが本番（Vercel Production）へ漏れてはいけない

## 問題点（実装前の状況）

UI案を差し替える手段が「ブランチを切り替えて再ビルドする」しか無かった。
テスト会の場で「じゃあもう一方も見せて」と言われても即座に応えられない。

## 修正設計

### 切替の経路

`?ui=a1|a2|current` というURLパラメータで選び、`localStorage` に記憶する。
弟の端末にはURLを送るだけでよく、リロードだけで切り替わる。

### 適用する案の決め方（`resolveUiVariant`）

判定は `src/utils/uiVariant.ts` の純粋関数 1 本に閉じている。
「URLパラメータ」「記憶している値」「開発ビルドかどうか」の3つだけを入力に取り、
`window` や `import.meta.env` を直接読まない。**本番ビルドで `current` に固定されること**を
テストから直接確かめられるようにするための構造。

| 条件 | 適用する案 | 記憶を更新するか |
| --- | --- | --- |
| 本番ビルド（`isDev=false`） | `current` | しない |
| `?ui=` が有効値 | その案 | する |
| `?ui=` が不正値 | `current` | する |
| `?ui=` が無く、記憶が有効値 | 記憶している案 | しない |
| `?ui=` が無く、記憶も無い／壊れている | `current` | しない |

判断が分かれる2点について、採った解釈と理由:

- **「未指定は `current`」の解釈**: Issue 本文には「不正値・未指定は `current`」とあるが、
  同じ本文に「localStorage に記憶する」「リロードで維持される」ともある。
  未指定を常に `current` にすると記憶が一切効かなくなり、後者と矛盾する。
  そこで「**パラメータでは何も選ばれていない**」の意味に取り、記憶 → `current` の順で
  フォールバックする形にした。テスト会中にURLからパラメータが落ちても、
  選んだ案のまま触り続けられる方が目的に合う
- **不正値のときに記憶も `current` へそろえる**: 打ち間違い（`?ui=a11` 等）のときに
  「画面は `current` なのに記憶は `a1`」という見えない食い違いが残ると、
  次にパラメータ無しで開いたとき勝手に案が変わって観察記録が濁る

### 開発時のみ有効にする二重の防御

1. `resolveUiVariant` が `isDev=false` のとき問答無用で `current` を返す
2. 隅の表示は既存のサンプル読込ボタンと同じ `import.meta.env.DEV && ...` で囲う

2 のおかげで本番バンドルからは表示コンポーネント自体が落ちる
（`npm run build` 後の `dist/assets/*.js` に文字列「UI案」が含まれないことを確認済み）。

### いまどの案かの表示

画面右下に固定の小さなバッジ（`.ui-variant-badge`）を出す。テスト会の写真・録画から
「詰まった場面がどの案のときだったか」を後から突き合わせるための観察記録用。

- **対照群 `current` でも出す**。出る案と出ない案があると、「表示があること自体」が
  案の違いになってしまい、比較の条件がそろわない
- `pointer-events: none` でクリックを素通りさせる（バッジの下にある譜面を触れなくしない）
- `@media print` で `display: none`（画面専用の開発用表示なので紙には出さない）

### 段2・段3への引き渡し

- `useUiVariant()` の戻り値を見て「自分の案のときだけ描く」形にする（A1 文脈バー向け）
- `.app-root` に `data-ui-variant="a1|a2|current"` を付けてあるので、
  CSS だけで済む表現（A2 の淡色化など）は `[data-ui-variant="a2"] ...` を目印にできる

`current` のときは属性が `current` になるだけで、見た目は 1px も変わらない。

# 設計書: UI案 A1「文脈バー」（Issue #405 段2）

段1（上記）で作った切替の土台の上に、案 A1 を載せる。`?ui=a1` のときだけ現れる。

## 目的と問題点

いまの画面は、これから何が起きるかを決める3つの状態が、それぞれ別の場所に散っている。

| 状態 | どこに出ているか |
| --- | --- |
| 編集レイヤー（右手/左手 × 声部1/2） | チップの色（当初は「音符・休符」タブ内。2026-08-25 に Undo/Redo 横へ常設） |
| 開いているタブ | タブボタンの枠の色 |
| 持っているツール | パレットのボタンの選択枠 |

いずれも**色の違いだけ**で、言葉になっていない。初めて触る人は「自分がいまどの状態か」を
言い表せず、譜面をクリックして初めて結果が分かる。テスト会で詰まったときに
原因が **レイヤー / タブ / ツール** のどれだったかを観察者が判別できないと、
#404 の設計判断に使える一次データにならない。

## 修正設計

ツールバーのタブ行のすぐ下に、1行の帯（`.ui-context-bar`）を常設する。

```
レイヤー 右手・声部1 / タブ 演奏記号 / ツール pp
```

- 見出し語（「レイヤー」「タブ」「ツール」）を**中身と一緒に**出す。
  値だけを並べると「右手・声部1」が何の区分なのかが伝わらず、
  詰まった原因を言葉にする（＝観察データにする）という目的を果たせない
- レイヤーの区画は**ピアノ譜のときだけ**出す。単旋律・弦楽四重奏・アンサンブルには
  「手 × 声部」のレイヤー選択が無く、空欄や「なし」を出すと**存在しない概念を教えてしまう**
- 折り畳み中（`.toolbar.collapsed`）は他の行と同じく隠す。折り畳みは
  「譜面を広く見たい」ときの操作なので、帯だけ残るのは目的に反する
- 印刷には出ない（`.toolbar` 自体が `@media print` で `display: none`。個別指定は不要）
- 表示専用でクリックできる要素は置かない。切り替えは従来どおりタブ・チップ・パレットで行う

### 表記の正本を1か所にまとめた（重複実装を作らない）

文脈バーは、パレットのツールチップやレイヤーチップと**同じ言葉**を出さなければ、
「バーに出ている言葉」でボタンを探せず逆に迷わせる。一方で、これらのラベルは
これまで `Palette.tsx` の中（module 内の private 関数）と `ScorePage.tsx` の中
（JSX に直書きの配列）にしか無く、そのままではコピーが増える。
片方だけ直して表記がずれる事故（#223 の修正が声部2の別実装へ届かず #280 が起きた型）を
新たに作らないため、**ラベルの正本を `src/utils/editorContextLabels.ts` に集約**した。

| 移した／集約したもの | 元の場所 | 参照する側 |
| --- | --- | --- |
| 音価・臨時記号・四分音・リピート・括弧・強弱のラベルと記号表記 | `Palette.tsx`（private） | Palette のツールチップ / 文脈バー |
| タブの並びと表示名（`TOOLBAR_TAB_BUTTONS`）・`ToolbarTab` 型 | `ScorePage.tsx`（コンポーネント内） | タブ行 / 文脈バー |
| ピアノのレイヤー4種（`PIANO_LAYER_OPTIONS`） | `ScorePage.tsx`（JSX に直書き） | レイヤーチップ / 文脈バー |

アーティキュレーション・装飾記号・テキスト要素は既に
`articulationUtils` / `ornamentUtils` / `textElementUtils` に公開関数があるため、それをそのまま使う。

### 文脈バーの中身を作る純粋関数

`src/utils/uiContextBar.ts` の `buildContextBarSegments()` が、
`scoreType` / レイヤー / タブ / ツール から表示する区画の配列を返す。
`describeTool()` は `Tool` の全モードを網羅した `switch`（`never` 検査つき）なので、
**ツールを増やしたときにバーだけ更新し忘れると型エラーになる**。
DOM も React も使わないので、ScorePage 全体を描かずにテストで固定できる（段1 の `resolveUiVariant` と同じ形）。

### 本番ビルドへの二重の防御

段1 と同じく、`resolveUiVariant` が本番では `current` を返すことに加えて、
描画側も `import.meta.env.DEV && uiVariant === 'a1' && ...` で囲う。
`npm run build` 後の `dist/assets/*.js` に `ui-context-bar` の文字列が含まれないことを確認済み
（コンポーネントごと落ちている）。

## レビューで足した修正（#408 round1・round2）

### ツールバー高さの上限（実害あり）

文脈バーはツールバーを1行ぶん高くする。ScorePage の高さ計測には「暴走した実測値を弾く」
上限280pxがあり、**スマホ幅でタブ行とパレットが折り返すと実高がこれを超えて切り捨てられ、
固定ヘッダーの下へ譜面が潜る**。

- 丸めの計算を純粋関数 `src/utils/toolbarHeight.ts` の `resolveToolbarHeight` へ切り出した
- A1 のときだけ `extraAllowancePx: UI_CONTEXT_BAR_HEIGHT_ALLOWANCE_PX`（44px）を渡して上限を上げる
- 表示判定は `showUiContextBar` に一本化し、高さ計算と描画で同じ条件を使う（2箇所に持つと片方だけ変わる）
- 実測が数値にならないとき `--toolbar-h: NaNpx` になる既存の穴も塞いだ

### 声部3以降のラベル

`pianoLayerLabel` のフォールバックが「パート1・声部3」になり、手の呼び名が消えていた。
ピアノ譜では手が分かっているので「右手・声部3」を保つ。`editorContextLabels.test.ts` を新設
（このファイルはテストが0件だった）。

### 二重ガードの意味とテスト

描画側は `import.meta.env.DEV && uiVariant === 'a1'`。フック側（段1）が既に本番で `current` を
返すため**画面の挙動としては冗長**だが、二重にする目的は「**本番バンドルからコンポーネント自体を
落とす**」ことにもある。これは観測可能な差なので、フックを `a1` に固定した隔離テスト
（`ScorePageUiContextBarProdGuard.test.tsx`）で描画側ガードだけを検証する。

## 実機調整（2026-08-25・PR #410）

- **A1 文脈バーの置き場所**: ヘッダー内（当初）→ タブ列の横（第1版）→ **譜面背景の左上**（確定）。
  「入力するボタン群」と「今の状態の表示」を場所で分けるという運用者所感による。
  fixed + `--toolbar-h` でヘッダー直下・`pointer-events: none`・印刷非表示・**折り畳み中は出さない**。
  ヘッダー外へ出たため #408 の `extraAllowancePx` は不要になり削除（`resolveToolbarHeight` の仕組みは残置）
- **A2 の色帯**: 「現状との違いが分からない」所感を受け 0.08 → 0.16（`ACTIVE_LAYER_BAND_COLOR`）
- **A3（`?ui=a3`）新設**: A1+A2 の両方込み。有効値・ラベル・本番固定の防御はすべて既存の型に乗せた
- **レイヤーチップの常設化**（UI案とは独立の既定UI変更）: 「音符・休符」タブ内 → **Undo/Redo の隣**へ。
  記号を付けるときもアクティブレイヤーの音符しかクリックできない（#316）ため、タブ内にあると
  記号1つ付けるのにタブ往復が要った。レイヤーはタブ非依存の状態なので、同じくタブ非依存の
  Undo/Redo と並べる。**対照群（current）にも効く変更**である点に注意（テスト会の観察では
  「チップが常設された現状」が新しい基準線になる）
