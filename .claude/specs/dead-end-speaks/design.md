# 設計書: 「行き止まりは喋る」原則と無言行き止まりの棚卸し（Issue #318）

## 問題

月光の清書中に #315（またぎ音符の当たり判定が左手クリックを飲む）を踏んだとき、
回避手順（またぎ解除 → 左手を先に入力 → 再度 ⇵）は**レビュアーが口頭で伝えて**初めて使えた。
アプリだけを触るユーザーは同じ場面で行き止まりになる。

個別のバグは直せばよいが、本当の問題は「**操作が無反応で、理由も次の一手も示されない**」という
体験そのものである。無言の拒否は、ユーザーからは次のどれとも区別が付かない。

- クリック位置が悪い（もう一度押せば効くかもしれない）
- そもそもこの機能では無理（別の手を探すべき）
- アプリが壊れた（作業を中断すべき）

## 原則

操作が効かない・機能が意図的に制限されている場面では、アプリが必ず

1. **理由**（なぜ効かないのか）
2. **代替手順**（どうすれば目的を達成できるのか＝抜け道）

を通知（`notifyScoreEdit`）またはツールチップで示す。**無言 return の新設を禁止**する。
開発ルールとしての本文は `AGENTS.md` / `CLAUDE.md` の「行き止まりは喋る」節にある。

### 拒否そのものは変えない

この原則は「できないことをできるようにする」ものではない。
拒否の判定は従来どおりに保ち、**黙って終わるのをやめる**だけである。
判定まで一緒に変えると回帰の範囲が読めなくなるうえ、
「なぜ拒否するのか」の設計判断（例: 休符は段またぎの対象外）を無効化してしまう。

### 実装上の約束

- 文言は `src/utils/scoreEditorNotices.ts` の**文言ビルダー**として置く。画面側に文字列を直書きしない
  （同じ意味の文言が2か所に散ると、片方だけ直したときに食い違う。#280 と同じ壊れ方）
- 判定は **`setScore` / `setPartsScore` の updater の外**で行う。
  updater の中で通知すると、React が updater を2回呼ぶ場面（StrictMode など）で通知も二重に出る
  （[`delete-feedback-and-selection-clear/design.md`](../delete-feedback-and-selection-clear/design.md) の記述と同じ理由）
- 通知の出口は #238 で作った `SCORE_EDIT_NOTICE_EVENT`（画面下端中央・`role="status"`・4秒）を使う。
  新しい通知の仕組みを増やさない

### 「元に戻せます」を付けるかの線引き

`UNDO_HINT`（Cmd/Ctrl+Z）は **譜面が実際に変わったとき**だけ付ける。
拒否の通知（何も起きなかった）に付けると「何かが起きて、それを戻せる」と誤読させる。

| 通知の種類 | UNDO_HINT | 例 |
| --- | --- | --- |
| 譜面が変わった | 付ける | 「音符を削除しました（Cmd/Ctrl+Z で元に戻せます）」 |
| 譜面が変わった（が、戻す対象が直感的でない） | 付けない | 「下の五線へ表示を移しました（所属は…）」※トグルなのでもう一度押せば戻る |
| 拒否・何も起きなかった | 付けない | 「この小節は拍がいっぱいで置けません（…）」 |

### #6 だけは「拒否」ではなく「成功」の通知である

運用者の追加提案2（Issue #318 コメント）に対応する。
**表示先の五線と、その音符の所属（パート・声部）は別物**であり、
これは cross-staff 設計の芯（[`cross-staff-notation/design.md`](../cross-staff-notation/design.md) §2）だが、
画面上で所属を知る手段が無い。

運用者は「下の五線へ移した音符は下声（声部2）の所属になった」と解釈し、
声部2が空である前提が崩れて #322 の症状を踏んだ。恒久策は #316 の色分け（レイヤー可視化）で、
この通知はその前倒しの1行対策である。したがって文言は「移した」だけで終わらせず、
**「所属は変わらない」まで言い切る**こと。

## 追加で直したもの: 記号系ツールの対象外クリック（Issue #330・棚卸しC群 C-1〜C-3）

記号系ツール（強弱・カスタム記号・カスタム記号のサイズ/位置調整・汎用の ⤢ ✥）は
すべて「音符に付ける／音符に付いている記号を調整する」ためのもので、
それ以外を押したときは何も起きなかった。行き止まりが3種類あり、いずれも無言だった。

| # | 場所 | 条件 | 変更前 | 追加した文言 |
| --- | --- | --- | --- | --- |
| C-1 | `PianoSystemCanvas.tsx` の休符クリック分岐（`else if(activeEvs[j]?.isRest)` の先頭） | 休符に記号系6ツールのいずれかを使う | 無言 return（ツールごとに1行ずつ・6行） | 休符には○○を付けられません／使えません（音符をクリックしてください） |
| C-2 | `customSymbolResizeMode` / `customSymbolOffsetMode` の `if (!existing)` | 調整しようとしたカスタム記号がその音符に付いていない | 無言 return | この音符には「○○」が付いていません（先に記号を付けてからサイズ調整／位置調整を使ってください） |
| C-3 | 汎用調整（⤢ ✥）の `if (targets.length === 0)` | 調整できる記号が1つも付いていない音符を押した | 無言 return | この音符には調整できる記号がありません（記号を付けてから ⤢ / ✥ を使ってください） |

### 文言ビルダーを1つにまとめた理由

対象ツールが6つあり、ツールごとに文言を書くと同じ意味の文が6つ以上散らばる。
片方だけ直したときに食い違う壊れ方（#280）を避けるため、
`describeSymbolToolUnavailable(tool, reason)` の1関数へ集約し、
ツール名（`SymbolTool`）と理由（`rest` / `symbolNotAttached` / `noAdjustableSymbol`）を差し込む形にした。

- カスタム記号の日本語名は `customSymbolDefs` から引く。解決は呼び出し側の `customSymbolNameOf` 1か所にまとめてある
- 「付ける」ツール（強弱・カスタム記号）と「調整する」ツール（サイズ・位置）で自然な動詞が違うため、
  そこだけビルダーの中で出し分ける（画面側には文字列を書かない、という約束は維持）
- C-1 の判定は、従来6行の `return` が並んでいた条件とまったく同じ集合（`activeSymbolTool` が非 null になるとき）。
  **拒否の条件は変えていない**
