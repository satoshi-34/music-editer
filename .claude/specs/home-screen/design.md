# 設計書: ホーム画面（譜種選択・保存ファイル・設定の玄関）

> 対応 Issue: [#500](https://github.com/satoshi-34/music-editer/issues/500)
> 関連: [#497 保存先の明示](https://github.com/satoshi-34/music-editer/issues/497) /
> [#181・#109 複数作品の保存管理](../multi-score-storage/design.md) /
> [#318 行き止まりは喋る](../dead-end-speaks/design.md)

## 問題

起動すると即・譜面画面という1画面構成だったため、

- 「どの譜種で新しく作るか」を決める入口が、譜面を開いたあとの「楽譜設定」タブの中にしかない
- 保存されている作品は「ファイル」タブの奥の「作品一覧 ▾」を開かないと見えない
- 設定類がタブに散っていて、初めて触る人が全体像をつかめない

「UIの体系化」（弟インタビュー回答②）と「すぐ開けると不安」（#497 の背景）の両方に効く玄関として、
ホーム画面を追加する。ログイン画面は作らない（お試しの障壁を上げない。#498 の方針）。

## 修正設計

### 画面の重ね方（なぜ ScorePage を隠さずに重ねるか）

`App.tsx` が **譜面画面（ScorePage）を常にマウントしたまま**、その上へ全画面の
ホーム（`HomeScreen`）を重ねる。ホームを閉じる＝重ねをやめる、という切り替えだけを行う。

- **「前回の続き」を1クリックにするため**: 起動時の復元（`useWorkLibrary.initializeWorks` →
  自動保存の読み込み）はホームの裏で従来どおり走っている。ホームを閉じるだけで編集を再開でき、
  「起動→即編集」の速さを1クリック以上悪化させない（Issue の最重要の回帰要件）
- **`display: none` で隠さない理由**: 譜面画面は表示幅の実測値から初期の表示倍率を決める
  （`ScorePageInitialZoomFit`）。隠すと幅が 0 になり倍率が狂う
- ホームのレイヤーは `z-index: 3000`（既存のモーダル類 2000〜2100 より上）。
  `@media print` では非表示にして、ホームが出たまま印刷指示が飛んでも紙に出ないようにしている

### 機能の実体は譜面画面のものを呼ぶ（二重実装をしない）

ホームは表示専用のコンポーネントで、処理は持たない。譜面画面が
`ScorePageHomeActions`（`homeActionsRef` 経由）として操作口を公開し、ホームのボタンはそれを呼ぶ。

| ホームの操作 | 実際に動く既存処理 |
| --- | --- |
| 前回の続きを開く | 何もしない（起動時の復元済み。ホームを閉じるだけ） |
| 譜種を選んで新規作成 | `performNewScore()`（ツールバーの新規作成と同じ）→ `handleScoreTypeChange(譜種)` |
| 保存した作品を開く | `handleSelectWork(workId)`（作品一覧パネルと同じ） |
| ファイルを開く（.score.json / MusicXML(.mxl) / PDF(β) / 以前の手動保存） | ファイルタブの各導線と同じ ref・同じハンドラ |
| 設定 | `handleToolbarTabChange('score' / 'layout' / 'playback')` |

譜種の並び・表示名・説明は `SCORE_TYPE_BUTTONS`（`src/utils/editorContextLabels.ts`）を正本にし、
「楽譜設定」タブの種類ボタンとホームの譜種選択が同じ定数から描かれるようにした
（同じラベルを2か所に書くと、片方だけ直したときに食い違う。#223→#280 と同種の事故を避ける）。

### 隠しファイル入力を常設へ移した理由

`.score.json` / MusicXML / PDF の隠し `<input type="file">` は「ファイル」タブの中に置かれており、
タブを開いていないと**要素そのものが存在しなかった**。ホームから開く導線を呼ぶには、
タブを切り替えて再レンダーを待ってから `click()` する必要があり、
Safari は「ユーザー操作と同じ処理の流れ」で呼ばれない `input.click()` を無視する（#464 の実機知見）。
そのため入力要素を `app-root` 直下の常設へ移し、タブ切替の反映を待たずにその場で `click()` できるようにした。
ファイルタブの見た目・操作は変わらない（ボタンとハンドラはそのまま）。

### ホームへ戻る導線と、未保存の扱い（#318）

ツールバー右上（ヘルプ・フィードバックと同じ「どのタブからでも押せるアプリ操作」の並び）に
🏠ホームボタンを置く。押すと戻る前に、

1. 自動保存の待機（1.5秒デバウンス）を止める（`cancelPendingAutosave`）
2. いまの内容を作品へ保存する（`saveCurrentWork`）
3. 作品一覧を読み直してからホームを表示する

という順で処理する。待機中のまま戻ると直前の編集が保存されないまま一覧に並び、
「保存されていない」ように見えてしまうため。ホーム側でも
「編集内容はこの端末のブラウザへ自動保存されています」と明示し、黙って済ませない（#318 の趣旨）。
ホームボタンは `onGoHome` が渡されたときだけ出るので、譜面画面単体をマウントする既存テストには現れない。

### バージョン表示（受入条件7）

ホームのフッターに `v3.6.0` の形で出す。値は `package.json` の `version` を
`vite.config.ts` の `define`（`__APP_VERSION__`）でビルド時に埋め込み、`src/utils/appVersion.ts` から読む
（画面側に版番号を手書きすると更新を忘れ、リリースノートと突き合わせられなくなる）。
着手時点の `package.json` は `0.0.0` のままだったため、保存データのバージョン
（`storage.ts` の `CURRENT_VERSION = '3.6.0'`）とリリースノートに合わせて `3.6.0` へそろえた。

### 将来枠（ログイン）

ヘッダー右に空の枠（`.home-header-slot`）だけ置いてある。ボタン・分岐は実装しない
（過剰設計にしない、という Issue の指示どおり）。後から足しても並びが崩れないようにするための場所取り。

## 追記（round 1 対応・2026-08-31）

Codex 最終ゲート round 1 の指摘（P1×4・P2×2）への対応で、以下が当初設計から変わった:

- **切替結果の判別化（P1）**: `useWorkLibrary.switchWork` の戻り値を
  `WorkSwitchResult`（sameWork / loaded / empty / error の判別付き）へ変更。
  現在作品をホーム一覧から選んだとき・読込失敗時に譜面を空リセットしない
- **ホーム表示中の遮断（P1）**: ラッパーの `inert`（フォーカス・クリック・支援技術）+
  `utils/homeVisibility.ts` の共有フラグ（window/document 級のキーボードショートカットを
  各リスナーの入口 `ignoreWhenHomeShown` で無視）。の2重遮断
- **成功時のみ画面遷移（P1）**: `ScorePageHomeActions` の各操作は成否を返し、
  App は成功時だけホームを閉じる。新規作成の保存失敗時は譜種を適用せず
  `describeHomeActionBlocked('create')` を通知。「ホームへ戻る」も保存失敗時は
  譜面に留まり `describeHomeActionBlocked('goHome')` を通知（#318）
- **移行後の一覧読み直し（P2）**: ScorePage の起動時移行・復元完了で
  `onLibraryReady` を呼び、App がホームのスナップショットを読み直す
- **操作の持ち越し（P2）**: 操作口の登録前に押されたホームのボタンは
  `pendingActionRef` に持ち越し、登録直後に実行する（無言で捨てない）
- テスト: App.test.tsx に現在作品選択・ショートカット遮断（正の対照付き）・
  保存失敗時の中断（新規作成／ホーム戻り）・移行後の一覧、の統合テストを追加

## 追記（round 2 対応・2026-08-31）

- **切替の原子性（P1）**: switchWork は切替前保存の失敗で即 error を返し（未保存の編集を
  失わない）、切替先の読込成功を確認してから currentWorkId / lastOpenedWorkId を更新する
  （失敗時に保存先だけが切替先になり、次の自動保存が別作品を上書きする穴を閉塞）
- **失敗理由のホーム表示（P2）**: HomeActionResult（ok / message）を導入し、失敗時は
  App がホームに留まって `role=alert` の .home-error に message を表示する
  （譜面側の通知はホームの下・inert で視覚/支援技術に届かないため）
- **連打と持ち越し（P2）**: actionRunningRef で実行中の追加操作を無視（並行 startNewWork
  による重複作品を防止）。登録前の操作は配列 pendingActionsRef へ積み、登録直後に順次実行
- **切替瞬間の遮断（P3）**: goHome / 遷移成功時に setHomeShown を**同期的に**呼び、
  effect の描画後同期までの一瞬にショートカットが漏れないようにする
- テスト: 旧・自動保存スロットだけを事前投入する実移行テスト、保存失敗の選択的注入
  （全キー throw は isStorageAvailable まで壊れて検出力ゼロになる罠を回避）、
  ホーム側エラー表示、戻った直後のキー遮断、切替失敗時の ID 不動、を追加

## 追記（round 3 対応・2026-08-31）

- **キュー排出の二重化（P2）**: 復元データの無い初回起動では onLibraryReady が
  操作口の登録 effect より先に走るため、持ち越し操作の排出は onHomeActionsReady
  （登録直後・初回のみの合図）側でも行う（drainPendingActions を共用）
- **busy の可視化（P2）**: 実行中は HomeScreen の全ボタンを disabled+aria-busy にして
  連打を見た目でも止める（無言で無視しない）。「前回の続き」も同じ busy 制御下
- **例外の受け止め（P2）**: runOnScorePage は action の例外も catch し、ホームに留まって
  .home-error へ理由を表示する（未処理 Promise にしない）
- テスト修正（P3）: 読込失敗時の ID 検証を not.toBe(A) → toBe(B) へ（null 化の退行も検出）

## 追記（Issue #512・Office 系レイアウトへの再構成・2026-08-31）

見た目とレイアウトだけの再構成で、**機能・配線（前回の続き・開く導線・設定・バージョン表示・
busy/エラー表示・inert 遮断）は一切変えていない**。`HomeScreen` が表示専用である前提も同じで、
props・呼び出す関数・`data-testid` はすべて据え置き（既存テストは1文字も変えずに通る）。

### なぜ Office 系の型を借りるか

初見の人（弟の同期など）が説明なしで使い方を察せられるようにするため、Word / Excel /
スプレッドシートの起動画面が共通して持つ**構造の文法**だけを借りた。配色は真似ず、
アプリ既存のトーン（深緑＋白いカード）をそのまま使っている。

| Office 側 | このホームでの対応 |
| --- | --- |
| 左レール（ホーム / 新規 / 開く） | `.home-rail`（ホーム / 新規 / 開く / 設定） |
| 空白のブック＋テンプレートのギャラリー | 「新しく作る」の譜種カード（サムネイル付き） |
| 最近使ったアイテム | 「最近使ったファイル」（名前・更新日時の行形式） |

### 左レールを `<a href="#...">` にした理由

レールの項目は**ページ内の見出しへ飛ぶだけのリンク**にしてある。

- 画面遷移（配線）を増やさずに Office の骨格だけを借りられる
- 操作の実行中（`busy`）に全ボタンを無効化する既存の仕組み（round3 P2）で、
  移動まで止めてしまわない。`<button>` にすると「実行中は全ボタンが disabled」という
  仕様に巻き込まれ、無害な画面内移動までできなくなる

### 譜種サムネイルを静的 SVG にした理由

実譜面のプレビュー生成は範囲外（Issue #512 の制約）なので、譜種ごとに違うのは
**段数と括弧の種類**だけ、という点に絞った静的 SVG を `HomeScreen.tsx` 内で描いている
（`THUMBNAIL_SHAPES`: 単旋律=1段、ピアノ=2段＋波括弧、弦楽四重奏=4段＋角括弧、編成譜=5段＋角括弧）。
段数が増えるほど1段の高さが縮むので、五線の間隔も段数から計算してカード間で高さがそろうようにしている。
画像ファイルを増やさないので、譜種が増えたときも表へ1行足すだけで済む。

なお Office の「空白のブック」に相当する専用カードは作っていない。新規作成の入口を1つ増やすと
配線（`onCreateNew` 以外の経路）が増え、「配線は変えない」という制約に反するため。
実質的に最も素の譜種である「単旋律」がギャラリーの先頭に来る並びで代用している。

### モバイル幅

`max-width: 760px` で左レールを上部の横並び（1行・横スクロール可）に切り替え、本文を1列にする。
375px 幅でも横スクロールが出ないこと、カードが2列に収まることをブラウザで実測して確認した。

## 追記（Issue #528・「新規＋最近使ったファイル」中心への再構成・2026-09-02）

運用者の要望「新規作成と最近使ったファイルぐらいにして、ファイルを開くと設定は横でいい。Excel みたいな感じ」
＋ Issue のトリアージコメント3件（前回の続きの廃止・横並びグリッド・中央にも「開く」）への対応。
**保存データの形式・作品の切替処理・inert 遮断・busy 制御・エラー表示の配線は変えていない**（見た目と入口の整理）。

### 「前回の続き」バナーを廃止し、一覧の先頭が役目を継ぐ

緑の大きな「前回の続きを開く」ボタンと `resume` / `onResume` の経路をまるごと削除し、
「最近使ったファイル」一覧の先頭（＝いちばん新しく更新された作品）を1クリックで開く形にした。

- **なぜ配線ごと消したか**: 同じ「作品を開く」操作が2経路（ホームを閉じるだけ／`openWork`）あると、
  片方だけ直したときに挙動が食い違う（#223 → #280 と同種の事故）。一覧の先頭を押す経路に一本化した
- **速さは変わらない**: いま開いている作品を選んだ場合、`useWorkLibrary.switchWork` が `sameWork` を返して
  読み直しをしない（round1 P1 で入れた判別付きの戻り値）。譜面は再構築されないので、
  起動 → 1クリック → 編集再開という最短経路は維持される（既存テスト「現在編集中の作品をホーム一覧から
  選んでも、譜面が空にならない」がこの経路を押さえている）
- `App.readHomeSnapshot` は `listWorks()`（更新の新しい順）をそのまま渡すだけになり、
  `getLastOpenedWorkId` を使った「前回の続き」の別建ての決め方は不要になった

### 中央の構成（カードグリッド2枚）

1. **新しく作る**: 譜種カード4種＋「ファイルを開く」カード1枚を同じグリッドに並べる。
   「開く」を中央にも置くのは運用者の使用頻度が高いため（下段の種類別「ファイルを開く」とは併存。
   MuseScore も右下に『他のファイルを開く』を併置している）。中央のカードは
   `availableOpenKinds` の先頭（通常は `.score.json`）を開く。使える導線がひとつも無いときはカード自体を出さない
2. **最近使ったファイル**: 行形式（名前／更新日時のヘッダ付き）をやめ、作品名＋最終更新日時のカードグリッドへ。
   サムネイル（譜面のプレビュー画像）は将来の別 Issue なので、テキストカードのままにしている

### 画面幅を使い切るレイアウト

「今の縦にカードを積んでいく方式は PC 画面を活かせていない」という指摘に対して、

- `.home-main` の `width: min(880px, 100%)`（中央1カラム）をやめ、`width: 100%` ＋ `max-width: 1800px` へ。
  超ワイド画面で文字が端から端まで散らばらないよう、上限だけ残している
- カードのグリッドは `repeat(auto-fill, minmax(200px, 1fr))`（最近使ったファイルは 220px）。
  **`auto-fit` ではなく `auto-fill`** を使うのは、カードが2〜3枚しか無いときに `auto-fit` が空の列を潰して
  1枚を横いっぱいに引き伸ばしてしまうため（Excel のホームでも最近のファイルは幅いっぱいには広がらない）
- 実測: 1440×900 で「新しく作る」の5枚が1行に収まり、最近使ったファイルは5列に流れて中央の余白が消える。
  375 幅では左レールが上部の横並びに戻り、譜種カード2列・最近使ったファイル1列で横スクロールは出ない
