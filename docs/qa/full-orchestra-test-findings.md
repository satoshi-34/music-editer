## 事前準備で分かったこと

- `saveScoreData` は `PRIMARY` キー（`music-score-app-data`）に加えて `METADATA` キー
  （`music-score-app-meta`）にチェックサムを書く。**手動で `PRIMARY` だけを書き換えて
  `METADATA` を更新しないと「Stored data checksum verification failed」エラーになる**。
  今回は `music-score-app-meta` と `music-score-app-backup` を消してから読込むことで回避した。
  これはテスト手順上の注意点であり、アプリ側のバグではない（整合性チェックは意図通り機能している）。

## 発見事項（バグ・改善点）

現時点で **確定した実装バグは見つからなかった**。以下は今回のセッションで気付いた注意点・要フォローアップ事項。

1. **［低・情報］手動 localStorage 書き込み時のチェックサム不整合**
   - 事象: `music-score-app-data` だけを書き換えて `music-score-app-meta` を更新しないと
     読込時に「Stored data checksum verification failed」と表示される。
   - 重要度: 低（想定通りの整合性チェック。QA手順としてはメタキーも同時に消す/更新する必要がある点をここに記録）。
   - 対応: 不要（仕様通り）。次回以降のQA手順書に注記済み。

2. **［中・要対応］段の小節数調整UIの自動テスト網羅性が低い**
   - 事象: 「次の段へ送る」「間隔を詰める/広げる」等のボタンが、特定の段にフォーカス/ホバーしていないと
     `disabled` になる作りのため、スクリーンショット操作だけに頼る自動テストでは有効化条件の再現が難しい。
   - 重要度: 中（機能自体の欠陥ではなく、テスト容易性の問題）。
   - 当たり: ボタンの有効/無効を切り替えている state が「現在アクティブな段」の hover/selection に
     依存していると思われる（`src/components` 内の段関連コンポーネントを要調査）。
   - 次フェーズでの対応: 実装側に `data-testid` や `aria-current` 等、どの段が対象かを外部から
     判定できる属性を追加すると、自動QAでの検証がしやすくなる。

3. **［低・要フォローアップ］ブラウザ自動操作ツールのペイン安定性**
   - 事象: 本セッション中、スクロール操作後にスクリーンショット取得が黒画面・ツールバー二重描画などの
     表示崩れを繰り返した（`navigate` での再読込により都度復旧）。また、`computer` クリックの座標系が
     スクリーンショットのピクセル座標と実際のCSSピクセル座標で一致せず、スケール変換
     （x: 800/951, y: 802/953 相当）が必要だった。加えて、`getBoundingClientRect()` で取得した座標も
     ページスクロール後は非同期にずれるため、要素取得とクリックの間に时間差があると座標が無効になる
     （ビューポート外をクリックしてしまい何も起こらない）ケースを複数回確認した。
   - 重要度: 低（アプリのバグではなくQAツール側の制約）。
   - 対応: 次回セッションでは、座標クリックより先に `scrollIntoView` 直後に即座に座標を再取得し、
     かつ `computer` の座標系をスクリーンショット直後に毎回検証してから使う運用を徹底する。

4. **未実施項目（次フェーズへの引き継ぎ）**
   - (b) フルオケでの実際のマウスクリックによる音符入力・選択・矢印キー・Deleteの動作は、
     人間による手動確認が必要（自動化ツールの制約により未確定）。
   - (f) 段の小節数・間隔調整のフルオケでの動作確認（要 hover/選択状態の再現）。
   - (e) 印刷プレビューの全13ページを1枚ずつ目視確認（最終ページの寄せ・段またぎのはみ出し等）。
   - MusicXML書き出し / MIDI書き出しの動作確認（本フェーズでは未着手）。

## 発見事項（フェーズB）

### 1. ［重大・要修正］大編成（17パート、「大編成オーケストラ」プリセット）で下5パートが画面・印刷の両方から消失する

- **事象**: `scoreType: 'ensemble'` かつパート数が多い（17パート、`romantic-orchestra` プリセット）楽譜で、
  1段に17パート全部が描画されるとき、その段の実際の高さが A4 1ページの印刷可能領域を超える。
  しかし `.print-page`（`src/App.css` 906〜936行目付近）は `height: 297mm; overflow: hidden;` で
  高さが固定されているため、はみ出した下側（Vln I・Vln II・Vla・Vc・Cb の5パート）が
  `overflow: hidden` によって**丸ごと非表示**になる。これは印刷プレビューだけでなく、
  トグルをONにしていない通常の編集画面でも同様に発生する（ページ割り自体は常時有効なため）。
- **再現手順**: 「その他」タブから `symphony-test-score.json`（17パート）を読み込み、
  総譜（通常）表示のまま画面を見る、または印刷プレビューをONにする → どのページを見ても
  Picc.〜Perc.（12パート）までしか描画されず、Vln I 以降が一切表示されない。
- **DOM計測による確証**（`.print-page` の `offsetHeight` と `scrollHeight` の差分）:
  - 総譜（17パート）: 全13ページで `offsetHeight=1123px` に対し `scrollHeight=1528px`
    （**405px ぶんが overflow:hidden で切り捨てられている**）。
  - パート譜（Violin I 単体・Timpani 単体）: 全13ページで `scrollHeight ≦ offsetHeight`
    （クリッピングなし）。→ 単一パートでは高さが十分小さいため問題が起きないことも確認。
- **根本原因（コード調査）**:
  - `src/components/ScorePage.tsx` 172〜186行目の `BASE_SYSTEM_HEIGHT_PX.ensembleLarge`
    （パート数10超の編成で使う「1段あたりの想定高さ」定数）が `800px` に固定されているが、
    実測では17パート編成の1段の高さは `1384px`（`.system-stack` の `scrollHeight`、
    `notationSizeMultiplier=1` 時）で、想定の約1.7倍。コメントによると `800px` は
    「10パート超で常に1段/ページ」という以前のハードコード動作に合わせて調整された値であり、
    そもそも「1段がページ内に収まる」ことまでは保証していない。
  - 本来は `ScaledPageWrapper.tsx`（`.print-page` の実測高さ×倍率を `.page-wrapper` に
    反映し、A4を超える内容でもページ自体を伸ばす設計、コード内コメントに明記あり）が
    このケースを救う想定だったと見られるが、`.print-page` 自身のCSSが
    `height: 297mm`（固定）+`overflow: hidden` になっているため、
    `offsetHeight` が常に1123px止まりで計測が機能せず、意図した「ページを伸ばす」
    救済策が働いていない。
  - `BASE_SYSTEM_HEIGHT_PX.ensembleLarge` はパート数に関わらず「10パート超はすべて800px」という
    二値の閾値になっており、パート数に比例したスケーリングをしていない点も一因
    （`classical-orchestra` 相当の12パートは未検証だが、同じ定数を使うため潜在的に影響を受ける可能性がある）。
- **重要度**: 高。`romantic-orchestra`（大編成オーケストラ）はアプリ内蔵プリセットの中で
  最大編成であり、実在する正式なプリセットの通常利用で発生する。印刷・PDF出力だけでなく
  通常の編集画面でも弦楽器主要5パートが操作不能になるため、実質的にこの編成では
  弦楽器パートを一切編集できない状態になっている。
- **対応状況**: 未修正。原因は特定できたが、正しい修正には以下の設計判断が必要で、
  一晩の無人セッションで安全に実施するにはリスクが高いため、次フェーズでの人間レビューに委ねる。
  - (a) `.print-page` の `height: 297mm` を `min-height: 297mm` に変更し、大編成では
    ページを縦に伸ばして1段をすべて収める（画面・PDF出力には効くが、実紙への物理印刷では
    ブラウザの印刷エンジンが297mmを超えた部分を次の物理用紙へ強制的に送る可能性があり、
    ページ番号・小節継続などの整合性が崩れる恐れがある。要実紙印刷での検証）。
  - (b) `BASE_SYSTEM_HEIGHT_PX.ensembleLarge` をパート数に比例する計算式に置き換え、
    17パートでも `maxSystemsPerPage` の算出だけでなく「1段の実際の高さが常にページに収まる」
    ところまで保証する（さらに、収まらない場合は `notationSizeMultiplier` を自動的に
    縮小するなどのフォールバックが必要）。
  - いずれも印刷・PDF出力・全編成サイズに影響する共通コードのため、変更後は
    `romantic-orchestra` 以外の全プリセット（`piano`／`string-quartet`／`string-orchestra`／
    `chamber-orchestra`／`classical-orchestra`／`wind-band`）で印刷プレビューの
    リグレッション確認が必須。

### 2. フェーズAの「(b) 手入力△」の原因の再評価

- フェーズAでは「ブラウザ自動操作ツールの座標ズレ」が原因として記録されていたが、
  今回の調査で **Vln I 自体が上記バグにより描画されていなかった** ことが濃厚な原因として判明した。
  ツール側の座標ズレ問題（下記メモ）自体は今回も再現したため、両方が絡んでいた可能性が高い。
  次回、上記バグ修正後に同じ操作を再検証すること。

### 3. ［低・情報］ブラウザ自動操作ツールの安定性（フェーズAからの継続）

- 本セッションでも、`window.scrollTo()` でページ外の位置へスクロールした直後に
  `computer` の `screenshot` が黒一色の画像を返す不具合が高頻度・再現性高く発生した
  （`navigate` による再読み込みで一時的に復旧するが、スクロールすると再発）。
  1秒・3秒の待機を挟んでも改善せず。
- 回避策として、`resize_window` でビューポート自体を縦長（例: 1200×4000）にし、
  スクロールなしで多くのコンテンツを1枚のスクリーンショットに収める方法が有効だった
  （黒画面にならない）。次回セッションでは最初からこの方法を使うと良い。
- 座標クリックによる音符追加の自動操作は、可視パート（Picc.）に対しても今回は
  最終的に成功を確認できなかった（クリックしても音符が置かれた形跡がない）。
  引き続き人間による実機確認を推奨する。

## 修正内容

### 発見事項1の根本原因（追加調査）
フェーズBの原因分析（`BASE_SYSTEM_HEIGHT_PX.ensembleLarge=800px` が実測1384pxと乖離）に加え、
実装・実機検証を通じて**もう1つの独立したバグ**が見つかった。

- `src/components/PianoSystemCanvas.tsx` の `computeLayout()` が返す段の高さ `sysH` は
  `STAVE_SPACING=80px` 等の「`ctx.scale(s,s)` 適用前の論理座標」で計算されるが、
  `renderer.resize(W, sysH)` にはこの `sysH` を**そのまま（scale を掛けずに）**渡していた。
  `ctx.scale(s,s)` は以降の描画内容だけを縮小するため、音符・五線が視覚的に縮小されても
  SVG要素自体の実ピクセルサイズ（`.system-stack` / `.print-page` が高さ判定に使う
  実際のボックスサイズ）は常に scale=1相当のまま変わらず、「音符の大きさ」を
  自動縮小しても段の高さがまったく縮まらない状態だった。
  これは「音符の大きさを自動縮小すれば大編成でも収まる」という修正方針(b)を
  実装しただけでは効かない、という形で実機検証時に発覚した。

### 適用した修正（決定済み方針(b)、コミット順）
1. `fix: 大編成オーケストラで弦5パートが消えるバグを修正`
   - `measureLayoutUtils.ts` に `estimateEnsembleSystemHeightPx(partCount)` を追加。
     編成譜の段高さを `81px/パート + 16px` の一次関数で計算する
     （四重奏の実測基準340px/4パートと romantic-orchestra の実測1384px/17パートの
     2点から校正。従来の固定二値 `ensembleSmall=400px`/`ensembleLarge=800px` を廃止）。
   - `computeEnsembleAutoFitMultiplier(partCount, pageBudgetPx)` を追加。
     「1段がページに収まらない編成だけ」音符サイズを自動的に縮小する倍率
     （収まる編成では常に1.0＝縮小なし）。判定には本文ページ相当の予算
     （タイトルページ基準の厳しい `SCORE_AREA_BUDGET_PX=938px` ではなく、
     A4高−既定余白から求めた約1024px）を使い、classical-orchestra 等の
     標準編成を不必要に縮小しないようにした。
   - `ScorePage.tsx`: `maxSystemsPerPage` と `effectiveRenderScale` の両方に
     `ensembleAutoFitMultiplier` を反映。「音符の大きさ」スライダー横に
     自動縮小時の実効%を表示。
   - `.print-page` の `height: 297mm` は変更しなかった（実紙印刷でのページ整合
     リスクを避けるため。判断理由は `.claude/specs/view-zoom/design.md` に記録）。
   - ユニットテスト `src/utils/ensembleSystemHeight.test.ts` を新規追加。
2. `fix: 音符の大きさ縮小がSVGの実サイズに反映されていなかった問題を修正`
   - 上記の実機検証で発覚した `PianoSystemCanvas.tsx` の `renderer.resize` バグを修正。
     `renderer.resize(W, sysH)` → `renderer.resize(W, sysH * resizeScale)` の1行修正で、
     single/piano/quartet/ensemble すべての譜面種別に効く共通コンポーネントの修正。
3. `docs: 大編成オーケストラの弦パート消失バグ修正をREADME・設計書に追記`
   - README.md「音符の大きさ調整」節・`.claude/specs/view-zoom/design.md`
     「追補」章に修正設計・検証結果を記録。
