# 受容中のセキュリティリスク（music-editer）

ここに書かれているものは「認識した上で、いま直さない」と判断したもの。判断者は運用者。
**未評価のものをここに書いてはいけない**——到達可能性の評価と再検討条件が無い項目は、
受容ではなく単なる放置になる。

セキュリティスキャン（`.github/workflows/security.yml`）は critical のみ PR をブロックし、
high は表示のみにしている。**その緩和が正当であることの根拠がこのファイル**なので、
ここに載っていない high が出たら緩和の前提が崩れたものとして扱うこと。

## このアプリの攻撃面

**サーバーを持たないブラウザアプリ**である。バックエンド・認証・ユーザーアカウントが無く、
譜面データは利用者のブラウザの localStorage にのみ保存される。したがって
「他人のデータが見える」類のリスクは構造的に発生しない。

代わりに注意すべきは次の2つ:

1. **外部ファイルの読み込み**（MusicXML 読込・`.score.json` の読込）。攻撃者が細工した
   ファイルを利用者に開かせる経路がありうる
2. **フィードバック機能**（状態JSONをクリップボードへコピーし GitHub Issue 画面を開く）。
   譜面の内容が公開リポジトリへ投稿される導線なので、何が含まれるかの明示が要る
   （ボタンのツールチップと Issue テンプレートに記載済み）

## 到達可能性の分類

| | 内容 | 対応 |
| --- | --- | --- |
| 細工した譜面ファイルでコード実行・情報送信に至る | P0: 即時対応 |
| 利用者の意図しないデータが外部へ出る | P1 |
| ビルド時のみ動作する依存の脆弱性（開発者環境のみ） | 到達経路の有無で判断 |

## 記録のルール

- 受容の判断は運用者が行う。エージェントが勝手にこのファイルへ追記しない（提案はPRで行い承認を得る）
- 各項目には必ず「到達可能性の評価（根拠つき）」と「再検討条件」を書く
- 再検討条件を満たしたら、受容を解除して通常の修正フローに戻す
